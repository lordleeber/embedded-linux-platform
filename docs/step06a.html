6a.1起點為什麼

先讀別人的程式，再自己寫

Phase 2 的 GPIO 只有一條線、一個電位，所以可以直接動手。INA219 不一樣：它是一顆有 6 個 16-bit register 的晶片，要先設定量測範圍和校正值，讀回來的數字還要依設定換算。這些規則寫在 datasheet 裡，而廠商範例是「已經能動」的一份實作。先把它讀懂，再拿 datasheet 一條一條核對，就知道哪些數字可以照抄、哪些要自己算。這一章就會挑出一處：它的註解和程式寫的是兩組不同的數字（6a.5）。

互動雙方：I2C 的 controller（舊稱 master）是 Jetson 的 I2C 控制器 c250000.i2c，Linux 叫它 i2c-7；target（舊稱 slave）是 UPS 模組上的 INA219，7-bit 位址 0x41。controller 負責產生時脈、決定什麼時候讀寫，target 只回應叫到自己位址的傳輸。userspace 這一側是 ina219.py，它透過 python3-smbus 打開 /dev/i2c-7。這一步不做：不改範例、不寫自己的工具、不手動 i2cget / i2cset（6-b），不寫 kernel driver、不用 hwmon（Step 7、8）。

I2C
兩條線（SCL 時脈、SDA 資料）的匯流排，一條 bus 上可以掛多個 target，用 7-bit 位址區分。這台的 i2c-7 接在 40-pin header 的 pin 3（SDA）和 pin 5（SCL）。
INA219
TI 的電流 / 電壓監測晶片：量一顆小電阻（shunt）兩端的電壓算出電流，同時量 bus 電壓，晶片內部再乘出功率。
shunt（分流電阻）
串在電流路徑上的小電阻（範例的註解假設 0.01 Ω）。電流越大，兩端壓差越大：1 A 只有 10 mV。
i2c-dev
kernel 模組，把每條 I2C bus 開成 /dev/i2c-N，讓 userspace 用 ioctl() 自己指定位址、發起傳輸。這台的 /dev/i2c-7 是 root:i2c 0660，使用者在 i2c 群組就能用，不需要 root。
SMBus
I2C 上的一套固定傳輸格式（「寫 register 編號、再讀 N bytes」這類）。python3-smbus 是 Debian / Ubuntu 套件裡的 C 擴充模組，底層呼叫 i2c-dev 的 I2C_SMBUS ioctl。
6a.2路徑一次讀 register

一次讀 register 經過哪些站

controller 的那一格是傳輸在線上的樣子（依 SMBus 的 block read 格式）：先以寫入方向送出 register 編號，不放開 bus（RESTART），再以讀取方向收兩個 byte。這一步沒有接示波器或邏輯分析儀，線上的波形沒有實測，這裡寫的是格式。

6a.3讀寫16-bit

每個 register 是 16 bit，高位 byte 先送

  • smbus.SMBus(7) 打開 /dev/i2c-7。bus 編號 7 是這台 Jetson 的 Linux 編號，換一塊板子可能不同（6a.8 說怎麼查）。
  • read()：INA219 先送高位 byte（MSB），所以第一個 byte 左移 8 位。Jetson 的 CPU 是 little-endian，如果把兩個 byte 直接當成一個 16-bit 整數讀，高低位會對調：bus voltage 的 0x60 0x9A 會變成 0x9A60，換算出來是 19.756 V 而不是 12.364 V。
  • write()：同樣高位在前。
  • 建構子最後一行呼叫 set_calibration_16V_5A()：只要建立物件，就會寫入晶片。這支範例不是純讀取的工具。
位址register範例怎麼用
0x00 Configuration量測範圍、增益、ADC 解析度與取樣數、工作模式啟動時寫 0x0EEF
0x01 Shunt Voltageshunt 兩端電壓，有號數，10 µV/bit每輪讀，但輸出那行被註解掉
0x02 Bus Voltagebit 15..3 是電壓（4 mV/bit），bit 1 CNVR、bit 0 OVF 是狀態每輪讀，印成 Load Voltage
0x03 Power晶片算出的功率，單位由校正值決定每輪讀
0x04 Current晶片算出的電流，有號數，單位由校正值決定每輪讀
0x05 Calibration沒寫之前是 0，Current / Power 會一直是 0啟動時寫 26868（0x68F4）
6a.4啟動寫兩個 register

啟動時寫入的兩個值

常數代進去：(0<<13) | (1<<11) | (0xD<<7) | (0xD<<3) | 7 = 0x0EEF。拆開來看：

欄位bit值意思
BRNG130bus 電壓範圍 16 V（3S 電池最高 12.6 V，夠用）
PG12..1101shunt 增益 /2，量測範圍 ±80 mV（0.01 Ω 下是 ±8 A）
BADC10..71101bus 電壓：12-bit、32 次平均，一次轉換約 17 ms
SADC6..31101shunt 電壓：同上
MODE2..0111shunt 和 bus 連續轉換

欄位位置與意義照 TI 的 INA219 datasheet；tests/test_ina219_sample.py 的 test_config_fields 把這張表逐欄寫成斷言。實機上，範例跑過之後讀回 Config 是 0x0EEF、Calibration 是 0x68F4（實機測試 test_chip_keeps_what_the_script_wrote）。

為什麼要先寫 Calibration？INA219 的 Current register 不是直接量到的，是晶片拿 shunt 電壓乘上校正值算出來的（datasheet：Current = Shunt × Cal / 4096），Power 再由 Current 和 bus 電壓相乘。沒寫校正值時它是 0，電流和功率就一直是 0。

6a.5校正註解 ≠ 程式

註解說 13434，程式寫 26868

set_calibration_16V_5A() 裡有一大段註解，一步一步推導校正值。照著讀會發現，註解算出來的數字和下一行程式寫的不一樣：

項目註解程式由程式的 Cal 推回
Calibration1343426868—
Current LSB100 µA/bit0.1524 mA/bit0.04096 / (26868 × 0.01) = 0.15245 mA
Power LSB2 mW/bit3.048 mW/bit20 × 0.1524 mA = 3.048 mW
最大電流3.2767 A—32767 × 0.1524 mA = 4.99 A

程式這一組彼此一致：Current LSB 選 5 A / 32767 ≈ 0.1526 mA（註解第 3 步算的 MinimumLSB），Cal 照 datasheet 公式算出來約 26868，Power LSB 是 Current LSB 的 20 倍（datasheet 規定的關係），滿刻度剛好是函式名稱說的 5 A。註解則是另一組設定（100 µA、13434）留下來的，沒跟著改。前提是 shunt 真的是 0.01 Ω：這是註解的假設，這一步沒有拆模組量電阻，沒有查證。

測試的作法：test_lsb_constants_follow_from_calibration 從 Cal 推回 LSB，和程式的常數比對；test_comments_disagree_with_the_code 把兩組數字都釘住。哪天廠商改了範例，這兩條會先紅。

6a.6換算raw → 單位

四個 getter：位移、符號、乘上 LSB

  • 有號數：if value > 32767: value -= 65536 是手寫的 16-bit 二補數轉換。電流有方向，流過 shunt 的方向反了，Current 就是負的。
  • bus voltage 右移 3 位：低 3 bit 不是電壓。bit 1 是 CNVR（有新的轉換結果），bit 0 是 OVF（數學溢位）。不右移的話，狀態位會混進電壓裡。
  • Power 理論上不會是負的，範例照樣做了符號轉換；無害，但也沒必要。

Shunt Voltage0x00000 × 10 µV0 mV

前四列是 2026-10-11 從板子讀到的 raw 值；最後一列是測試裡的例子（test_current_is_signed）。CNVR 還有一個實機才看得到的行為：datasheet 說讀 Power register 會把它清掉。範例每輪都讀 Power，所以範例剛讀完時 CNVR 是 0，約 34 ms 後（bus、shunt 各一次 17 ms 的轉換）又變 1；實機測試 test_reading_power_clears_the_conversion_ready_bit 驗的就是這件事。

6a.7主迴圈每 2 秒

主程式：位址 0x41、電量是線性估計

  • 位址 0x41：類別的預設值是 0x40（INA219 的 A0、A1 都接地時的位址），主程式傳 0x41，代表這塊模組把 A0 接到 VS（依 datasheet 的位址表）。拿這個類別去讀別的模組，位址要自己改。
  • 電量百分比：(V − 9) / 3.6，9 V = 0 %、12.6 V = 100 %，中間線性，超出範圍夾住。12.6 V 和 9 V 正好是 3 顆鋰電池串聯（3S）每顆 4.2 V 和 3.0 V。鋰電池的放電曲線不是直線，所以這只是粗估。
  • 被註解掉的兩行：bus voltage 量的是 shunt 的負載側，電源側的電壓要再加上 shunt 壓降。範例只印負載側；壓降在 1 A 時是 10 mV，對電量估計影響很小。
  • 沒有結束條件：Ctrl-C 結束，會印出 KeyboardInterrupt 的 traceback（下面的實測輸出看得到）。

在 repo 根目錄執行（使用者要在 i2c 群組；timeout -s INT 等於 5 秒後幫你按 Ctrl-C，-u 讓輸出不被緩衝，否則被打斷時可能什麼都沒印出來）：

bus 編號怎麼對到實體腳位：i2cdetect -l 列出 i2c-7 c250000.i2c，Step 5-b 已經查過 c250000.i2c 是 header pin 3 / 5（pin 27 / 28 是 i2c-1 c240000.i2c，上面有板上的 ina3221，不要搞混）。

6a.9對照不用 overlay

為什麼這次不用像 Step 4、5 那樣設 overlay

Step 4-b、5-b 都得改 Device Tree、重開機，這一章卻什麼都沒設，python3 ina219.py 就讀得到。原因要看 overlay 當時在解決什麼問題：

overlay 在 Step 4-b / 5-b 做的事這一章為什麼不需要
讓我們的 driver 被 probe：platform driver 靠 DT 節點的 compatible 配對，沒有節點，insmod 了也不會呼叫 probe()沒有我們的 driver。範例走 i2c-dev：開 /dev/i2c-7、用 I2C_SLAVE ioctl 指定位址 0x41，再收發 byte。kernel 只負責把 byte 送上線，不知道 0x41 是什麼晶片；register 的意義全在 Python 裡（圖 6.1）
告訴 driver 硬體接在哪：led-gpios、button-gpios 寫在 DT 裡，driver 不寫死腳位bus 7、位址 0x41 直接寫死在範例裡（6a.3、6a.7）
設定 pad：pin 29 開機是 tristate（4-a 的坑），pin 33 要上拉；overlay 帶了 pinctrl 狀態NVIDIA 的基礎 Device Tree 已經啟用 c250000.i2c（status = "okay"，400 kHz），開機就有 /dev/i2c-7。pin 3 / 5 是 header 上專用的 I2C 腳位，直接接 SoC、不經 TXB0108（5-b 查過的載板規格書）

可以自己確認這幾件事（不需要 root）：

ls -l /dev/i2c-7; cat /sys/bus/i2c/devices/i2c-7/name; tr -d '\0' < /proc/device-tree/bus@0/i2c@c250000/status; echo; ls /sys/bus/i2c/devices/ | grep '^7-' || echo "no I2C client on bus 7"
crw-rw---- 1 root i2c 89, 7 Aug 26  2025 /dev/i2c-7 «1»
c250000.i2c «2»
okay «3»
no I2C client on bus 7 «4»
  1. 1i2c-dev 的節點已經在了（這台 kernel 是 CONFIG_I2C_CHARDEV=y，內建，不用載模組）；i2c 群組可讀寫。
  2. 2bus 7 就是 c250000.i2c 這個控制器。
  3. 3控制器在基礎 DT 裡就是啟用的。
  4. 4kernel 在 bus 7 上沒有任何 I2C client（有的話會出現 7-0041 這種目錄）：DT 裡沒有描述 0x41 上的晶片，也就沒有 driver 綁上它。範例照樣讀得到，因為 i2c-dev 不需要 client。

反過來說，不需要 overlay 是因為這一章不寫 driver。4-a 的 LED 也是 userspace 程式，卻得先開 pad；差別在 pin 29 開機時不能輸出，而 pin 3 / 5 開機就是 I2C 功能。這一點沒有讀 pinmux 暫存器確認，依據是「什麼都不設，掃描和讀寫就都成功」。

到 Step 7 寫自己的 I2C driver（struct i2c_driver、probe()）就需要了：kernel 要先知道「bus 7 的 0x41 上有一顆 edge,ina219」，才會建立 I2C client（第 4 點會多出 7-0041）並呼叫 probe()。這要在 overlay 裡、c250000.i2c 底下加一個節點，形狀和 4-b 的 LED 節點一樣靠 compatible 配對，只是多了 reg 寫 I2C 位址：

ina219@41 {
    compatible = "edge,ina219";
    reg = <0x41>;
};

（這段是 phase03.md 的規劃，位址照這一章改成 0x41；實際的 overlay 在 Step 7 才寫。）另一個不改 DT 的作法是測試時從 sysfs 臨時建立 client（new_device），Step 7 再比較兩者。

6a.10測試red → green

把章裡的每個說法寫成測試

這一步沒有新程式，要測的是「章裡對範例的說法」。tests/test_ina219_sample.py 共 24 個案例，期望值照 INA219 datasheet 寫，不是從範例的輸出抄：

  • 入庫的副本（2）：SHA-256 和記錄的一致；板上有 ~/UPS_Power_Module_C/ina219.py 時，兩份逐 byte 相同。
  • 啟動序列（5）：用假的 smbus 模組（放進 sys.modules，範例 import 到的就是它）記下所有寫入：主程式用 bus 7，讀寫都對位址 0x41；先寫 Calibration [0x68, 0xF4] 再寫 Config [0x0E, 0xEF]；Config 逐欄拆解（拆的是假 bus 記下的那筆寫入，不是測試自己寫的常數）；LSB 常數和 Cal 一致；註解和程式的兩組數字都釘住。
  • 換算（5）：bus voltage 丟掉低 3 bit、高位 byte 在前（反過來就不是 12.364 V）、shunt 與 current 是有號數、power 乘 3.048 mW。
  • 主迴圈（3）：用 runpy 把範例當主程式跑一輪（time.sleep 換成丟例外來停下），比對印出的四行；電量在 9 V、10.8 V、12.6 V 與範圍外的值；raw 是負的，電流就印成負數（只驗算術：這塊模組上哪個方向是負的還沒實測）。
  • 驗收腳本（4）：參數錯誤回 2；腳本用 i2cdetect -y -r（6a.8）；用 timeout --foreground 跑範例，Ctrl-C 才會立刻生效；PASS 訊息寫出實際的判定範圍（後兩條是 code review 後補，先紅再修）。
  • 讀輸出的 helper（1）：範例卡住不輸出時，實機測試要在時限內失敗，而不是一直等（code review 後補）。
  • 實機（4）：EDGE_INA219_HW=1 才跑，i2c 群組即可。範例印出 9～12.8 V 且電量照公式；跑過後 Config / Calibration 讀回 0x0EEF / 0x68F4；讀 Power 清掉 CNVR、0.1 秒後又設起來；讀不存在的位址 0x45 得到 EREMOTEIO（errno 121，模組被拔掉時範例會看到的錯誤）。

紅燈紀錄：範例還沒複製進 repo 時，19 個案例裡 1 個 failure、13 個 error（實機模式 14 個 error）；只有「Config 逐欄拆解」（那時拆的還是測試自己寫的常數，code review 指出它永遠不會紅，已改）和「讀不存在的位址」兩條在那之前就會過，它們不依賴範例，是守門用的。之後有兩條是我自己的期望寫錯，詳見 6a.12。

python3 -m unittest discover -s tests -p 'test_ina219_sample.py' -v
EDGE_INA219_HW=1 python3 -m unittest discover -s tests -p 'test_ina219_sample.py' -v

第一行不碰硬體（實機 4 個 skip，沒有 ~/UPS_Power_Module_C 時再多 skip 1 個）；第二行要有 UPS 模組接在 bus 7。注意實機測試會讓範例跑一下，也就是會寫入 Config 和 Calibration（寫的是範例本來就會寫的值）。

6a.12常見錯誤

踩過的坑

以為 i2cdetect 的空白是「沒有裝置」

症狀
i2cdetect -y 7 的 0x40 那列整列空白。
後果
以為模組沒接好、位址不對。
正解
Tegra 不支援 Quick Write，空白是沒掃；用 -y -r。

timeout 包 python，結果什麼都沒印

症狀
timeout 5 python3 ina219.py 結束碼 124、沒有任何輸出。
後果
以為範例沒讀到東西。
正解
stdout 接管線時 Python 會緩衝，被殺掉就沒有寫出；加 -u。

以為範例跑完 CNVR 一定是 1

症狀
實機測試讀到 0x6098，CNVR = 0。
後果
測試紅了，像是晶片沒在轉換。
正解
讀 Power 會清掉 CNVR，範例每輪都讀；等一次轉換（約 34 ms）再看。

相信範例的註解

症狀
註解寫 Cal 13434、100 µA/bit。
後果
照註解換算，電流差 1.5 倍。
正解
以寫進晶片的值為準，用 datasheet 公式從 Cal 推回 LSB。

以為範例只會讀

症狀
只是「跑一下看數字」。
後果
建立 INA219 物件就覆寫 Config 與 Calibration；之後別的程式看到的是範例的設定。
正解
知道它會寫；要純讀取，等 6-b 的工具。

以為 timeout 包住的程式收得到 Ctrl-C

症狀
驗收腳本在拔插那 20 秒內按 Ctrl-C，沒反應。
後果
要等整段取樣結束才退出（code review 指出，實測：8 秒的 timeout，trap 在第 8 秒才跑）。
正解
timeout --foreground：範例留在終端機的 process group，Ctrl-C 直接送到它（實測第 1 秒）。

直接用類別的預設位址

症狀
INA219() 不傳參數。
後果
預設 0x40，這塊模組在 0x41：Errno 121 Remote I/O error。
正解
照主程式傳 addr=0x41；先用 i2cdetect -y -r 確認。
6a.13收尾6-a → 6-b

這一步做到了什麼

  • 逐行讀懂廠商範例：bus 7、位址 0x41、高位 byte 在前、啟動時寫 Calibration 26868 與 Config 0x0EEF、四個 getter 的換算與電量公式。
  • 每個說法都有測試核對（24 個，含 4 個實機）；驗收 0 failure（--no-unplug）。
  • 找出註解和程式不一致，並從 datasheet 公式確認程式那組才是對的（前提：shunt 0.01 Ω）。
  • 沒有實測：拔掉 DC adapter 時的電流與方向（遠端登入，沒人能拔）。
  • 沒有查證：shunt 電阻值、模組的電源路徑（INA219 在電池側是由電壓推論的）。

下一章 6-b 拿掉 python3-smbus：先用 i2cget / i2cset 手動讀寫同樣的 register，再寫一支 C++ 小工具直接對 /dev/i2c-7 發 ioctl，印出 raw 值和換算結果，並且在模組不在時明確回報 I/O error。這一章的換算表和測試向量就是它的期望值。

1. 範例把讀到的兩個 byte 寫成 (data[0] << 8) + data[1]，如果寫反成 (data[1] << 8) + data[0]，12.364 V 會變成多少？

0x9A60 >> 3 = 4940，× 4 mV = 19.76 V。INA219 先送高位 byte；把兩個 byte 照 CPU（little-endian）的順序拼，就會高低對調。

2. 剛上電、沒跑過範例的 INA219，讀 Current register 會得到什麼？為什麼？

0。Calibration register 上電是 0，而 Current 是晶片用 shunt 電壓乘上校正值算出來的，所以一定要先寫 Calibration。

3. 註解寫 Current LSB 100 µA，程式寫 0.1524 mA。要相信哪一個？怎麼判斷？

相信和實際寫進晶片的 Calibration（26868）一致的那個：Current LSB = 0.04096 / (Cal × Rshunt) = 0.15245 mA。註解的 100 µA 對應的是 13434，程式並沒有寫這個值。

4. i2cdetect -y 7 的 0x40 那一列整列空白，代表 bus 上沒有 0x40～0x4f 的裝置嗎？

不代表。空白是「跳過沒掃」（控制器不支援 Quick Write），-- 才是「掃了沒回應」。要用 -r 改成讀取探測。
