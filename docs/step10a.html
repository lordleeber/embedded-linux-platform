OLED：把協定搬進 kernel

Step 9 用 userspace 工具證明了「該送哪些 byte」。這一步把同一串 byte 交給一個自己寫的 I2C client driver edge_oled：probe 時初始化面板，driver 持有一份 1024 byte 的畫面，userspace 經 /dev/edge_oled 寫整張畫面、清除、填滿。重點不在畫圖，而在 裝置的生命週期：錯誤怎麼往上回報、OLED 斷電後怎麼恢復、driver 被 unbind 時還開著的檔案怎麼辦。

10a.1起點為什麼

同樣的 byte，換一個主人

Step 9 的 oled_probe 每次執行都自己開 bus、自己 init、自己送畫面，程式結束就什麼都不剩。這在驗證協定時正好，但不能當成系統的一部分：兩支程式同時畫，就會互相蓋掉；沒有人記得面板現在是什麼狀態；Step 10-c 要週期刷新電池數值，也不該讓每支 app 都懂 SSD1306。

把它變成 driver 之後，面板只有一個主人：edge_oled 綁定 0x3C、在 probe 時初始化、持有畫面，userspace 只需要知道「寫 1024 byte」與兩個 ioctl。這一步刻意只做骨架（phase04 的 10-a）：transport 與 lifecycle，不做文字。

互動雙方：I2C 這一層和 Step 9 相同，controller 是 c240000.i2c（i2c-1，100 kHz），target 是 SSD1306（0x3C），資料只往 OLED 寫。多出來的一層是 edge_oled_ctl（userspace）→ /dev/edge_oled → edge_oled.ko。這一步不做：字型與文字排版（Step 10-b）、顯示 INA219 的數值（Step 10-c）。

shadow frame
driver 自己保存的那 1024 byte 畫面。SSD1306 在 I2C 下不能讀回 GDDRAM，所以「面板上現在是什麼」只能靠 driver 記住自己送過什麼。
i2c_master_send()
I2C client driver 送一個寫入訊息的 kernel API：START、位址 + W、一串 byte、STOP。回傳送出的 byte 數或負的 errno。Step 7 的 INA219 用的是 SMBus helper；SSD1306 的訊息長達 129 byte，用 plain I2C write。
memdup_user()
配一塊 kernel 記憶體、把 userspace 的資料整段複製進來；失敗時回 ERR_PTR(-EFAULT) 之類的錯誤指標。
kref
kernel 的引用計數。kref_get() 加一、kref_put() 減一，減到 0 時呼叫你給的釋放函式。這一步用它讓結構活得比「driver 綁定」久（10a.7）。
unbind / bind
寫 client 名稱到 /sys/bus/i2c/drivers/<driver>/unbind，kernel 就呼叫 remove()，module 仍留在記憶體裡；bind 再呼叫一次 probe()。Step 4-b 起每個 driver 都這樣測。
10a.2全景一次 write()

edge_oled_ctl edge：一次 write()，9 個 I2C 寫入

一張畫面約 1050 byte（含每個訊息的位址 byte），每個 byte 在線上是 9 個 clock（8 bit + ACK）：100 kHz 下約 94 ms，實測連寫 200 張平均 96.6 ms（第二輪 96.4 ms）。Step 10-c 若每秒刷新一次綽綽有餘。

10a.3綁定DT 節點

節點掛在 gen2_i2c，不是 INA219 那條 bus

和 Step 7 的 INA219 一樣，OLED 用 Device Tree 描述，加在同一份 overlay 裡。差別在 target：OLED 接在 pin 27/28，也就是 /bus@0/i2c@c240000，基底 device tree 給它的 label 是 gen2_i2c。Step 9 已經預告過這個坑：沿用 &hdr40_i2c1 會把節點掛到 INA219 那條 bus（c250000）上。

開機時 I2C core 把這個子節點變成 client 1-003c。client 的名字是 compatible 去掉廠商前綴：edge-ssd1306。Step 7 code review 學到，這個名字也會拿去比對每個 driver 的 i2c_device_id 表，所以不能取成上游 driver 認得的名字（例如 ssd1306）；驗收腳本用 modules.alias 確認沒有 module 認領它。

重開機後可以確認節點和 client 都在（在任何目錄都能跑，不需要 root；module 沒載入時 client 存在但沒有 driver）：

如果看不到 oled@3c，表示這次開機用的還是舊的 overlay：在 repo 根目錄 make -C dts，再 sudo python3 scripts/install_edge_gpio_overlay.py install dts/edge-gpio-overlay.dtbo，重開機（這台沒有 runtime overlay）。modalias 是 of: 開頭：udev 自動載入 module 時看的是 compatible，不是 client 名稱。

10a.4介面/dev/edge_oled

只收整張畫面

phase04 要的最小介面是「clear、fill、寫入 raw framebuffer」。include/edge_oled.h 是 kernel 與 userspace 共用的 header（同 Step 3 的 edge_test_ioctl.h）：

操作行為
write()剛好 1024 byte，一次就是整張畫面，送完才回傳；其他大小 -EINVAL，畫面不動。file offset 不理會。
read()讀回最後一次完整送出的畫面（driver 保存的那份，晶片讀不到）。寫到一半失敗的那張不算，雖然面板上可能已經是半張新畫面。跟一般檔案一樣照 offset 讀：讀完一次要 lseek(0) 或用 pread() 才能再讀。
EDGE_OLED_IOC_CLEAR全部 0，送出。
EDGE_OLED_IOC_FILL每個 byte 設成參數值（0xff 全亮），送出。參數是固定大小的 __u8，32 / 64-bit 編號相同。

為什麼不讓 write() 寫一部分？寫一半的畫面會讓面板停在「上半新、下半舊」，而一個 write() 可能被 kernel 切成好幾次傳給 driver 的情況（例如 userspace 用小 buffer 的 cat）也很難處理。一次一整張，畫面永遠是某一張完整的圖。

畫面的排列就是 Step 9 講的 GDDRAM 版面：frame[page × 128 + x]，bit 0 在上。edge_oled_ctl 的三張圖直接用 Step 9 的 ssd1306::test_picture()（這一步從 oled_probe.cpp 搬進 ssd1306.h），所以人眼看到的畫面可以和 Step 9 一張一張比。不接 OLED 也能看：把一個普通檔案當成裝置，write() 照樣寫進去（在 repo 根目錄，第一行會建置）：

10a.5傳輸flush

一次 flush：失敗了，下次就從頭來

Step 10-b 改了 edge_oled_flush()：每次 flush 都重送設定，結尾每次都送 Display ON。原因是 OLED 在兩次寫入之間斷電又接回時，下面這一版會讓螢幕一直黑著（實測重現過）。這一章 edge_oled.c 的五段節錄因此釘在 Step 10-a 合併時的 commit（外框標 @4479e44）。現在的寫法見下一章。

所有 I2C 傳輸都經過兩個函式。edge_oled_send() 把 control byte 放在前面、送一個訊息；edge_oled_flush() 決定要送哪些訊息：

幾個選擇：

  • 錯誤只回報、不重試（phase04：「不要在 probe 裡無限 retry」）。i2c_master_send() 的負值原樣往上傳：沒 ACK 是 -EREMOTEIO，userspace 看到的就是 Remote I/O error。回傳的 byte 數比要求的少（正常不會發生）也當成 -EIO，不假裝成功。
  • init 不是只在 probe 做一次。直覺的做法是「probe 初始化，之後只送畫面」。可是 OLED 斷電再接回時，晶片回到 power-on reset（Step 9 實測螢幕全黑；依 datasheet，reset 後 display OFF、charge pump 也關），只送畫面會全部 ACK、螢幕卻是黑的。所以 initialized 在任何一次失敗後變成 false，下一次 flush 會重送 25 byte 的 init，畫面送完再開顯示。驗收時四條線全拔再接回，下一次 write 自己把畫面帶回來了（10a.10 的 ⑩）。
  • byte 不在 driver 裡。init 序列與 window 指令放在 include/edge_oled_proto.h（plain C，kernel 能 include），test_edge_oled_proto 把它和 Step 9 的 ssd1306.h 逐 byte 比對：driver 送的就是 Step 9 在實機驗證過的那一串。

這個設計的盲點：driver 只有在「傳輸失敗」時才知道要重新 init。如果 OLED 在兩次寫入之間斷電又接回、中間沒有人寫，下一次寫入會成功 ACK，但只送了畫面，螢幕會一直是黑的（依 reset 狀態推論，沒有實測）。Step 10-c 要長時間週期刷新，這會變成真問題，已排進 Step 10-b 的「從 Step 10-a 帶過來的」：先寫出重現步驟，再決定是每次都送 init（約 2.5 ms）還是別的做法。結案：Step 10-b 實測重現了（接回後寫入全部 ACK、螢幕全黑），改成每次 flush 都送設定。

10a.6buffer誰擁有畫面

先複製，再上鎖

phase04 要求「buffer ownership 要明確」。這裡的答案是：畫面屬於 driver，userspace 的 buffer 只是來源。write() 的順序是重點：

  • 大小先檢查：不是 1024 就 -EINVAL，什麼都沒動。device 測試寫了 0、1、1023、1025、128 byte，都是 EINVAL，而且讀回來的畫面還是之前那張。
  • 先複製到暫存區：如果直接 copy_from_user() 進 shadow frame，指標在中途失效時 shadow frame 會只剩一半。memdup_user() 失敗就直接回錯誤，shadow frame 完全沒動。
  • 送成功了才寫進 shadow frame：flush 送的是暫存區，全部 ACK 才 memcpy 進 oled->frame。第一版是先複製再送，code review（PR #14）指出：送到一半失敗時，read() 會讀回一張面板從沒完整收到的畫面。驗收腳本因此加了一項：拔線時寫一張不同的圖（失敗），讀回來必須還是拔線前的 EDGE（10a.10 的 ⑨）。
  • 鎖裡先看 client：driver 已經被 unbind 時它是 NULL，回 -ENODEV（下一節）。
  • 只收整張畫面：如果讓 write() 照 offset 寫一部分，短寫或壞指標都會讓面板停在半張新、半張舊（10a.4）。

read() 直接在鎖裡 simple_read_from_buffer()（它會呼叫 copy_to_user()）。持有 mutex 時發生 page fault、睡一下是允許的（spinlock 才不行）；這個 driver 沒有 mmap，page fault 不會回頭要這把鎖，所以不會自己鎖死。第一版另外配一塊暫存區、解鎖後才複製，理由寫成「不該在持鎖時做」，那是說得太重了，code review 後拿掉。

ioctl 的 CLEAR / FILL 也一樣：先在暫存區填好，送成功了才寫進 shadow frame，呼叫同一個 flush。所有傳輸都在 mutex 底下同步做完，沒有 timer、沒有 work queue：phase04 說「remove 時取消 pending work」，這一步的答案是根本不留 pending work。

10a.7lifecycleunbind 時檔案還開著

結構要活得比綁定久

Step 5-b 的按鍵 driver 用 devm_ 配記憶體，unbind 時自動釋放。這裡如果照做會出事：sysfs 的 unbind 不需要卸載 module（fops.owner 只擋 rmmod），所以有人開著 /dev/edge_oled 時照樣能 unbind；remove() 返回、devm_ 的記憶體被釋放之後，那個檔案再 write()，driver 就會去用已經釋放的結構。

open 和 remove 會不會撞在一起？misc_open() 是在持有 misc_mtx 的情況下呼叫我們的 open，而 misc_deregister() 也要拿這把鎖（依 upstream v5.15 的 drivers/char/misc.c；這台沒有 kernel 原始碼，沒對照 NVIDIA 的版本）：remove 一旦走過 misc_deregister()，就不會再有新的 open，進行中的 open 也一定已經拿到 reference。remove 順手送 Display OFF：螢幕黑了，就代表沒有 driver 在管它；這個指令失敗（OLED 已經拔掉）只記一行 warning，不影響 remove。probe 的最後一步 misc_register() 失敗時也一樣先送 Display OFF 再釋放（code review 補上；只有接第二片 SSD1306、名稱撞到時才會發生，沒有實測）。

模擬（不是實機）：在瀏覽器裡按按鈕，看引用計數和每個操作的結果

        

      

      
試試看：insmod → open → unbind → write，會看到 -ENODEV；這時再 bind，舊的那個檔案仍然是 -ENODEV，因為它指著舊的結構，新的綁定配了一個新的。要先 close 再重新 open。模擬裡「檔案開著時 rmmod 會被拒絕」是依 fops.owner 的規則推論，這次沒有實測。

    

  


  

    
10a.8共存oled_probe

    

      
driver 在的時候，userspace 工具要讓路

      
Step 9 的 code review 指出：oled_probe 用 I2C_RDWR，位址寫在每個訊息裡，從不「佔用」位址，所以 driver 綁定 0x3C 之後它照樣寫得進去，會在 driver 底下重新 init、換掉畫面，而 driver 的 shadow frame 毫不知情。Step 7 的 i2cget 會被 kernel 擋下（EBUSY），是因為它走的 I2C_SLAVE 會檢查位址有沒有 driver；I2C_RDWR 不做這個檢查。所以這次由工具自己檢查：

      
      
      
測試不需要真的載入 driver：環境變數 OLED_PROBE_SYSFS 換掉 /sys，在暫存目錄做一個假的 bus/i2c/devices/250-003c/driver 連結。驗收時則是真的：1-003c is bound to driver edge_oled (Device or resource busy): use its interface, or --force（10a.10 的 ⑥）。--force 在實機上沒有測：它會照樣寫，而如果寫的是 off，driver 不會知道螢幕被關了。

Step 10-b 處理文字：一套最小的 bitmap 字型、draw_char / draw_string、換行與超出範圍。這一步的 shadow frame 就是它要畫上去的地方；10a.5 那個「之間斷電」的盲點也在 10-b 先處理，因為 10-c 會讓螢幕長時間顯示。

      
1. 為什麼 write() 先 memdup_user()，而不是在鎖裡直接 copy_from_user() 進 shadow frame？
複製可能失敗一半（壞指標），直接寫進 shadow frame 就會留下半張畫面。而且就算複製成功，送到面板也可能失敗；shadow frame 要等全部送成功才更新，所以一定需要一個暫存區。（持有 mutex 時 copy_from_user() 睡一下本身是允許的，那不是理由。）

      
2. 開著 /dev/edge_oled 時 unbind，再 bind，用舊的 fd 寫入會怎樣？
還是 -ENODEV。舊的 fd 指著舊的結構，它的 client 已經是 NULL；bind 時 probe 配了一個新的結構。要關掉重新 open 才會用到新的。

      
3. probe 送 11 個訊息，之後每次 write 只送 9 個。少的是哪兩個？什麼時候 write 又會送 11 個？
少了 init 序列與最後的 Display ON。上一次 flush 有任何一個訊息失敗（initialized 變成 false）時，下一次 flush 會再送 init，畫面送完再送 Display ON。

      
4. driver 綁定時 i2cget 會被 kernel 擋下，oled_probe 卻不會。差在哪？
i2cget 先用 ioctl(I2C_SLAVE) 設定位址，i2c-dev 在這一步檢查位址有沒有 driver，有就回 EBUSY。oled_probe 用 I2C_RDWR，位址寫在每個訊息裡，沒有這個檢查，所以只能由工具自己看 sysfs。
