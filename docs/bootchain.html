UEFI 之前：上電後最早跑的那幾層韌體

下一章的 UEFI 是「最先讓我們看得到東西的一層」，但它不是第一個跑的程式。按下電源到 UEFI 開始之間，還有 BootROM、MB1、MB2 和一批跑在別的處理器上的韌體。這些在執行中的 Linux 裡幾乎看不到，所以這一章分清楚三件事：哪些是 NVIDIA 文件的說法、哪些能從更新包的檔案名稱間接看到、哪些在 kernel 的開機訊息裡有直接的痕跡。

kernel 5.15.148-tegra · L4T R36.4.7（nvidia-l4t-bootloader 36.4.7-20250918154033）· 新增 docs/bootchain.html；修改 docs/{index.html, step03.html, uefi.html}、CLAUDE.md。不新增 code，所有指令只讀不寫、不需要 root

板子上的韌體（晶片內的 ROM、flash 裡的各層韌體） kernel 從 Linux 看得到的證據
BC.1起點為什麼有好幾層

UEFI 要有地方跑，才有辦法讓你看到它

UEFI 是一支幾十 MB 的程式，要用到 DRAM、要讀 NVMe、要有時脈和電源。可是剛上電時，DRAM 還沒初始化、時脈是預設值、除了 SoC 內建的少量 SRAM 以外沒有可用的記憶體。所以必須有更小、更簡單的程式先把這些硬體準備好，再把下一層載進來。每一層只做自己那一步，載入下一層，這就是一條開機鏈。

第二個原因是安全：NVIDIA 的文件說，晶片裡有一個叫 PSCROM 的 ROM，持有金鑰，替 BootROM 驗證、解密後面載入的階段，並稽核下一階段，讓信任從晶片內不能改的 ROM 開始往後接（這章不展開 Secure Boot，只在這裡先交代為什麼要分層）。

互動雙方：載入的一方是前一層，被載入的一方是後一層，載入來源是 SoC 外的 QSPI flash（板子上的一顆小容量 flash，放所有早期韌體）。每一層跑完就把控制權交給下一層。這一章不做：不讀、不寫、不更新 flash，不講 Secure Boot 與簽章，不解開韌體映像。

先講好證據的等級：這一章大部分內容（誰載入誰、每層做什麼）來自 NVIDIA 的文件和我的背景知識，在這台板子上沒有逐項驗證。能在板子上確認的只有兩類：更新包檔案裡出現的名稱、kernel 開機訊息裡出現的字串。每一節都會標明是哪一種。

BootROM / PSCROM
BootROM 燒在 SoC 晶片裡、出廠後不能修改，上電後第一個執行；依 NVIDIA 文件，它在 BPMP（下面會講）離開 reset 時開始跑，初始化開機媒體，載入 BR-BCT、PSCBL1、MB1 與 MB1-BCT 後就停下。PSCROM 是另一個固定在晶片裡的 ROM，負責驗證與解密。
QSPI flash
板上一顆小容量、斷電後內容還在的 flash 晶片。SPI 是一種簡單的序列匯流排，Q（Quad）是一次用 4 條資料線傳輸；Tegra 的 QSPI 控制器支援單線、雙線與四線（NVIDIA 文件）。依文件，cold boot 時 BPMP 的開機程式和下一階段 UEFI 都放在它裡面。注意它不是 NVMe，rootfs 不在這裡。它的容量 NVIDIA 的文件沒有明寫，這章沒有確認（有第三方文章寫 16 MB，我沒找到官方出處，所以不採用）。
MB1 / MB2
NVIDIA 的第一、第二層 bootloader（Microboot 1、2）。依文件，MB1 跑在 BPMP 上，由 BootROM 載入到晶片內的 SRAM，負責平台設定、SDRAM（DRAM）初始化、載入韌體與載入 MB2；MB2 跑在 CPU 複合體（CCPLEX）上，另有一個跑在 BPMP 上、負責偵測裝置型號的 MB2 Applet。UEFI 在文件裡稱為 CPUBL（給 CPU 的 bootloader）。誰載入 UEFI，我查到的文件摘錄沒寫，這章不下結論。
BCT
Boot Configuration Table，給早期韌體用的設定資料。更新包的字串裡有 MB1_BCT。
BPMP
Boot and Power Management Processor，SoC 裡一顆獨立的小處理器，跑自己的韌體（BPMP-FW），管時脈、電源與 reset。
TF-A / BL31
Arm Trusted Firmware 的常駐部分，跑在比 kernel 更高的特權級（EL3），提供 PSCI（開關 CPU 核心的標準介面）等服務。這是我的背景知識；這次查的 NVIDIA Boot Flow 頁面沒有提到 TF-A 和 OP-TEE。
OP-TEE
Trusted Execution Environment 的作業系統，跑在 secure world，更新包裡叫 tos（trusted OS）。
capsule（.Cap）
UEFI 規格定義的韌體更新包格式。nvidia-l4t-bootloader 套件把整組早期韌體包成 .Cap 放在 /opt/ota_package。
BC.2全景BootROM → UEFI

五層，和它們在 Linux 裡留下的痕跡

左邊是開機的順序（依 NVIDIA 文件），右邊是這台板子上能找到的證據。右邊的方框如果是虛線，代表這一層在執行中的 Linux 裡找不到任何東西。每個方框都可以點，跳到講那一站的小節。

BC.3在哪裡flash 與 slot

早期韌體在 QSPI flash，從 Linux 讀不到它

rootfs 在 NVMe，但前面那五層不在。板子上的設定檔記得它們放在哪：

cat /etc/nv_boot_control.conf
ls /dev/mtd*
cat /proc/mtd
nvbootctrl dump-slots-info 2>/dev/null

  2. 2TEGRA_CHIPID 0x23 是 T234，也就是 Orin 這一代的 SoC。
  3. 3TEGRA_OTA_BOOT_DEVICE /dev/mtdblock0：設定檔把更新的目標寫成一個 MTD（flash）區塊裝置，和 NVMe 無關；它指的是放早期韌體的 QSPI flash。
  4. 4可是現在這個 kernel 沒有任何 /dev/mtd*，/proc/mtd 也只有標題。意思是：從這個執行中的 Linux，沒辦法直接讀那顆 flash。這章沒有追究為什麼設定檔寫了這個節點、系統裡卻沒有。
  5. 5bootloader 有 A、B 兩組 slot，目前用 B，兩組狀態都是 normal。A/B 是為了更新韌體失敗時能退回舊的一組；這章不展開，Step 規劃裡有需要時再回頭看。Current version: 0.0.13 是什麼的版本，這章沒有查。

nvbootctrl 不加 2>/dev/null 時，非 root 會在 stderr 印好幾行 open fail errno = 13：它想開的某些裝置要 root，但上面這些資訊不需要。

跑出來和這裡不一樣時：SD 卡開機的板子 TEGRA_BOOT_STORAGE 會是 mmcblk0；沒有 nvbootctrl 的話它在 nvidia-l4t-tools 套件裡（這台已裝）；slot 目前是 A 還是 B 取決於你的板子更新過幾次。

名稱用途（依名稱與 NVIDIA 文件，沒有解開映像驗證）

BC.5痕跡kernel 開機訊息

kernel 開機的前幾秒，已經看得到這些韌體留下的東西

kernel 的開機訊息保存在 journal 裡。早期韌體做完的事，kernel 啟動後會碰到它們，並且印出一行：

journalctl -k -b -o cat | grep -E 'efi: EFI|psci: PSCIv|SMCCC: SOC_ID|optee: revision|tegra-bpmp bpmp: firmware|Unknown kernel command line'
od -An -tx1 /proc/device-tree/bpmp/phandle
od -An -tx1 /proc/device-tree/bus@0/i2c@c250000/clocks | head -1
$ journalctl -k -b -o cat | grep -E 'efi: EFI|psci: PSCIv|SMCCC: SOC_ID|optee: revision|tegra-bpmp bpmp: firmware|Unknown kernel command line'
efi: EFI v2.70 by EDK II «1»
psci: PSCIv1.1 detected in firmware. «2»
Unknown kernel command line parameters "nv-auto-config bl_prof_dataptr=2031616@0x271E10000 bl_prof_ro_ptr=65536@0x271E00000", will be passed to user space «3»
SMCCC: SOC_ID: ID = jep106:036b:0234 Revision = 0x00000401 «4»
tegra-bpmp bpmp: firmware: e941463f35523d12ee54-da583751bbf «5»
optee: revision 4.2 (d78bc5fa) «6»
$ od -An -tx1 /proc/device-tree/bpmp/phandle
 00 00 00 03 «7»
$ od -An -tx1 /proc/device-tree/bus@0/i2c@c250000/clocks | head -1
 00 00 00 03 00 00 00 36 00 00 00 03 00 00 00 66
  1. 1kernel 認得 UEFI：版本 2.70、實作是 EDK II。這是上一章 UEFI.6 的 linux,uefi-* 屬性之外，另一個「kernel 看到了 UEFI」的證據。
  2. 2PSCI 是 kernel 叫韌體開關 CPU 核心的標準介面。detected in firmware 表示這個服務是韌體提供的，不是 kernel 自己做的。TF-A 的 BL31 通常提供它（我的背景知識）；更新包字串裡確實有 BL31: %s。實作者是 UEFI 還是 BL31，kernel 這行沒說。
  3. 3上一章 UEFI.6 提過的 bl_prof_*：kernel 不認得它們，所以放行給 userspace。名稱裡 bl 大概是 bootloader、prof 是 profile，是早期各層記錄開機時間用的資料位置（從名稱判斷，沒查）。
  4. 4SMCCC 是 kernel 呼叫更高特權級韌體的方式，這行讀回晶片 ID；0234 和前面的 TEGRA_CHIPID 0x23（T234）對得上。
  5. 5tegra-bpmp 是 kernel 和 BPMP 溝通的 driver，它讀到 BPMP 韌體的版本字串。表示 BPMP 在 kernel 開始前就已經載入並執行了。
  6. 6OP-TEE 版本 4.2，kernel 的 optee driver 找到了 secure world 的 OS，表示 tos 已經在跑。
  7. 7這一組和本專案直接有關：DT.6 提過的 i2c@c250000（header pin 3/5 的 I2C controller），它的 clocks 屬性第一個 cell 是 0x03，正是 bpmp 節點的 phandle。也就是說，Step 6、7、8 讀 INA219 用的 I2C 時脈，是 kernel 透過 BPMP 韌體要來的。

跑出來和這裡不一樣時：版本字串（EDK II 的版本、OP-TEE 的 4.2、BPMP 的字串）會隨你的 L4T 版本而不同；journalctl -k 沒有權限時加 sudo，或把使用者加進 adm 群組（這台的使用者已在）。如果你的 journal 沒有保留開機訊息，改用 sudo dmesg | grep …。

BC.6常見錯誤容易搞混

容易搞混的地方

標「沒實測」的項目，是只有文件或字串指向、沒有真的做過。這章同樣沒有故意弄壞任何東西。

以為 apt 更新就換了韌體

症狀
dpkg -l 顯示 nvidia-l4t-bootloader 新版了，開機訊息裡的 EDK II 版本卻沒變。
後果
以為更新失敗，或以為已經用上新韌體。
正解
套件只是把更新包（.Cap）放進檔案系統；寫進 flash 要另外一個步驟，依文件由 UEFI 在重開機時套用（沒實測）。用 nvbootctrl 的 Capsule update status 看。

在 Linux 裡找 BootROM 或 MB1 的檔案

症狀
find / -name '*mb1*' 找不到可以執行的映像。
後果
以為系統少了東西。
正解
BootROM 在晶片裡；MB1、MB2 在 QSPI flash，Linux 看不到那顆 flash（BC.3）。只有更新包 .Cap 裡有副本。

以為 ESP 上的 BOOTAA64.efi 就是 UEFI 韌體

症狀
想「更新 UEFI」就換掉 ESP 的 BOOTAA64.efi。
後果
換的是 L4TLauncher，UEFI 本體（cpu-bootloader）沒變。
正解
UEFI 在 flash，ESP 的是它載入的 L4TLauncher（UEFI.4）。兩者同屬 nvidia-l4t-bootloader 這個套件（BC.4 的 SHA-256 相同）。

把 PSCI 的「in firmware」當成 UEFI

症狀
讀到 psci: PSCIv1.1 detected in firmware，以為 UEFI 在提供電源管理。
後果
要查 CPU 開關問題時去找錯一層。
正解
PSCI 通常由 TF-A 的 BL31 提供（背景知識，沒實測），UEFI 在 kernel 啟動後就不再執行（UEFI.1）。

板子停在更早的階段還想用 Linux 工具

症狀
上電後沒有畫面、ssh 連不上，efibootmgr 當然也沒得跑。
後果
不知道卡在哪一層。
正解
接序列 console（這台 kernel 命令列有 console=ttyTCU0,115200）看早期韌體的訊息，必要時進 recovery 模式重燒（沒實測）。

以為 Force Recovery 是 Linux 在管

症狀
DT 裡有一個 key-force-recovery 節點（DT.6），以為按它由 kernel 處理。
後果
以為在 Linux 裡能「按」出 recovery 模式。
正解
依文件，進 recovery 是上電時由 BootROM 檢查那根腳，那時 Linux 還不存在；DT 的那個節點只是讓 kernel 能把它當成一顆按鍵來讀（沒實測）。
BC.7收尾→ UEFI

這一章讀懂了什麼

  • UEFI 前面還有 BootROM（與 PSCROM）→ MB1 → MB2，加上 BPMP-FW、TF-A、OP-TEE 等其他韌體（依 NVIDIA 文件與背景知識）；cold boot 時 BPMP 的開機程式和 UEFI 放在 QSPI flash。
  • 早期韌體不在 NVMe、也讀不到；能看到的是 nvidia-l4t-bootloader 的更新包裡的名稱清單（BC.4）。
  • kernel 開機訊息裡有 EFI、PSCI、BPMP、OP-TEE 的痕跡，證明這些韌體在 kernel 之前已經在跑（BC.5）。
  • 本專案相關的一例：I2C controller 的時脈是 kernel 透過 BPMP 韌體取得的。
  • 映像怎麼解開、簽章與 Secure Boot、MB1 與 MB2 各自載入什麼的確切分工：這章沒有查證。
  • 怎麼更新與還原這些韌體（capsule、A/B slot 的切換）：不在這章範圍。

本章引用的 NVIDIA 文件：Jetson AGX Orin, Orin NX, and Orin Nano Boot Flow（BootROM、PSCROM、MB1、MB2、UEFI 的分工）、Jetson Orin Series（QSPI 的用途與控制器寬度）。文件版本和這台的 L4T R36.4.7 不完全相同，細節以你的版本為準。

下一章 UEFI 與開機從第 5 層開始：UEFI 怎麼找到 L4TLauncher、extlinux.conf 怎麼決定載入什麼，最後把 kernel 交出去。

1. 為什麼不讓 BootROM 直接載入 UEFI？

BootROM 在晶片裡、不能修改，只能做最簡單的事，也只有少量 SRAM 可用；DRAM 要靠後面的層初始化。UEFI 很大、要用 DRAM，必須等前面的層把硬體準備好。此外 BootROM 不能改也代表不能修 bug，讓它越簡單越好。

2. 你想確認 /boot/efi/EFI/BOOT/BOOTAA64.efi 是不是 nvidia-l4t-bootloader 套件裡的那一份，怎麼做？

對兩個檔案跑 sha256sum（BC.4）：/opt/ota_package/t23x/BOOTAA64.efi 和 ESP 裡的那個。雜湊相同就是同一份。

3. kernel 開機訊息有一行 optee: revision 4.2，這代表什麼？

kernel 的 optee driver 找到了 secure world 的 OP-TEE，版本 4.2。OP-TEE 是更新包裡 tos 分區的內容，在 kernel 啟動前就已經由早期韌體載入並執行。

4. /proc/mtd 是空的，但 /etc/nv_boot_control.conf 寫 TEGRA_OTA_BOOT_DEVICE /dev/mtdblock0。這代表早期韌體不在 flash 嗎？

不能這樣推論。設定檔表示更新的目標是一個 MTD 裝置，更新包裡也有早期韌體的名稱；而這個 kernel 沒有暴露 MTD 裝置，所以「從這個 Linux 讀不到」。這章沒有查它為什麼沒有，只能說兩邊的資訊對不上，需要再查。
