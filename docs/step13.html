13.1起點為什麼

application 不該知道 register 長什麼樣

到 12-b 為止，Jetson 讀 ADC 的方式是這樣：

i2ctransfer -y 1 w1@0x42 0x10 r2@0x42
0x11 0x08

拿到兩個 byte 之後，呼叫的人還得知道：0x10 是 ADC_LOW、要一次讀 2 byte（分開讀可能來自兩次轉換）、little-endian、HIGH 只有低 4 bit 有意義，所以這是 0x811 = 2065。每個要用 ADC 的程式都得重寫一次這些規則，而且任何一個寫錯，都是「讀到奇怪的值」這種很難追的錯。

Linux 的做法是把這些知識集中在一個 driver 裡，userspace 只看到一個意思明確的介面。這一步的 driver 叫 edge_ctrl，它把 register map v1.1 包成八個 sysfs 檔。

互動雙方：Jetson 的 i2c-1（c240000.i2c，100 kHz）是 controller，Blue Pill 的 I2C1（0x42）是 target，接線和 firmware 都和 12-b 一樣。新的一層在 Jetson 的 kernel：Device Tree 描述「i2c-1 上 0x42 有一顆 edge,edge-ctrl」，edge_ctrl.ko 認領它。這一步不做：heartbeat（Step 14）、poll() 等事件（Step 19），也不改 firmware。

I2C client
kernel 裡代表「某條 I2C bus 上某個位址的一顆晶片」的物件，名稱像 1-0042（bus 1、位址 0x42）。Device Tree 的節點在開機時就變成 client，driver 載入後才綁上去。
sysfs 屬性
/sys 底下的一個檔案，讀它時 kernel 呼叫 driver 的 show()，寫它時呼叫 store()。一個檔放一個值、文字格式。
dev_groups
struct device_driver 的欄位：driver core 在綁定成功後替 driver 建立這組屬性檔，解除綁定時刪掉。driver 自己不用呼叫建立、刪除。
i2c_transfer()
I2C core 的函式，把幾個 struct i2c_msg 當成一筆 transaction 送出，中間用 repeated START 接起來，期間 adapter 是鎖住的。
repeated START
不送 STOP、直接再送一次 START：寫完 pointer 後馬上轉成讀，bus 不會在中間被別人拿走。
errno
系統呼叫失敗時告訴 userspace 原因的數字，例如 EREMOTEIO（對方沒回 ACK，印成 Remote I/O error）、EINVAL（參數不合法）。

13.3綁定DT + probe

開機時就有 client，insmod 時才有 driver

和 Step 7 的 INA219、Step 10-a 的 OLED 一樣，先在 overlay 裡描述這顆晶片：

gen2_i2c 是 NVIDIA 基底 Device Tree 給 /bus@0/i2c@c240000 的 label，也就是 Linux 叫 i2c-1 的那條 bus，header pin 27 / 28。OLED 的 oled@3c 也在這條 bus 上，但另外放一個 fragment，兩者互不影響。

compatible 是 edge,edge-ctrl，不是規劃裡寫的 edge,controller。原因是 Step 7 踩過的坑：I2C core 會用 compatible 去掉廠商前綴當 client 名稱（這裡是 edge-ctrl），DT 比對不到時還會拿這個名稱去比每個 driver 的 i2c_device_id 表。controller 這種通用字比較有機會撞到別人的 driver，有測試檢查這台 kernel 的 modules.alias 裡沒有人認領 i2c:edge-ctrl。

重開機後節點生效，client 1-0042 出現、還沒有 driver。insmod 時 compatible 相符，I2C core 呼叫 probe：

probe 的工作是「確認這真的是我認得的東西」。第一步是問 adapter 能不能做一般的 I2C transfer（I2C_FUNC_I2C）：read_reg() 用的是「寫 pointer + repeated START + 讀」，只支援 SMBus 的 adapter 做不到。這台的 i2c-1 可以（i2cdetect -F 1 列 I2C yes），這一行是 code review 補上的標準檢查。接著，一個 ACK 只證明 0x42 有人回應，所以要看 DEVICE_ID 是不是 0xED，再照 12-a 寫下的版本規則看 PROTOCOL_VERSION：major 要是 1，minor 至少是 1（這個 driver 要用 ADC 和按鍵，map 1.0 沒有）。四個 register 用一筆讀取拿到，一次 transaction 就完成檢查。

STATUS 只讀出來印在 dmesg，不清除。它的 RESET bit 是給 application 判斷「板子重開過」用的，driver 一載入就把它清掉，這個資訊就沒了。

屬性檔不是 probe 建立的：

用 .dev_groups 而不是在 probe 裡呼叫 sysfs_create_group()，好處是生命週期不用自己管：unbind、rmmod 時檔案一定會跟著消失，驗收腳本也檢查了這件事。

13.4介面為什麼是 sysfs

八個檔，一個檔一個值

phase05 讓這一步在 sysfs 和 character device 之間選一個，但要寫清楚理由。這一步選 sysfs：

考量結論
值的性質全部是「現在是多少」的狀態（版本、ADC、按鍵、LED、STATUS），沒有串流、沒有事件。sysfs 正是給這種值用的。
使用方式cat / echo 就能用，shell 腳本和任何語言都不用 ioctl 定義。
為什麼不是 hwmonADC 讀的是 A0 上任意的電壓（0–4095 的原始值），按鍵、LED、STATUS 也都不是 hwmon 的類別（Step 8 的 INA219 才是）。
之後的 poll()Step 19 要讓 userspace 等 STM32 的事件，需要 wait queue 和「一次事件算一個還是一個 bit」這類語意。phase08 規劃的是 /dev/edge_ctrl，到時再加 character device，不在這一步預先做。

檔案都在 client 的目錄 /sys/bus/i2c/devices/1-0042/ 底下：

檔案 · 權限內容 · 讀的 register
device_id · 04440xed · 0x00
firmware_version · 04440.3 · 0x01–0x02，一筆讀取
protocol_version · 04441.1 · 0x03
adc · 04440–4095 · 0x10–0x11，一筆讀取 2 byte
button · 04441 按著、0 放開 · 0x12 bit 0
button_presses · 0444開機以來的按下次數，255 之後回 0 · 0x13
led · 06440 / 1；寫入只收 0 和 1 · 0x20
status · 06440x80 這種兩位 hex；寫入照 write-1-to-clear 轉送 · 0x30

可寫的兩個檔是 0644，不是 0666：kernel 不允許 sysfs 屬性給 others 寫（編譯時就會擋），所以寫入要 root。WATCHDOG_STATUS（0x31）沒有開放，它到 Phase 6 才有意思。

13.5傳輸read_reg

pointer 和讀取放在同一筆 transaction

12-a 的 register map 規定：pointer 只由寫入設定，auto-increment 只在同一筆 transaction 裡有效。所以讀取一定要「寫 pointer」和「讀」連在一起。用一次 i2c_transfer() 送兩個 message，有兩個效果：

  • 中間沒有人插得進來。adapter 在整筆 transaction 期間是鎖住的。同一條 bus 上還有 OLED 的 driver、userspace 的 i2ctransfer，如果分成「先寫 pointer、再讀」兩次呼叫，別人可能在中間把 firmware 的 pointer 改掉。
  • 一筆讀取的 byte 來自同一個快照。12-b 的 firmware 在讀取開始時拍快照，所以 adc 一次讀 2 byte，LOW 和 HIGH 一定是同一次轉換；firmware_version 也一次讀 0x01–0x02。

i2c_transfer() 回傳成功送出的 message 數。小於 2 卻不是負數，代表只完成了一部分，這不算成功，所以回 -EIO，不讓呼叫的人拿著沒填好的 buffer 繼續用。

寫入只有一個 message：i2c_master_send() 送 reg 和 value。firmware 的 F103 在看到 byte 之前硬體就回了 ACK（Step 11），所以 bus 上不會失敗的寫入，值仍然可能被 firmware 丟掉。這就是下一節 led_store() 要自己先擋的原因。

13.6屬性show / store

讀：直接問板子。寫：先擋，再送

每個 show() 的形狀都一樣：讀 register，失敗就回傳負的 errno，成功就用 sysfs_emit() 寫文字。沒有快取：driver 不記得上次的值，每次讀檔都真的走一趟 bus。代價是每次讀都要一筆 transaction（adc 是位址、pointer、位址、2 個資料共 5 個 byte，100 kHz 下算起來約 0.45 ms，沒有量），換來的是讀到的永遠是板子上現在的值，有人用 i2ctransfer -f 改了 LED，下一次 cat led 就看得到。

為什麼 driver 要自己檢查？firmware 收到 LED_CONTROL = 2 時，bus 上照樣 ACK，只是把值丟掉、在 STATUS 設 BAD_VALUE。如果 driver 直接轉送，echo 2 > led 會「成功」，寫的人完全不知道值沒生效。在 driver 先擋，錯誤就以 EINVAL 回到 echo，這是 userspace 期待的行為。

擋的範圍要和 firmware 完全一樣：擋多了，合法的值送不出去；擋少了，又回到「靜靜被丟掉」。這個規則放在共用 header 的 edge_ctrl_led_ok()，13.7 的測試逐值比對兩邊。

STATUS 的寫入不用翻譯：12-a 定的規則本身就適合 echo。寫 0x01 清 RO_WRITE、寫 0xff 全清、寫 0 什麼都不清。driver 只擋超過一個 byte 的值。

kstrtouint(buf, 0, &v) 的 base 0 代表「看前綴決定進位」：0x10 是十六進位、010 是八進位、其他是十進位。它也接受結尾一個換行，所以 echo 1（送出 "1\n"）可以用。下面的模擬器可以試不同的輸入：

模擬：driver 的 store() 與 firmware 的 LED / STATUS（JavaScript，不是板子）
echo>
LED_CONTROL 0STATUS 0x80

      

      
模擬器照 kstrtouint() 的規則解析，前面多一個 +、前後有空白、"1\n\n" 這類細節以 kernel 原始碼為準；實機上試過的值只有 13.10 列出的那些。

13.8錯誤不是晶片的錯

    

      
bus 出錯時，driver 什麼都不記

      
Step 11 踩過一次：麵包板上 PB6 誤接到 GND，Tegra 的 controller 約每 100 ms 印一行 I2C transfer timed out，同一條 bus 上的 ina3221 也讀不到；線一放開，bus 自己恢復。phase05 把這件事交給這一步：整條 bus 都 timeout，不是這顆晶片的錯。

      
這一步的錯誤處理因此刻意很少：

      
    
        
  • 每次存取失敗，errno 原樣回給讀寫的人（read_reg() / write_reg() 的最後一行）。
    • 
        
  • driver 不記「這顆晶片壞了」的狀態，也不 unbind 自己。下一次存取直接重試，bus 好了就成功。
    • 
        
  • 每次失敗不印 log。tegra-i2c 自己會印；一個每秒讀一次的程式遇到斷線，driver 再印一行只會洗版。（probe 失敗例外：那只會發生一次，dev_err_probe() 會印出原因。）
    • 
      

      
實機上測的是比較溫和的情況：拔掉 ST-Link，Blue Pill 斷電，0x42 不再回 ACK：


PASS board gone: device_id fails (cat: /sys/bus/i2c/devices/1-0042/device_id: Remote I/O error)
PASS board gone: adc fails (cat: /sys/bus/i2c/devices/1-0042/adc: Remote I/O error)
    same bus, ina3221 0x40 manufacturer ID: 0x4954
PASS board back: device_id 0xed again, same binding (no unbind / bind)
PASS status 0x80 has RESET: the restart is visible

      
斷電的 Blue Pill 沒有把 bus 拉住：同一條 bus 上的 ina3221 照樣讀到 0x4954。插回之後不用 unbind / bind，device_id 就讀回 0xed，而 status 的 RESET bit 告訴 application 板子重開過，LED 等狀態已經回到預設值。這正是 probe 不清 STATUS 的理由。

      
沒有實測：SCL / SDA 被拉到 GND、整條 bus timeout 的情況（errno 會是 timeout 而不是 EREMOTEIO）。它走的是同一段程式碼，只由原始碼測試守住「錯誤路徑不留狀態、不印 log」；要重現得把線接到 GND，這一步沒做。probe 遇到 DEVICE_ID 不對、map 不相容回 -ENODEV 這條路，也只有向量與原始碼測試（板上沒有別的 firmware 版本）。

13.10驗收實機

    

      
實測：先沒有節點，再有節點

13.11常見錯誤

    

      
踩過與差點踩的坑

      

        
測試寫空字串
症狀
寫 "" 到 led，期待 EINVAL，卻沒有錯誤。
後果
以為 driver 漏擋，其實這個 case 根本沒呼叫到 driver。
正解
測 "\n"：那才是 echo > led 送出的東西。

        
把錯誤的值直接轉送
症狀
echo 2 > led 回傳成功，LED 卻沒變。
後果
firmware 照樣 ACK、只在 STATUS 記一筆，寫的人不知道失敗。
正解
driver 先檢查，範圍和 firmware 完全相同，有向量逐值比對。

        
ADC 分兩次讀
症狀
偶爾讀到差 256 的值。
後果
LOW 和 HIGH 來自兩次轉換（12-b 的錯位）。
正解
一次 i2c_transfer() 讀 2 byte，有原始碼測試守著。

        
綁定後還用 i2cget
症狀
Could not set address to 0x42: Device or resource busy。
後果
上一步的驗收腳本在 driver 載入時跑不了。
正解
比對用 i2ctransfer -f；verify_stm32_i2c.sh 在 module 卸載後跑。

        
通用的 compatible
症狀
規劃寫 edge,controller，client 名稱就是 controller。
後果
名稱拿去比所有 driver 的 i2c_device_id，有機會被別人認領（Step 7）。
正解
用 edge,edge-ctrl，測試查 modules.alias。

        
上一步的範圍測試
症狀
建好 kernel/edge_ctrl/，12-b 的測試就紅了。
後果
它斷言「這個目錄不存在」（12-b 不准寫 driver）。
正解
拿掉那一條，firmware 的範圍檢查保留。

      

    

  


  

    
13.12收尾下一步

    

      
這一步做到了什麼

      
    
        
  • edge_ctrl.ko：Device Tree 綁定 1-0042，probe 檢查 DEVICE_ID 與 map 版本，八個 sysfs 屬性（識別、版本、ADC、按鍵、計數、LED、STATUS）。application 不再碰 /dev/i2c-1。
    • 
        
  • phase05 的驗收條件成立：Jetson Linux driver → I2C → STM32 firmware → GPIO / ADC / status 整條路可以工作，driver 的值和 raw I2C 一致。驗收 0 failure（第一輪 1 個失敗是測試寫錯，修測試後重跑）。
    • 
        
  • Step 11 帶過來的「整條 bus timeout 不是晶片的錯」：錯誤只回 errno、不留狀態；Blue Pill 斷電後不用重新綁定就恢復。
    • 
        
  • 測試：6 組向量（driver header 對 firmware 的 i2c_target.c）、22 個 static、9 個 device 測試。規模：非空白新增 999 行（含 code review 的修正），超過 800 的上限，而且動工前沒有寫下估計；其中測試與驗收腳本佔 711 行。
    • 
        
  • 沒有實測：整條 bus timeout（SCL 拉到 GND）；probe 拒絕不相容 firmware 的路徑（只有向量）。
    • 
      

      
Step 14 進到 Phase 6：讓 STM32 從被動的周邊變成 Jetson 的 supervisor。Jetson 定期寫一個 HEARTBEAT register，STM32 用 timer 判斷多久沒收到就進入 fault 狀態。這會是 register map 第一個「寫入有副作用」的 register，12-b 的 code review 已經記下：firmware 的 write_reg() 目前把其他可寫位址都當 STATUS 處理，加 HEARTBEAT 前要先改。

      
1. 為什麼 read_reg() 用一次 i2c_transfer() 送兩個 message，而不是先 i2c_master_send() 寫 pointer、再 i2c_master_recv() 讀？
一次 transfer 期間 adapter 是鎖住的，中間用 repeated START 接起來，別的 bus 使用者（OLED driver、userspace）插不進來改 firmware 的 pointer；分兩次呼叫，中間可能被插隊，讀到別的 register。

      
2. firmware 對 LED_CONTROL = 2 會 ACK 並丟掉。driver 為什麼不乾脆轉送，讓 firmware 自己處理？
那樣 echo 2 > led 會回傳成功，錯誤只留在 STATUS，寫的人不會知道。在 driver 先擋，錯誤以 EINVAL 回到 userspace。前提是擋的範圍和 firmware 完全相同，所以有向量逐值比對。

      
3. probe 為什麼不把 STATUS 清掉？
STATUS 的 RESET bit 是 application 判斷「板子重開過」的唯一管道。driver 一載入就清，這個資訊就沒了；斷電重插之後讀到 0x80，正是靠這一點。

      
4. Blue Pill 斷電時 cat adc 失敗。driver 要不要記下「裝置壞了」，之後的讀取直接回錯？
不要。失敗可能是整條 bus 的問題（像 Step 11 的短路），也可能只是暫時斷電；記下狀態反而讓板子回來後還是讀不到，得手動重新綁定。每次存取直接試、失敗就回 errno 最簡單，也最正確。

      
5. 測試 edge_ctrl_regs.h 時，為什麼要把 firmware 的 i2c_target.c 一起編進來？
只拿 driver 的 header 跟自己比永遠會過。用 firmware 真正的 state machine 回答 driver 的 transaction，期望值才是「板子上會發生的事」，兩份 header 分歧時才會紅。
