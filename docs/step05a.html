按鍵事件不一定要寫 driver

Step 4 先在 userspace 點亮 LED（4-a），再寫 kernel driver（4-b）。按鍵也照這個順序：這一章不寫任何 kernel code，只用 kernel 本來就有的 GPIO character device，請它在按鍵的邊緣上產生事件。程式呼叫 read() 之後一樣會睡著、一樣不吃 CPU、一樣有 debounce。中斷、佇列、wait queue 都由 kernel 的 gpiolib-cdev 處理；下一章 5-b 再把這些在自己的 driver 裡親手寫一遍。

5a.1起點為什麼

同一顆按鍵，先不寫 driver

4-a 的 edge_gpio_blink 透過 /dev/gpiochip0 請求一條 line 當輸出。同一個介面也能請求輸入，而且可以要求 kernel 在電位變化時通知：請求時加上「偵測上升、下降邊緣」的旗標，kernel 就會替這條 line 登記中斷；中斷進來時，它把一筆事件放進這次請求自己的佇列。程式對請求拿到的 fd 呼叫 read()，沒有事件就睡著。

互動雙方：硬體端是按鍵和 GPIO controller（中斷來源）；kernel 裡處理中斷和佇列的是 gpiolib 的 character device 部分（gpiolib-cdev），不是我們寫的；userspace 是 edge_gpio_button，它透過 ioctl 請求 line，再對 line 的 fd 做 blocking read()。這一步不做：kernel driver、Device Tree 的修改、poll()（Phase 8）。

gpiolib-cdev
kernel 裡實作 /dev/gpiochipN 的那部分 gpiolib。4-a 用它設定輸出值，這一章用它的邊緣事件功能。
line request
用 GPIO_V2_GET_LINE_IOCTL 向 chip 請求一或多條 line，成功後拿到一個新的 fd（req.fd）。之後的讀寫、設定都對這個 fd 做；關掉它就釋放 line。
edge event
請求時加 GPIO_V2_LINE_FLAG_EDGE_RISING / _FALLING，每次邊緣都會在 req.fd 上產生一筆 struct gpio_v2_line_event（時間戳、上升或下降、序號）。
rising / falling
uAPI header 的定義是「inactive → active」/「active → inactive」，看的是邏輯值。加了 ACTIVE_LOW 之後，按下（實體低電位）就是 rising。
debounce 屬性
GPIO_V2_LINE_ATTR_ID_DEBOUNCE 加上 debounce_period_us，請 kernel 過濾短於這個時間的變化（kernel 5.10 起支援）。

5a.4請求ioctl

請求 line：輸入、低電位有效、雙邊緣、20 ms debounce

  • INPUT | ACTIVE_LOW：和 5-b 的 DT 寫 GPIO_ACTIVE_LOW 是同一件事。之後 kernel 回報的電位和邊緣都是邏輯值：按下 = 1 = rising。
  • EDGE_RISING | EDGE_FALLING：兩種邊緣都要，按下、放開各一筆。只要其中一個旗標，kernel 就會替這條 line 登記中斷。
  • 屬性：attrs[0].mask = 1 的意思是「這個屬性套用到這次請求的第 0 條 line」（bit 0），一次請求多條 line 時可以分別設定。debounce_period_us = 20000 和 5-b 的 EDGE_BUTTON_DEBOUNCE_MS 一樣，方便對照。
  • consumer：gpioinfo 會顯示這個名字，驗收腳本靠它確認 line 被誰持有。
  • 請求成功後就把 chip 的 fd 關掉：line 由 req.fd 持有，和 chip 的 fd 無關。
5a.5啟動假事件

沒人按，卻先收到一筆 released

第一版程式寫完，實機測試卻紅了：沒有人碰按鍵，程式一啟動就讀到 seq=1 released，正常結束。用一支只在 scratchpad 裡的實驗程式（不入庫）量了兩件事：請求後每 2 ms 讀一次實體電位，以及第一筆事件距離請求多久。

000000000011111111111  (raw, one digit per ~2 ms) «1»
event falling(released) seq=1 at request+20884 us «2»
  1. 1按鍵是放開的（真實電位是 1），但請求之後大約 20 ms 都讀到 0，之後才是 1。三次都一樣；不開 edge detection 也一樣。
  2. 2開了 edge detection 時，這次 0 → 1 被當成一個邊緣：實體上升 = 邏輯下降 = released，約在請求後 20.1～21.0 ms。不設 debounce 也一樣，所以不是 debounce 造成的。

這個現象還有一個規律：line 剛被釋放不久（不到約 0.3 秒）再請求時不會發生，所以連續重跑時看不到，隔一下就看得到。為什麼要 20 ms，我沒有查到原因，這裡只記實測事實。

這和 5-b driver 的 if (val == eb->last) return; 是同一個想法：只有狀態真的改變才算一次按下或放開。

印出的 seq 是程式自己的計數，只算印出來的 pressed / released。第一版直接印 kernel 的 seqno：kernel 把被丟掉的啟動假事件也算進去，第一筆就是 seq=2；更麻煩的是每略過一筆事件都會變成跳號，驗收腳本會誤判成遺失，真正的佇列溢位也分不出來（code review 指出）。現在 kernel 的 seqno 只拿來檢查有沒有缺口：每讀一筆（不管有沒有略過）就和上一筆比，缺了就在 stderr 印 lost。

50 ms 夠不夠？連續啟動 30 次（每次間隔 0.5 秒）：30 次都出現那筆假事件，0 次在 50 ms 之後才到，和量到的 20.1～21.0 ms 一致。另外，如果按壓剛好在這 50 ms 內開始，穩定後讀到的就是「按下」，程式把它當成初始狀態，第一筆印出的會是它的 released。驗收腳本等穩定之後才提示人按，所以不會碰到。

同一個現象也會讓 gpioget 讀錯：它請求 line 之後立刻讀，放開時也讀到 0。這台板子上實測（不需要 root）：

for i in 1 2 3 4; do sleep 1; gpioget gpiochip0 43; done
0
0
0
0

按鍵全程是放開的。把 sleep 1 拿掉、緊接著連跑，有機會讀到 1（line 剛被釋放）。5-b 的章原本教讀者用單次 gpioget 確認接線，這一步已經更正。

想自己看到「丟掉一筆」：先等一秒、再啟動程式，訊息印在 stderr。在 repo 根目錄執行（使用者要在 gpio 群組，edge_button.ko 不能載入）：

sleep 1; ./build/edge_gpio_button 1 & sleep 1; ps -o stat,wchan:20,cmd -p $!; kill $!; sleep 0.5
ignored 1 edge(s) while the line settled «1»
STAT WCHAN                CMD
S    do_wait_intr         ./build/edge_gpio_button 1 «2»
interrupted
[1]+  Exit 1                  ./build/edge_gpio_button 1
  1. 1那筆啟動假事件被丟掉了。如果前一秒內有別的程式剛用過 line 43，這行可能不會出現。
  2. 2程式睡著（S），睡在 kernel 的 do_wait_intr：gpiolib-cdev 的 wait queue。5-b 的 driver 版會顯示 edge_button_read。
5a.6read()事件迴圈

讀事件：一次一筆 gpio_v2_line_event

  • read() 要一次讀一整筆 gpio_v2_line_event（48 bytes）；也可以給更大的 buffer 一次讀好幾筆，這裡一次一筆，和 5-b 的程式一樣。
  • signal 的處理照 5-b code review 的教訓：handler 只設旗標、不設 SA_RESTART，每次 read() 前檢查旗標。已知限制：檢查旗標和進入 read() 之間有極小的空隙，signal 剛好落在中間時，要等到下一個事件才會醒。根治要用 ppoll() 搭配 signal mask，排進 Phase 8 的 Step 19（那一步本來就要寫 poll() client）；驗收腳本目前靠 timeout -k 兜底。
  • 輸出格式和 5-b 的 edge_button_wait 完全相同，兩支驗收腳本用同一套檢查（pressed / released 交替、seq 連號）。

時間戳有一個觀察：同一次執行中，毫秒的小數部分幾乎固定（例如 213.055104920、213.222101615，都是 x.10 ms），也就是落在 1 ms 的格點上。5-b 修正後在 IRQ 取時間，數字是隨機的；5-b 修正前在 work 取時間，落在 4 ms 的格點上（CONFIG_HZ=250）。我的推測是 Tegra 的 GPIO controller 支援硬體 debounce、以 1 ms 為單位計數，訊號穩定 20 ms 之後才發中斷，所以 5-a 的時間戳大約比按下晚 20 ms。這是推論，沒有查證（沒有讀 tegra186 GPIO driver 的原始碼，這台也沒有附）。

5a.7pad開機預設

不設 pad 也讀得到嗎？

5-b 的 overlay 有一組 pinctrl 狀態，但它只在 edge_button.ko probe 時才會套用。這一章沒有 driver，pad 就維持開機時的設定。4-a 的 LED 正是卡在這裡：開機時 pad 是 tristate，輸出到不了腳位。輸入的情況呢？驗收前重開機、不載入 driver，讀到的就是開機預設值：

    132 (soc_gpio21_ph0): pull=1 tristate=1 enable-input=1 open-drain=0 io-reset=0 rcv-sel=0 io-hv=0 schmitt=0 pull-down-strength=0 pull-up-strength=0 drive-type=0 gpio-mode=0 function=rsvd0 «1»
    no edge_button probe in this boot: this is the boot-default pad «2»
  1. 1enable-input=1：輸入有開，所以不需要任何 pad 設定就能讀。tristate=1 只關掉輸出，對輸入沒有影響。pull=1 是內部下拉（5-b 的 pinctrl 設的是上拉 pull=2）；外接的 330 Ω 上拉比它強很多，所以放開時還是 1。
  2. 2腳本用 dmesg 找這次開機有沒有 edge_button probe 過：pinctrl 狀態在 driver 卸載後不會還原，probe 過的話看到的就不是開機預設值了。

這個輸出來自下一節的驗收腳本（要 root 才能讀 debugfs 的 pinconf）。注意最後的 gpio-mode=0：同一次開機裡，line 43 被請求、釋放過之後它會變成 1（5a.9 的重跑就是），所以只有 pull、tristate、enable-input 三項算開機預設值，腳本的訊息後來也改成這樣。

5a.10常見錯誤

踩過的坑

以為請求後立刻讀到的就是真實電位

症狀
沒人按，程式一啟動就收到 released。
後果
第一筆事件是假的；只讀一筆的程式直接結束。
正解
請求後先等穩定（50 ms），丟掉期間的事件，只認改變狀態的事件。

用單次 gpioget 確認接線

症狀
按鍵放開，gpioget 讀到 0。
後果
以為上拉沒接好或按鍵卡住。
正解
用會持有 line 的程式（本章的程式、debugfs）確認；單次讀值落在請求後的 20 ms 內。

直接印 kernel 的 seqno

症狀
程式略過一筆事件，印出的 seq 就跳號。
後果
驗收腳本誤判成遺失；真的溢位反而分不出來。
正解
印自己的計數；kernel seqno 只用來檢查缺口，缺了報 lost。

測試把等待寫進斷言訊息

症狀
assertIsNone(p.poll(), "..." + p.communicate()[0]) 卡住。
後果
訊息先求值，communicate() 等一個正確睡著的程式，測試永遠不結束。
正解
確定失敗之後才組訊息：if p.poll() is not None: self.fail(...)。

以為開機預設 pad 是上拉

症狀
pinconf 顯示 pull=1。
後果
沒有外接上拉時，放開會被拉成低電位（還要加上 TXB0108 的問題）。
正解
外接 330 Ω～1 kΩ 上拉，蓋過內部的下拉。

以為 driver 卸載後 pad 會還原

症狀
載入過 edge_button.ko 之後，pinconf 變成 pull=2。
後果
誤把上一個 driver 留下的設定當成開機預設值。
正解
要看預設值就重開機；腳本會檢查這次開機有沒有 probe 過。
5a.11收尾5-a → 5-b

這一步做到了什麼

  • 不寫 kernel code，用 gpiolib-cdev 的 edge event 等按鍵：blocking read()，等待時 0 CPU tick；按一下、長按、快速連按都通過，驗收 0 failure。
  • 開機預設 pad（重開機後、沒有載入 driver）就能讀：enable-input=1。
  • 找到並處理請求 line 後約 20 ms 的假事件；順帶更正了 5-b 章裡「用 gpioget 確認接線」的說法。
  • 沒有實測：佇列滿（依 gpiolib-cdev 原始碼是丟最舊的事件、seq 跳號；未在本機核對）。
  • 20 ms 假事件的原因、時間戳落在 1 ms 格點的原因都沒有查證；50 ms 的穩定期是依實測值留的餘裕。

下一章 5-b 做同一件事，但把圖 5.1 中間的 gpiolib-cdev 換成自己寫的 kernel driver：Device Tree 描述按鍵、devm_request_irq()、IRQ handler 只排一個 20 ms 後的 work、自己的 kfifo 和 wait queue。兩章的輸出格式一樣，可以直接對照。

1. 這一章的程式沒有 IRQ handler，按下按鍵時是誰處理中斷的？

kernel 的 gpiolib-cdev。請求 line 時帶了 EDGE_RISING | EDGE_FALLING，它就替這條 line 登記中斷，中斷進來時做 debounce、把 gpio_v2_line_event 放進這次請求的佇列，再叫醒睡在 read() 的程式。

2. 按鍵是接地觸發（按下 = 低電位），為什麼程式把 rising 當成按下？

請求時加了 GPIO_V2_LINE_FLAG_ACTIVE_LOW，kernel 回報的是邏輯值；uAPI 的 rising 定義是 inactive → active，也就是按下。

3. 為什麼程式啟動後要先睡 50 ms？拿掉會怎樣？

請求 line 後約 20 ms 內 pin 讀到 0，恢復時 kernel 會報一筆 released。拿掉的話，line 閒置一陣子之後啟動，第一筆就是這個假事件；只讀一筆的話程式會直接結束，實機測試「沒人按不能有事件」會失敗。

4. edge_button.ko 載入時執行這一章的程式，會發生什麼？

請求 line 43 失敗，印 request line 43: Device or resource busy，結束碼 1：一條 line 同時只能有一個使用者，driver 先拿走了。
