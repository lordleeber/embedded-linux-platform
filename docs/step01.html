Step 1 · 建立可重複的開發環境基線

先把這台 Jetson 的板型、系統版本、kernel 和工具記下來。後面的 module 與 Device Tree 都要以這份資料為起點。

這一步的資料流

執行者在 Jetson target 上啟動 scripts/check_host_env.sh。腳本只讀取系統檔案、呼叫 uname 和檢查指令是否存在，最後輸出結果或寫入版本快照。這一步沒有 I2C/SPI controller 與 target 之間的交易，也沒有新增 driver 或 MCU firmware。

Jetson 系統檔 / 指令 → check_host_env.sh → PASS/FAIL 報告
                                            └→ docs/jetson-version.txt

1. 執行與解讀結果

bash scripts/check_host_env.sh
bash scripts/check_host_env.sh --record docs/jetson-version.txt

--record 會覆寫指定快照檔。可先只執行第一行檢查；要更新基線時才執行第二行。輸出分成平台資訊、平台檢查和工具檢查。PASS 表示當前檢查通過，FAIL 會讓腳本以狀態碼 1 結束。參數不正確或無法寫快照時回傳 2。

工具檢查包含 gcc、g++、cmake、make、git、dtc、i2cdetect 和 v4l2-ctl。最後三個指令分別由 device-tree-compiler、i2c-tools 和 v4l-utils 套件提供。

2. 為什麼記錄這些版本

資料來源後面如何使用
板型/proc/device-tree/model確認實際 target 與 pinout 文件相符。
Kernel release / 架構uname對照 module 與 headers。
Ubuntu 版本/etc/os-release記錄 userspace 基底。
L4T release/etc/nv_tegra_release對照 Jetson BSP。
JetPack 套件dpkg-query記錄本機安裝的套件版本；缺失時標為 unavailable。
Kernel headers/lib/modules/$(uname -r)/build下個 Step 編譯 kernel module 時使用。

目前的 headers 檢查只確認目錄存在。能否編譯並載入與正在執行的 kernel 相符的 module，要在 Step 2 實際驗證。

3. 接線先記錄，之後再驗證

本 Step 執行時硬體尚未接線。接線表先列出 INA219、OLED、LED、STM32 和 IMX219 的訊號與待填欄位。接線時要逐一填入 Jetson 40-pin header 的實體 pin、Linux controller 或 bus、電壓、對端 pin 和驗證方式。header pin 號不能直接當 Linux GPIO 編號；電壓和共地也必須先核對。實際 bus 掃描留在後續對應的 Step。

4. 驗收與重現

python3 -m unittest discover -s tests -v
python3 scripts/check_book.py docs

四個測試用模擬的 Jetson 資料與工具路徑驗證：全部可用時回傳 0；缺 dtc 時明確回報失敗；缺 v4l2-ctl 時仍可留下平台快照；缺板型與 L4T 資料時也會失敗。教材檢查會核對本章連結與導覽。

這台 Jetson 的檢查輸出保存在 版本快照，驗收結果和限制保存在 基線紀錄。換機或更新 JetPack 後重跑腳本，逐項比對版本和板型。

範圍：本章只建立工具與硬體資訊基線；沒有實作 kernel driver、修改 Device Tree、安裝 Yocto 或撰寫 STM32 firmware。
