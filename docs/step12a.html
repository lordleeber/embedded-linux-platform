register map v1.0：把 demo 變成契約

Step 11 的四個 register 能動，但只是 demo：多 byte 怎麼讀沒定義，寫錯了 Jetson 也不會知道，firmware 改版時 driver 不知道能不能繼續用。這一步不加任何新周邊、不接新線，只把 protocol 本身定成一份可以維護的契約：位址分區、版本號、auto-increment、回報錯誤的 STATUS register，以及 bus 出錯後讓 I2C1 自己恢復。

12a.1起點為什麼

driver 要照著寫的東西，得先寫清楚

Step 13 要在 Jetson 上寫 kernel driver edge_ctrl，它只能照 register map 寫。Step 11 的 map 有三個洞，driver 一碰就會出問題：

  • 多 byte 的值怎麼讀？Step 12-b 的 ADC 是 12 bit，一個 byte 放不下。Step 11 一次讀 3 個 byte 會拿到同一個 register 三次，等於沒定義。
  • 寫錯了怎麼知道？F103 收到 byte 時硬體已經回了 ACK，firmware 想拒絕也來不及。Step 11 唯一的辦法是讀回來比對。
  • firmware 換版之後，driver 還能不能用？沒有版本規則，driver 只能假設 firmware 永遠不變。

這一步的答案依序是 auto-increment、STATUS register 和 PROTOCOL_VERSION。另外還清掉 Step 11 code review 留下的一件事：bus 出錯之後 I2C1 沒有重設，萬一卡住只能按 RESET。

互動雙方和 Step 11 一樣：Jetson 的 i2c-1（c240000.i2c，100 kHz）是 controller，Blue Pill 的 I2C1（0x42）是 target，Jetson 這邊仍然只用 i2c-tools。接線完全沒變。這一步不做：ADC 與按鍵（Step 12-b）、真正的 watchdog（Phase 6）、SPI、DMA、Jetson kernel driver（Step 13）。

auto-increment
一次 transaction 裡連續讀寫多個 byte 時，每個 byte 自動對應下一個 register 位址。讀 2 個 byte 就能拿到 ADC 的低、高兩半。
RW1C
write-1-to-clear：寫 1 的 bit 被清成 0，寫 0 的 bit 不動。常見於狀態暫存器，F103 自己的 SR1 也類似（寫 0 清，叫 rc_w0）。
read-to-clear
另一種清法：讀一次就清掉。這一章會說明為什麼這顆周邊不能用它。
BERR · ARLO · OVR
F103 I2C 周邊的三種錯誤：bus error（在不該出現的位置看到 START / STOP）、arbitration lost（自己送 1，線上卻是 0）、overrun / underrun（資料來不及搬）。
SWRST
I2C 周邊 CR1 裡的軟體重設位元：設 1 再設 0，周邊回到 reset 狀態，所有 I2C1 暫存器都清掉。
ES096
ST 給 STM32F101/102/103 的 errata sheet（勘誤）。其中一條：I2C 的 analog filter 可能讓 BUSY 旗標卡在 1，周邊不再回應。
12a.2全景一次 4 byte 讀取

一次 i2ctransfer w1@0x42 0x00 r4@0x42

先看這一步的核心：寫 pointer 0x00，接著讀 4 個 byte。Step 11 的 11.5 留了一個伏筆：F103 用 TXE 送資料時，會在 Jetson 回 NACK 之前先把下一個 byte 放進 DR。讀 4 個 byte，firmware 其實被問了 5 次：

firmware 分不出哪一次 tx() 的 byte 會真的送出去：TXE 中斷只說「DR 空了」，不說「上一個 byte 被 ACK 了」。所以規格要寫成「多取一個 byte 也沒關係」，而不是靠 firmware 去數。

12a.3契約register map v1.0

分區、七個 register、一個版本號

位址先分成四區，之後加 register 時就知道該放哪裡，也看得出哪些位址是保留的：

範圍用途
0x00–0x0F識別與版本：DEVICE_ID、FW 版本、PROTOCOL_VERSION
0x10–0x1F感測與輸入：Step 12-b 的 ADC、按鍵（現在全部讀 0xFF）
0x20–0x2F輸出控制：LED_CONTROL
0x30–0x3F健康狀態：STATUS、WATCHDOG_STATUS

WATCHDOG_STATUS 現在固定是 0，只先佔住位址：Phase 6 做 watchdog 時，driver 不必改 map 就知道去哪裡讀。

版本規則：兩個版本號，管兩件事

FW_MAJOR / FW_MINOR 描述 firmware 這個「產品」：每次發佈都要改，只修 bug 也一樣。PROTOCOL_VERSION 描述 driver 看到的「介面」，一個 byte 拆成兩半：

Step 11 的 firmware 沒有 0x03，讀到 0xFF（major 15），所以 driver 一眼就分得出「版本規則之前」的 firmware。這一步自己就是 major 改變：寫入改成 auto-increment，Step 11 的規則「第 2 個以後的資料 byte 丟掉」不成立了。Step 12-b 加 ADC 與按鍵，預計是 1.1。

12a.4protocolauto-increment

auto-increment 只活在一筆 transaction 裡

EEPROM 常見的做法是 pointer 跟著讀寫一直往前走：讀了 0x01，下一次不寫 pointer 直接讀，就拿到 0x02。這顆周邊如果照做，圖 12.1 那個多取的 byte 每次都會讓 pointer 多走一格：

所以規則是：pointer 只由寫入的第 1 個 byte 設定；transaction 裡另外有一個 cursor 往前走；每次讀取開始時，i2c_target_read_start() 把它放回 pointer。代價寫進了 register map：Jetson 不能「接著上次的地方」繼續讀，每次都從 pointer 開始。對 driver 來說這不是限制：它本來就會每次先寫 pointer。

cursor 是 uint8_t，過了 0xFF 自然回到 0x00，這個「繞回」也寫進了規格，有向量和實機測試。Step 11 的 DISCARD 狀態不見了：多出來的資料 byte 不再丟掉，而是寫到下一個位址，各自檢查。i2ctransfer w3@0x42 0x20 0x01 0x00 會把 LED 打開，再因為 0x21 沒定義在 STATUS 留一個 bit。

「cursor 回到 pointer」只寫在 read_start() 一個地方是刻意的。第一版在 stop() 也寫了一次，結果把 read_start() 拿掉，測試幾乎都還是綠的（12a.7）：同一件事寫在兩個地方，一個壞了，另一個會把它蓋住。下面的模擬器是同一套規則的 JavaScript 版，「讀」會把多取的那個 byte 也列出來：

模擬：瀏覽器裡的 i2c_target.c（JavaScript 改寫），不是實機
state IDLE ptr 0x00 cursor 0x00 LED 0 STATUS 0x80

      

      
試試：START + 寫 → 送 0x00 → 讀 n = 4，看第 5 個「預先取」的 byte；再直接讀一次 n = 1，拿到的仍是 0xED。然後寫 0x20、0x05、STOP：LED 不變，STATUS 多了 0x04。

    

  


  

    
12a.5錯誤回報STATUS

    

      
STATUS：寫 1 清除，讀取不清

      
      
      
為什麼不用 read-to-clear？它對 driver 最省事：讀一次拿到錯誤、順便清掉。但回到圖 12.1：讀 0x2F（沒定義）的 1 個 byte 時，TXE 會順便取 0x30，那個 STATUS byte firmware「讀過」，Jetson 卻沒收到。read-to-clear 的話，旗標就在沒人看到的情況下消失了。這不只是推論：把 firmware 改成 read-to-clear 燒進板子，test_status_survives_a_read_that_runs_into_it 實機紅了，旗標真的不見了。這也是第一次實測證實「TXE 會預先取下一個 register」，Step 11 只推論過。

      
其他幾條規則也是從同一個理由來的：

      
    
        
  • 讀取任何位址都不算錯誤，包括沒定義的。多 byte 讀取本來就會讀過一個區塊的尾端（讀 0x03 的 2 個 byte，第 2 個是 0x04），加上那個多取的 byte，「讀了沒定義的位址」根本分不出是不是 Jetson 的本意。
    • 
        
  • 旗標會累積到 Jetson 清掉為止；寫 0x01 只清 bit 0，其餘保留。所以「讀 STATUS → 處理 → 只清處理過的 bit」之間發生的新錯誤（不同 bit）不會被誤清。同一個 bit 在兩次讀取之間發生兩次，看起來和一次一樣。
    • 
        
  • 清 STATUS 本身不算錯誤，寫 0x00 什麼都不清。
    • 
      

    

  


  

    
12a.6firmware中斷的改動

    

      
main.c：讀取開始的時機、bus 出錯後重設 I2C1

      
EV handler 只多了一件事：ADDR 而且是讀取（TRA = 1）時呼叫 read_start()，而且要在 TXE 之前。同一份 SR1 快照可能同時有 ADDR 和 TXE，順序反了，第一個 byte 就會用舊的 cursor 去取。這條順序有原始碼測試守著。

      
      
錯誤中斷原本對所有旗標都一樣處理：清掉、結束 transaction。現在分兩路。AF 照舊是讀取的正常結束；BERR / ARLO / OVR 是真的出錯，記進 STATUS，接著用 SWRST 把 I2C1 整個重設：

      
      
    
        
  • 先存 SR1 再清：I2C_ClearITPendingBit() 會把這些 bit 寫成 0，之後再讀就分不出剛才是哪一種了。
    • 
        
  • SWRST 清掉所有 I2C1 暫存器，包括自己的位址 OAR1、ACK、中斷致能。所以原本的初始化拆成兩半：GPIO、時脈、NVIC 只做一次（i2c1_target_init()），I2C1 自己的暫存器放進 i2c1_regs_init()，重設後再跑一次。忘了這件事，重設完 0x42 就永遠不會 ACK 了。
    • 
        
  • 沒做的：ES096 對「BUSY 卡住」建議的完整做法，是把 SCL / SDA 暫時切成 GPIO、手動切換電位，再 SWRST。這一步只做 SWRST，不保證能解開 ES096 那種卡住；沒有重現方法，加了也驗不了，所以排到後面的 Step（Phase 6 的 Step 14）。第一版的註解寫成 SWRST 就能處理 ES096，code review 指出說過頭了，已改。
    • 
        
  • 沒有 rollback：bus error 之前收到的 byte 已經生效了（pointer、已經寫進去的資料），之後的 byte 不算。Jetson 看到 BUS_ERROR，就把那一筆寫入整筆重送。目前可寫的只有 LED_CONTROL 和 STATUS（write-1-to-clear），重送都沒有副作用，所以這樣就夠了。第一版的 register map 寫成「這筆 transaction 作廢」，也是 code review 指出的。
    • 
      

      
這段怎麼驗？Jetson 的 controller 只會送合法的 transaction，沒辦法從 Jetson 故意製造 BERR。所以把問題拆成兩半。重設程序本身：燒一個測試用的 firmware，讓每次讀取結束（AF）都 SWRST + 重新設定，再跑完整的實機測試和驗收腳本（500 筆 transaction）。結果 全綠，表示重設後 0x42 照樣 ACK、中斷照樣進來、protocol 狀態正確，而且是在幾百次重設之後。偵測 BERR / ARLO / OVR 那一段：沒有實測，只有 host 向量（i2c_target_bus_error() 設 bit、結束 transaction）與原始碼測試（ER handler 看這三個旗標、AF 不算錯誤）。

測試：先寫規格，再故意把 firmware 改壞

      
    
        
  • tests/test_i2c_target.cpp：16 組向量（Step 11 是 11 組）。新的包括：每個 RO register 被寫時設 RO_WRITE、10 個沒定義的位址先讀（不算錯）再寫（UNMAPPED_WRITE）、STATUS 的 write-1-to-clear、被預先取不會被清、bus error、讀取 auto-increment 與繞回、讀取不移動 pointer、寫入 auto-increment、寫入後同一筆 transaction 讀回。測試的讀取 helper 每次都多呼叫一次 tx()，模擬那個多取的 byte。
    • 
        
  • tests/test_stm32_i2c_target.py：41 個。register-map.md 對 header（多了 STATUS 的 bit 表，和「分區、little-endian、write-1-to-clear、major / minor」這些規則有沒有寫進文件）；原始碼檢查多了 read_start() 在 tx() 之前、ER handler 看三個錯誤旗標並 SWRST、AF 不算錯誤；硬體測試 12 個，其中兩個逐一走過全部 256 個位址：每個都讀一次對照規格，每個 RO / 沒定義的位址都寫一次、檢查值沒變和 STATUS 的 bit。硬體測試的預期值寫在測試檔裡，不從 header 讀：header 錯了，測試不會跟著錯。

先紅

      
先寫 header（介面就是規格）與空的 stub，讓向量在「行為」上失敗，而不是編譯錯誤：56 個 check 失敗。Python 那邊，靜態、文件與腳本的測試紅了 8 個；Step 11 的 firmware 上，實機測試 11 個紅了 10 個。沒紅的是 test_read_after_the_value_changed，它是不回歸的守門測試，本來就該綠。

      
變異：每一種都燒進板子

      
「讀取不移動 pointer」和「read-to-clear 會掉旗標」都跟 TXE 的硬體行為有關，只在 host 上紅不夠，所以每個變異版都燒進 Blue Pill 跑實機測試：

      

        
故意改成結果

        
          
讀取移動 pointer（EEPROM 式，圖 12.3 上排）向量 3 個 check、實機 2 個測試紅（test_reads_never_move_the_pointer、test_read_after_the_value_changed）

          
STATUS 改成 read-to-clear向量 5 個 check、實機 3 個紅，包括「讀 0x2F 之後旗標還在」：證實 TXE 真的會預先取 0x30

          
EV handler 不呼叫 read_start()第一次全綠；補測試後實機 1 個紅；code review 後實機 3 個紅，見下

          
每次讀取結束都 SWRST + 重新設定不是錯誤，是用來驗證重設程序：實機 12 個與驗收腳本全綠

        
      

      
第三種最有意思。第一版的 stop() 和寫 pointer 都會把 cursor 放回 pointer，所以絕大多數情況下，read_start() 做的事早就做好了。只有一種情況分得出來：同一筆 transaction 先寫了資料，再 repeated START 讀。資料 byte 讓 cursor 走到 reg+1，沒有 read_start() 的話，讀回來的是下一個 register：


i2ctransfer -y 1 w2@0x42 0x20 0x01 r1@0x42


0x01

      
規格說讀取從 pointer（0x20）開始，所以要讀到剛寫的 0x01；拿掉 read_start() 會讀到 0x21 的 0xFF。補上這個情況的向量、實機測試和驗收腳本一行之後，這個變異版實機 1 個紅、向量 1 個 check 紅。教訓和 Step 11 的「測試只看 LED」一樣：寫測試時要問「這行 code 拿掉，哪個測試會紅？」，答不出來就是還缺一個。

      
只紅 1 個還是太薄。code review 指出根本原因：同一條規則寫在 stop() 和 read_start() 兩個地方。把 stop() 裡那行拿掉，只留 read_start()，同一個變異版在 host 端從 1 個 check 變成 5 個，燒進板子變成 實機 3 個紅（包括「讀取不移動 pointer」和「LED 切換後讀回」）。補測試只是把洞補上；拿掉重複，才讓一個錯誤在很多地方都看得到。

  3. 3phase05 的負向測試：每一種不合法的寫入都在 STATUS 留下自己的 bit，值本身沒變。
    4. 
        
  4. 4RO_WRITE 和 BAD_VALUE 同時存在時寫 0x01，只清掉 RO_WRITE：write-1-to-clear。
    5. 
        
  5. 5一次讀 4 個 byte，依序是 0x00–0x03：Step 11 同一條檢查讀到的是同一個 register 三次。
    6. 
        
  6. 6前一行讀了 0x01 起的 3 個 byte（再加上多取的一個），這次不寫 pointer 直接讀，仍然從 0x01 開始：讀取不移動 pointer。
    7. 
        
  7. 7phase05 的驗收條件「Jetson 端可穩定讀寫多個 register」：單 byte、多 byte、不寫 pointer 的讀取交錯 500 次，全對，之後 STATUS 是 0，表示中間沒有任何寫入被丟掉。每筆是一個新 process，平均約 3 ms。
    8. 
      

      
你的板子沒接 OLED 時那行同樣是 SKIP。在板子旁就不加 --no-look，腳本會問 LED 亮、滅兩次。手動試 auto-increment 與 STATUS：


i2ctransfer -y 1 w1@0x42 0x00 r4@0x42


0xed 0x00 0x02 0x10


i2cset -y 1 0x42 0x20 9 && i2cget -y 1 0x42 0x30 && i2cset -y 1 0x42 0x30 0x04 && i2cget -y 1 0x42 0x30


0x04
0x00

      
LED_CONTROL 寫 9 被丟掉，STATUS 讀到 BAD_VALUE（0x04），寫 0x04 清掉後是 0。第一行如果是 0x84，表示 RESET bit 還在（板子重開後沒人清過），用 i2cset -y 1 0x42 0x30 0xff 全清。如果 0x03 讀到 0xff，板子上跑的還是 Step 11 的 firmware。

      
沒有實測：真正的 bus error（BERR / ARLO / OVR）的偵測，見 12a.6；ES096 的 BUSY 卡住（沒遇到）；400 kHz；OLED 與 STM32 同時在 bus 上。

      
之後使用者在板子旁跑了不加 --no-look 的完整腳本，0 failure：人確認 LED 亮、滅，500 筆混合讀取 1.4 s 全對。那一輪的 STATUS「找到時」是 0x00，因為板子從上一輪之後沒有重開。

    

  


  

    
12a.9常見錯誤

    

      
踩過與差點踩的坑

      

        
pointer 跟著讀取走
症狀
不寫 pointer 的讀取，每次都比預期多跳一個 register。
後果
driver 讀到別的 register 的值，而且只在某些讀法下發生。
正解
pointer 只由寫入設定，cursor 在 transaction 結束時回到 pointer。

        
STATUS 用 read-to-clear
症狀
讀了 0x2F 之後，STATUS 的旗標不見了。
後果
錯誤被一個沒送出的 byte 清掉，Jetson 永遠看不到。
正解
write-1-to-clear，讀取沒有副作用。

        
把「讀沒定義的位址」當錯誤
症狀
每次多 byte 讀取讀過區塊尾端，就多一個錯誤旗標。
後果
STATUS 一直有雜訊，真正的錯誤被淹沒。
正解
只有被丟掉的寫入與 bus error 算錯誤。

        
SWRST 之後忘了重新設定
症狀
bus 出錯一次之後，0x42 永遠不再 ACK。
後果
本來要避免的「只能按 RESET」，換個方式發生。
正解
SWRST 清掉 OAR1、ACK、中斷致能；把 I2C1 自己的設定拆成 i2c1_regs_init()，重設後再跑。

        
測試沒抓到 read_start
症狀
把 read_start() 從 EV handler 拿掉，向量和實機全綠。
後果
「寫完資料同一筆讀回」讀到下一個 register，沒人發現。
正解
補 w2@ 0x20 0x01 r1@ 這個情況；再把重複的規則拿掉，只留在 read_start()。

        
註解寫得比實測多
症狀
ER handler 的註解原本寫「the Jetson retries」。
後果
讀者以為重設期間的 transaction 會自動重送；i2c-tools 不會。
正解
改成「失敗；要不要重試由 Jetson 端決定」。寫進教材前，每句宣稱都要有出處。

      

    

  


  

    
12a.10收尾下一步

    

      
這一步做到了什麼

      
    
        
  • register map v1.0：分區、七個 register、STATUS 的 bit、little-endian 的多 byte 規則、版本規則，寫在 register-map.md 和 i2c_target.h，測試讓兩份一致。
    • 
        
  • phase05 的驗收條件成立：protocol 有明確文件，Jetson 端穩定讀寫多個 register（500 筆混合讀取全對），不合法的寫入能從 STATUS 看到。驗收 0 failure。
    • 
        
  • Step 11 帶過來的三件事：多取的 byte 不再影響 pointer（從規格上消失）、寫入失敗有 STATUS 回報、bus error 後重設 I2C1（重設程序實測過）。
    • 
        
  • 測試：16 組 C++ 向量、41 個 Python 測試；四個變異版都燒進板子驗過。規模：非空白新增 566 行（產品碼 143、測試 361、驗收腳本 62，含 code review 的修正）。
    • 
        
  • 沒有實測：真正的 bus error 偵測、ES096 的 BUSY 卡住、400 kHz。
    • 
      

      
Step 12-b 把 0x10–0x1F 填起來：ADC_LOW / ADC_HIGH 與 BUTTON_STATE，需要新接線（可變電阻與按鍵）。ADC 是第一個多 byte 的值，會用到這一章的 little-endian 和 auto-increment；兩個 byte 還要來自同一次轉換，否則一次讀取可能拿到新的低位元組和舊的高位元組。PROTOCOL_VERSION 會變成 1.1。

      
1. 讀 4 個 byte，firmware 的 tx() 會被呼叫幾次？為什麼多的那次不會出事？
5 次。第 5 次發生在第 4 個 byte 開始送出時（TXE），那時 Jetson 還沒回 NACK。它不會出事，是因為讀取沒有任何副作用：不移動 pointer、不清 STATUS，transaction 一結束 cursor 就回到 pointer。

      
2. 為什麼 STATUS 不用 read-to-clear？
讀 0x2F 時 TXE 會順便取 0x30，那個 byte 不會送到 Jetson。read-to-clear 的話旗標就在沒人看到時被清掉；變異版燒進板子實測，旗標真的不見了。

      
3. Step 12-b 加了 ADC register，PROTOCOL_VERSION 要怎麼改？只認得 1.0 的 driver 還能用嗎？
minor 加 1，變成 0x11。ADC 放在原本讀 0xFF 的位址，既有 register 的意思不變，所以只認得 1.0 的 driver 照樣能用（它不會去讀 ADC）。如果改的是 LED_CONTROL 的意思，就要升 major。

      
4. i2ctransfer -y 1 w3@0x42 0x20 0x01 0x00 之後，LED 和 STATUS 是什麼？
LED 亮（0x20 = 1），然後 0x00 寫到 0x21，那裡沒有定義，所以 STATUS 設 UNMAPPED_WRITE（0x02）。每個資料 byte 各自寫到下一個位址、各自檢查。

      
5. SWRST 之後為什麼要重跑 i2c1_regs_init()，卻不必重設 GPIO 和 NVIC？
SWRST 只重設 I2C1 周邊自己的暫存器（CR1、CR2、OAR1、CCR……），自己的位址、ACK、中斷致能都會被清掉。PB6 / PB7 的 pad 設定在 GPIOB 的 CRL，中斷優先權在 NVIC，都不屬於 I2C1，不受影響。
