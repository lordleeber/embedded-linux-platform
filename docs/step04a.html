先在 userspace 點亮 pin 29

這是第一次接上真正的硬體：一顆接在 40-pin header 第 29 腳的紅色 LED。原本的計畫是直接寫 kernel driver，結果 driver 每一項檢查都通過，LED 卻始終不亮。問題不在程式碼，而在晶片腳位的 pad：JP6 開機時它是斷開的。這一步先不碰 kernel，用一支最精簡的 C++ 程式和一支設定 pad 的腳本，把「電路、pad、GPIO line」分層驗清楚。

4a.1起點為什麼拆

driver 全部 PASS，LED 卻不亮

Step 4 原本要做的是「Device Tree 描述一顆 LED，platform driver 在 probe() 裡拿到 GPIO 去控制它」。driver 寫好、overlay 也套上之後，驗收腳本 33 項 PASS：driver 有 probe、gpioinfo 顯示 line 105 是 output、debugfs 讀到的電位跟著寫入在 hi 和 lo 之間切換。只有一項 FAIL，而 LED 一次都沒亮：

FAIL PQ.05 pad is tristated: output will not reach the pin

為了排除「是不是我們的 driver 寫錯」，再用系統內建的 gpioset 直接控制同一條 line，完全不經過我們的程式碼。結果一樣不亮。兩條獨立的路得到同一個結果，代表問題在比 GPIO 更底層的地方。

所以原本的 Step 4 拆成兩步：4-a（本章）先在 userspace 把問題分層、確認 LED 真的點得亮；4-b 再回到 kernel driver，並用 Device Tree 正式處理 pad。原本的 Step 4 也已經累積了約 930 行，超過每步約 800 行的上限，拆開剛好。

互動雙方：controller 是 Jetson 上的 userspace 程式 edge_gpio_blink，target 是 SoC 的 GPIO controller 和 pin 29 的 pad，最後接到麵包板上的 LED。這一步不做：kernel driver、Device Tree、IRQ、按鈕；也不把 /dev/mem 當成正式做法。

GPIO line
GPIO controller 裡的一條可控制的訊號，通常對應晶片上的一根腳。程式用「哪個 controller 的第幾條 line」指定它。
gpiochip
kernel 把每個 GPIO controller 開放成一個字元裝置 /dev/gpiochipN。userspace 打開它、用 ioctl 請求 line，就能控制 GPIO，不需要寫 driver。
pad
晶片邊緣和外界接觸的那一小塊電路。裡面有輸出驅動器、輸入接收器、上拉／下拉電阻，以及一個選擇這根腳給哪個功能用的多工器。GPIO controller 決定「想輸出 1」，pad 決定這個 1 能不能變成腳位上的電壓。
tristate
輸出的第三種狀態「高阻抗」（Hi-Z）：輸出驅動器和腳位斷開，既不推高也不拉低。
pinmux / pinctrl
設定 pad 的硬體暫存器叫 pinmux；Linux 管理它們的子系統叫 pinctrl。4-b 會用 Device Tree 透過 pinctrl 設定 pad，本章先直接寫暫存器。三個詞的分別與 DT 的寫法見 Device Tree 入門 DT.9。
/dev/mem
把實體位址空間攤開成一個檔案的特殊裝置。SoC 的暫存器都對應到某個實體位址，所以 root 可以透過它直接讀寫硬體暫存器，完全繞過 kernel 的 driver。
4a.2路徑程式 → 電壓

一個 1 要經過幾站才變成 3.3 V

從程式寫下 1，到 LED 亮起，中間有五站。前三站都正常時，所有軟體工具都會告訴你「輸出是 hi」，因為它們讀的是第三站的暫存器，看不到第四站。

這張圖也說明了為什麼驗收一定要有人看 LED：腳本能讀到的最底層是 SoC 的暫存器和 pad 的設定，腳位上的實際電壓只有 LED（或三用電表）看得到。

port Q 從 100 開始，PQ.05 是第 5 支，所以 100 + 5 = 105。對照上一章 DT.6：Device Tree 用的是另一套編號，binding header 定義成 port × 8 + pin，不管每個 port 實際有幾支腳一律當 8 支算，所以同一根腳在 DT 裡是 15 × 8 + 5 = 125，4-b 寫 overlay 時用的就是這個數字。不要把 header pin 號、DT 編號和 line 編號混用。

4a.4pad0x458 → 0x400

把 pad 打開：一個暫存器、三個欄位

PQ.05 的 pad 設定在實體位址 0x02430068：pinmux 區塊的基底 0x02430000（Device Tree 裡的 pinmux@2430000）加上偏移 0x68。一個 32-bit 暫存器佔 4 個 byte（0x02430068～0x0243006B），用不同的 bit 表示不同的電氣設定。要打開 pad，是執行 sudo python3 scripts/pad_pin29.py open，它把其中三個欄位清成 0。下圖是這次開機、line 105 用過之後，開啟 pad 前後讀到的值；真正剛開機時 bit 10 還是 0，值是 0x00000058：

  • tristate（bit 4）：1 = 輸出驅動器斷開。這是 LED 不亮的原因，非清不可。
  • input（bit 6）：輸入接收器。當輸出用不需要；NVIDIA 自家 40-pin overlay 對 pin 29 也是設成 0。
  • pull（bit 3:2）：10 是內部上拉。腳位由輸出主動驅動時不需要，改成 00（不拉）。
  • bit 10：GPIO／SFIO 的選擇位元（SFIO 是腳位的特殊功能，例如 I2C、UART），open 不動它。debugfs 的 gpio-mode 顯示的就是這個 bit。上游 kernel v6.12 的 tegra_pinctrl_gpio_request_enable() 在 line 被請求時把它清成 0（GPIO），tegra_pinctrl_gpio_disable_free() 在 line 釋放時把它設成 1（SFIO）。所以 gpio-mode=1 從字面看像「GPIO 模式」，照上游的寫法其實是選 SFIO。這和實測相符：剛開機是 0，line 用過、釋放之後是 1，所以 0x458、0x400 裡的 bit 10 都是釋放後留下的。

tristate 和 input 容易搞混，因為一個 pad 裡輸出和輸入是兩條獨立的路。input 控制的是腳位上的電壓能不能被 Jetson 讀進來：

                 ┌─ 輸出驅動器（tristate 控制）← SoC 要送出去的值
腳位 pin 29 ─────┤
                 └─ 輸入接收器（input 控制）  → SoC 讀到的值
欄位控制的方向這個 pad 開啟後為什麼
tristate = 0輸出：Jetson 把電壓送到腳位接上LED 要靠它驅動，非清不可
input = 0輸入：Jetson 讀腳位的電壓關掉LED 只需要輸出，Jetson 不必讀它

用途不同，設定也不同。LED 只輸出，所以把 input 關掉；Step 5 的按鍵要讓 Jetson 讀狀態，pad 就是 tristate=1 enable-input=1，不輸出、只讀。低位元組 0x58 也是 tristate = 1、input = 1，對還沒決定用途的腳最安全，不會意外把電壓送出去。

這和 GPIO 的 direction（gpioinfo 顯示的 output、input）是不同層的設定：direction 在 GPIO controller，tristate 和 input 在 pad。所以才會出現 gpioinfo 顯示 output、pad 卻還是 tristate、LED 不亮的狀況。

圖只畫 bit 0～11，是因為這裡讀到的 1 都在這一段，要講的欄位也在這一段，不代表更高的 bit 都沒在用。上游的對照表還列了 bit 12（Schmitt trigger）和 bit 13（drvtype），它們讀到 0，所以圖上看不出來。bit 14 以上這張表沒有列，但要查 TRM 才能確定有沒有功能。pad_pin29.py 只清三個欄位、其他 bit 一律保留，就是因為不該動沒有查清楚的 bit。

偏移 0x68 沒有公式可以算，每個 pad 的暫存器位置是 SoC 的硬體設計，要查表。可以查的地方是 pinctrl driver 裡的對照表，上游 kernel v6.12 的 drivers/pinctrl/tegra/pinctrl-tegra234.c 有這一行：

PINGROUP(soc_gpio32_pq5, RSVD0, EXTPERIPH3, DCB, RSVD3, 0x0068, 0, Y, 5, 7, 6, 8, -1, 10, 12),

第一個參數是 pad 名稱，0x0068 是相對於 pinmux 區塊基底的偏移，所以位址是 0x02430000 + 0x68。同一行也列了 input 在 bit 6、GPIO／SFIO 選擇在 bit 10。其他 pad 的偏移不一定相鄰，例如 soc_gpio08_pb0 是 0x5008。這是上游的檔案，這台跑的 NVIDIA 5.15 kernel 沒有原始碼可以對照，所以下面的實機讀回仍然必要。

這個位址當初不是查表來的，而是憑印象提出的，所以第一步只讀不寫：讀回 0x458，低位元組拆開和 debugfs 的 pull=2 tristate=1 enable-input=1 function=rsvd0 完全一致，才判斷位址大致沒錯。對錯的位址寫入，可能改到別根腳或別的硬體。

這個比對只能排除大部分猜錯的情況，確認不了就是 pin 29。這四個值不是 pin 29 獨有的：JP6 會把沒指定用途的 header 腳都設成「上拉、tristate、只收輸入」，所以猜到另一根 header 腳的暫存器，很可能也讀到相同的低位元組。真正能確認的是這些證據：

open 和 close 只在暫存器「看起來就是這個 pad」時才寫：低位元組是開機值 0x58，或者低位元組是 0x00 而且 bit 10 為 1（實測打開後的值 0x400）。其他值代表位址錯了、或這根腳被設成別的功能，一律拒寫並回傳 1。第一版只要低位元組是 0x00 就當成「已開啟」，code review 指出：很多不相干的位址讀出來就是 0x00000000，萬一位址錯了，close 會把 0x58 寫進一個不認識的暫存器。所以全 0 一律拒寫。代價是：剛開機、還沒有程式請求過 line 時（bit 10 可能還是 0），open 之後會得到 0x000，這時 close 會被拒絕，要先跑過一次 edge_gpio_blink。

寫入時只動三個欄位，其他 bit 原樣保留。存取方式是把 /dev/mem 從 0x02430000 mmap 一頁進來，再用 32-bit 的 memoryview 讀寫第 0x68 / 4 格：

mmap 是 Python 標準函式庫的模組，不用另外安裝。它是用 C 寫的擴充模組（這台在 /usr/lib/python3.10/lib-dynload/mmap.cpython-310-aarch64-linux-gnu.so），只是包了一層 Linux 的 mmap(2) system call，和 C 程式 #include <sys/mman.h> 用的是同一個。mmap 把檔案的一段內容對應到 process 的記憶體裡，之後讀寫那段記憶體，就等於讀寫那個檔案。對 /dev/mem 來說，讀寫那段記憶體就是讀寫實體位址，也就是硬體暫存器：

參數意思
fd/dev/mem，代表整個實體位址空間的特殊檔案
mmap.PAGESIZE對應一頁（4096 byte）。mmap 以頁為單位，offset 也必須對齊頁的邊界，所以從 0x02430000 開始，而不是直接從 0x02430068 開始
MAP_SHARED寫入會直接寫到底層，也就是真的寫進暫存器，而不是寫到 process 自己的私有副本
PROT_READ | PROT_WRITE這段記憶體可以讀，也可以寫
offset=PINMUX_BASE從實體位址 0x02430000 開始，也就是 pinmux 暫存器所在的那一頁

memoryview(page).cast("I") 把這一頁當成 32-bit 整數的陣列，reg[0x68 // 4] 就是 0x02430068 那個暫存器。不用 lseek 加 read / write，是因為 kernel 處理那類存取時，不保證剛好是一次 32-bit 的存取；mmap 之後，存取就是 CPU 對那個位址做一般的 load / store，比較可控。

這有兩個已知限制，寫在腳本開頭：CPython 沒有保證這是單一一次 32-bit 匯流排存取（實測一直正常）；讀和寫之間，kernel 的 pinctrl driver 理論上也可能改到同一個暫存器。對一個沒有任何 device 使用的 pad、只在實驗時用的工具來說可以接受。這個修改 kernel 完全不知道，重開機就會消失。

為什麼這支用 Python，不用 C / C++

repo 裡沒有記錄這個決定的理由（phase02.md 只規劃了檔名），以下是從程式碼和它的定位推回去的：

  • 它是臨時工具，不是產品碼。它放在 scripts/，不在 apps/，只在 4-a 實驗時用來打開 pad。4-b 改用 Device Tree 的 pinctrl 之後就不再需要了。這個專案要長期留下、會進 image 的東西用 C++，驗收和實驗用的工具用 bash 或 Python。
  • 不用建置。直接 sudo python3 scripts/pad_pin29.py open 就能跑，不必先跑 CMake，也避免用 root 建置、在 build/ 留下 root 擁有的檔案（Step 2 踩過的坑）。
  • 好測試。--mem 參數讓 tests/test_pad_pin29.py 用一個稀疏檔假裝成 /dev/mem，在同一個 unittest 裡就能測讀改寫和拒寫，不需要 root，也不會碰到硬體。
  • 邏輯很單純。讀一個 32-bit 值、檢查、清幾個 bit、寫回去，Python 寫起來短、容易讀。

代價就是上面第一個限制：暫存器存取其實是 C 比較適合的工作。C 寫成 volatile uint32_t *reg，編譯器保證會產生一條 32-bit 的 load 和一條 store；Python 這邊靠的是 CPython 目前剛好這樣實作，不是規格上的保證。對一個只在實驗時用、4-b 之後就退役的工具來說，這個取捨可以接受；如果要長期留下，或是要碰很多暫存器，就該改用 C，或直接用現成的 busybox devmem。

和 Step 3 的 edge_test_cli 一樣是 open 加 ioctl，差別在 ioctl 的結果：GPIO_V2_GET_LINE_IOCTL 成功後，kernel 在 req.fd 裡回傳一個新的檔案描述子，代表「這條 line 的使用權」。之後的操作都對這個 fd 做。line 已經被別人持有時，請求會失敗，errno 是 EBUSY。consumer 是給人看的名字，gpioinfo 會顯示誰正在用這條 line。

所以這支程式手上有兩個 fd，分工不同：

fd從哪來代表什麼拿來做什麼
chipopen("/dev/gpiochip0")整顆 GPIO controller只用一次：GPIO_V2_GET_LINE_IOCTL 請求 line
req.fdkernel 在 ioctl 成功時填進 req請求到的 line（這裡只有 105）寫值：GPIO_V2_LINE_SET_VALUES_IOCTL

line 的使用權綁在 req.fd 上：這個 fd 還開著，line 就是你的；close(req.fd)，或程式結束時由 kernel 自動關掉，line 就被釋放。close(chip) 只是關掉 controller 的那個 fd。想親眼看看的話，在程式閃燈時另開一個終端機跑 ls -l /proc/$(pgrep edge_gpio_blink)/fd，會看到一個指向 /dev/gpiochip0，另一個是 anon_inode:gpio-line，後者就是 req.fd。

在這台機器上編譯印出來是 0xc250b407：方向 3（_IOWR，雙向）、大小 592（整個 struct gpio_v2_line_request）、magic 0xB4（GPIO 子系統的代號）、序號 7。方向必須是雙向，因為這個 ioctl 不只把請求傳進 kernel，kernel 還要把 req.fd 寫回來；如果只能單向傳資料，你就拿不到新的 fd。

gpio_v2_line_request req{} 結尾的 {} 會把整個 struct 清成 0。不加的話，區域變數的內容就是 stack 上殘留的垃圾值。程式只填了四個欄位，但 592 byte 裡的其他欄位 kernel 一樣會讀：padding[5] 和 config.padding[5] 是保留給未來版本用的，kernel 要求它們全是 0；config.num_attrs 表示後面附了幾個額外設定（debounce、個別 line 的 flags 等）。在這台機器上實測，用 input 請求 line 105，故意把其中一項設成非 0：

不清零的話，最糟的情況不是每次都失敗，而是有時成功、有時 EINVAL，結果取決於 stack 上剛好留下什麼，這種 bug 很難重現。kernel 要求保留欄位必須是 0，以後的版本才能賦予它們意義，而不會讓舊程式出錯。傳給 kernel 的 struct 一律先清零再填欄位，後面的 gpio_v2_line_values v{} 也一樣。

第二個 ioctl 設定輸出值，最後關掉 fd 就是釋放：

mask 和 bits 都是位元遮罩：一次請求可以包含多條 line，第 n 個 bit 對應 offsets[n]。這裡只請求一條，所以只用 bit 0。要注意 bit 編號是 offsets[] 的索引，不是 GPIO 編號：控制 line 105 用的是 bit 0，不是 bit 105。mask 選出這次要寫的 line，bits 是要寫入的值；沒被 mask 選到的 line 保持原值，所以同時請求多條 line 時，一次 ioctl 也可以只改其中幾條。迴圈跑 10 次，偶數次寫 1、奇數次寫 0，每次寫完 usleep(500000) 停 500000 µs，也就是 0.5 秒，所以是 5 次閃爍、約 5 秒。

rc 是 return code，也就是程式最後的結束碼（shell 裡用 $? 看）：先設成 0，出錯就改成 1，最後統一 return rc。請求 line 失敗時程式直接 return 1，因為那時候還沒拿到 line。拿到 line 之後就不能這樣做了：在迴圈裡直接 return 的話，LED 可能停在亮的狀態。所以出錯時只記下 rc = 1、break，讓程式照常走完收尾。

迴圈結束後不管原因是什麼，都再寫一次 0 才釋放。這個順序很重要：Tegra 的 GPIO driver 釋放 line 時不會把輸出改回 0，最後寫的值會一直留著（見 4a.9）。迴圈會提早結束的情況有兩種：寫入失敗（每次 ioctl 都檢查回傳值，失敗就印出原因、回傳 1），以及收到 Ctrl-C 或 SIGTERM：

signal handler 只設一個旗標。usleep() 被 signal 打斷會提早回來，迴圈看到 stop 就離開，接著照常寫 0、釋放，最後印 interrupted 並回傳 1。如果沒有這段，在 LED 亮著的那半秒按下 Ctrl-C，程式會直接被殺掉，line 由 kernel 釋放，LED 就一直亮著。這兩處（寫入檢查、signal）都是 code review 指出後才補上的。

signal 的細節

Ctrl-C 和 SIGINT 不是同一件事。Ctrl-C 是按鍵：終端機送出字元 0x03，kernel 的 tty driver 認出這是中斷字元（stty -a 裡的 intr = ^C），不把它交給程式當輸入，而是改送 SIGINT 給前景程式。同一個 signal 也可以用指令送出，程式分辨不出來源：

按鍵 / 指令signal（編號）這支程式怎麼處理
Ctrl-C、kill -INT <pid>SIGINT（2）有 handler：停止閃爍、寫 0、釋放，結束碼 1
kill <pid>（不加選項的預設值）、timeoutSIGTERM（15）同上
Ctrl-\SIGQUIT（3）沒攔截：立刻終止，不收尾
kill -9 <pid>SIGKILL（9）無法攔截：立刻終止，不收尾

kill 的名字有點誤導，它其實是「送 signal」的指令，送哪一種由選項決定。handler 的作用也不是讓程式忽略 Ctrl-C，而是把「立刻終止」換成「盡快結束，但先收尾」：剩下的閃爍不會執行，只有迴圈後面的寫 0、印 interrupted、close 會執行。沒有 handler 時，SIGINT 由 kernel 直接終止程式，shell 看到的結束碼是 130（128 + 2）。

  • 為什麼 handler 只設旗標。signal 可能在任何一行中間打進來，handler 裡只能呼叫 async-signal-safe 的函式，perror、fputs 都不在清單上。所以 handler 只記錄「有人要求停止」，收尾交給 main() 自己做。
  • 為什麼是 volatile std::sig_atomic_t。sig_atomic_t 保證寫入不會只做一半就被打斷；volatile 讓編譯器每次都重新讀 stop，不會把迴圈條件裡的值放在 register 裡不再更新。
  • 最壞情況會晚 0.5 秒。signal 如果剛好在「檢查完 !stop」之後、「進入 usleep」之前送達，usleep 就沒有東西可以打斷它，會睡滿 0.5 秒，到下一次檢查才離開迴圈。只是慢一點，收尾不會漏掉。如果改用 C++ 的 std::this_thread::sleep_for 也會是這樣：libstdc++ 的版本被 signal 打斷後會自己把剩下的時間睡完。
  • 連按 Ctrl-C 也不會強制結束。glibc 的 signal() 裝好的 handler 會一直有效，第二次 SIGINT 只是再設一次旗標。

和 Python 版對照

pad 打開之後，用 Python 的 libgpiod（python3-libgpiod，v1 API）做過同樣的實驗，在板子上實測可以閃。pad 沒打開時，它和 gpioset 一樣不會亮：libgpiod 底下呼叫的是同一組 ioctl（gpioset 本身就是 libgpiod 附帶的指令），只能改到 GPIO controller 的暫存器，碰不到 pad。換一種程式語言不會繞過 4a.4 那一步。這段不在 repo 裡，放在這裡是為了對照：

這支程式刻意寫得精簡：沒有參數解析，chip、line、次數、間隔都寫死。代價是「chip 不存在」「line 超出範圍」「寫入失敗」這些錯誤路徑沒有自動測試，只靠 perror 印出原因。

4a.6測試red → green

pad 腳本用假的 /dev/mem，程式用真的腳位

tests/test_pad_pin29.py 的 8 個案例不碰硬體：測試建立一個稀疏檔案當成 /dev/mem，在 0x02430068 那個 offset 寫入暫存器值，再用 --mem 讓腳本去讀寫它。預期值來自板子的實測（開機 0x458、打開後 0x400），不是從腳本抄的。案例涵蓋解碼、open、重複 open 不動作、close 還原、高位元保留、剛開機 bit 10 還是 0 時也能 open、不認得的值（包括全 0）一律拒寫，以及用法錯誤。

tests/test_edge_gpio_blink.py 的 3 個案例會真的驅動 pin 29，所以只有設了 EDGE_GPIO_HW=1 才跑（也才會建置程式），沒設就 skip：

  • 跑完結束碼 0，之後 gpioinfo 顯示 line 105 是 unused（已釋放）。
  • 執行中 gpioinfo 顯示 consumer 是 "edge_gpio_blink"、方向 output；這時再啟動第二個，它要回傳 1，stderr 有 request line 105 和 busy。
  • 在第一段亮燈期間分別送 SIGINT 和 SIGTERM：1 秒內結束、回傳 1、stderr 有 interrupted，line 已釋放。

測試結束時，如果先啟動的那個程式還沒結束，清理程序會把它 kill 掉，不讓它繼續佔著 line 105、拖累後面的測試。

兩支測試都在實作之前寫好，先看它們紅：pad 腳本還不存在時有 9 個 failure；CMake 還沒有 edge_gpio_blink 這個 target 時，blink 測試在建置那一步就出錯。code review 之後補的三個案例（全 0 拒寫、bit 10 規則、signal）也是先紅再修。實作之後再做變異測試，每次故意改壞一處，看測試會不會抓到：把 output 改成 input、改掉 consumer 名稱、改掉錯誤訊息、拿掉低位元組檢查、漏清 pull、整個暫存器寫 0、不裝 SIGTERM handler、不印 interrupted，每一種都讓測試失敗。抓不到的是「最後有沒有寫 0」：line 釋放後 debugfs 就不再列出它，這一點只能靠讀程式碼和看 LED。

不需要 root 的部分隨時可以跑（在 repo 根目錄）：

python3 -m unittest discover -s tests -p 'test_pad_pin29.py' -v
EDGE_GPIO_HW=1 python3 -m unittest discover -s tests -p 'test_edge_gpio_blink.py' -v

第二行大約跑 11 秒，pad 開著時 LED 會閃十幾次。執行者要在 gpio 群組裡（/dev/gpiochip0 是 root:gpio 0660），而且 line 105 不能被別的程式佔著，否則 setUp 就會失敗。

4a.9常見錯誤

踩過或差點踩的坑

debugfs 說 hi，就以為有電

症狀
gpioinfo 是 output、debugfs 是 hi，LED 不亮。
後果
花時間在沒有問題的 driver 上找 bug。
正解
那是 output 暫存器，不是腳位電壓。看 pinconf 的 tristate，並用 gpioset 這種不經過自己程式的工具對照。

照網路範例，以為開機就能用

症狀
Python 範例在別人那裡能閃，在 JP6 上不亮。
後果
懷疑接線或程式。
正解
JP6 開機時這根腳的 pad 是 tristate。很多範例是 JP5 時代寫的，或作者先跑過 jetson-io（它產生的就是 pinmux overlay）。

沒讀就寫 /dev/mem

症狀
憑印象的位址直接寫入。
後果
位址錯了就會改到別的硬體，而且沒有錯誤訊息。
正解
先查 pinctrl driver 的對照表，再讀、拆欄位和 debugfs 比對；pad_pin29.py 把「低位元組不符就拒寫」寫死。

gpioset 結束後 LED 還亮著

症狀
gpioset --mode=time --sec=3 ... 105=1 結束很久了，LED 仍亮。
後果
line 已經沒人管，腳位卻一直輸出 3.3 V。
正解
Tegra 釋放 line 時不會歸零。程式要自己最後寫 0 再釋放；4-b 的 driver 在 remove() 裡也要這樣做。

以為 pinconf 一個 group 一行

症狀
驗收腳本用 grep 只抓到 115 (soc_gpio32_pq5):，兩項假 FAIL。
後果
腳本說 pad 沒開，但其實開了。
正解
那個檔案是「名稱一行、每個設定一行」，改用 awk 收到下一個 group 為止。

Jetson.GPIO 不認得 Super

症狀
import 就丟出 Could not determine Jetson model。
後果
官方 Python 函式庫在這台不能用。
正解

4a.10收尾4-a → 4-b

這一步做到了什麼

  • 接線正確：pad 打開後，userspace 程式能讓 pin 29 的 LED 閃爍（人眼確認）。
  • 分層證明：同一支程式在 pad 關閉時暫存器照樣切換、LED 不亮，問題鎖定在 pad 的 tristate。
  • line 的使用權：執行中 gpioinfo 看得到 consumer，第二個使用者拿到 busy，結束後釋放；驗收0 failure。
  • Ctrl-C / SIGTERM 中斷時也會先寫 0 再釋放；每次寫入都檢查回傳值。
  • 沒有自動驗證：程式結束時腳位是否為 low（line 釋放後 debugfs 不再列出），只靠看到 LED 熄滅；寫入失敗的路徑也無法從外部觸發。SIGKILL / crash 時 LED 仍可能留在亮的狀態。
  • pad 是用 /dev/mem 硬改的，kernel 不知情，重開機就消失；bit 10 的意義和暫存器位址只對照過上游 kernel 的 driver，沒有對照 TRM 和這台 NVIDIA kernel 的原始碼。

下一步 4-b 回到原本的計畫：Device Tree 描述這顆 LED，platform driver 在 probe() 裡用 devm_gpiod_get() 拿到 GPIO。而本章用 /dev/mem 做的事，會改成寫在 overlay 裡的 pinctrl 狀態，在 probe() 之前由 kernel 自動套用。到時候 edge_gpio_blink 也有新用途：driver 載入期間跑它，應該要拿到 busy。

1. debugfs 顯示 PQ.05 輸出 hi，LED 卻不亮。列出兩種可能，各要怎麼查？

pad 被 tristate（看 debugfs pinconf-groups 的 tristate=，或讀 pinmux 暫存器）；接線問題（LED 方向接反、沒接到 pin 30，可以把 LED 改接 pin 1 的常時 3.3 V 確認 LED 本身是好的）。

2. 為什麼 gpioinfo 用 105，而 Device Tree 裡同一根腳是 125？

gpiochip 依序累加每個 port 實際的腳數，port Q 從 100 開始；DT binding 一律把每個 port 當 8 支腳算，15 × 8 + 5 = 125。driver 解析 DT 時再換算回 105。

3. pad_pin29.py 為什麼讀到 0x00000000 時拒寫？它的低位元組明明是「已開啟」的 0x00。

很多不相干的位址讀出來就是全 0。如果位址錯了，把它當成「已開啟」再 close，就會把 0x58 寫進一個不認識的暫存器。實測的已開啟值是 0x400，所以腳本要求 bit 10 也為 1 才算數。

4. 程式在亮燈時被 Ctrl-C 會怎樣？如果是 crash（例如 SIGKILL）呢？

Ctrl-C（SIGINT）有 handler：迴圈提早結束、寫 0、釋放，LED 熄滅。SIGKILL 和 crash 攔不到：kernel 會在程式結束時關掉 fd、釋放 line，但 Tegra 不會把輸出歸零，LED 會一直亮著，直到有人再寫 0 或把 pad 關掉。
