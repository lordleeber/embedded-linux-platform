11.1起點為什麼

從「讀別人的晶片」到「設計自己的晶片」

Phase 5 的目標是一條完全自己寫的路：Jetson 上的 Linux driver（Step 13）對話的那顆周邊，firmware 也是自己寫的。要先有周邊，driver 才有對象，所以這一步只做 MCU 那一端，用 Jetson 的 userspace 工具證明 protocol 通了。好處是之後 driver 出問題時，可以先用同一組 i2cget 指令確認周邊本身沒壞。

互動雙方：Jetson 的 i2c-1（c240000.i2c，header pin 27 / 28，100 kHz）是 controller（舊稱 master），每次 transaction 都由它開始；Blue Pill 的 I2C1 周邊（PB7 = SDA、PB6 = SCL）是 target（舊稱 slave），只會回應，不會自己往 bus 上送東西。這條 bus 就是 Step 9 起 OLED 用的那條，板子上還有兩顆板載晶片 fusb301（0x25）與 ina3221（0x40）。這一步不做：ADC、watchdog、SPI、DMA、Jetson kernel driver。

Blue Pill
一塊便宜的 STM32F103C8T6 最小系統板：Cortex-M3 72 MHz、64 KB flash、20 KB RAM、8 MHz 晶振，板上一顆接在 PC13 的 LED（低電位亮）。BOOT0 / BOOT1 是兩個 jumper，決定 reset 後從 flash 還是從晶片內建的 bootloader 開機。
SPL
Standard Peripheral Library，ST 在 HAL 之前提供的周邊函式庫（這裡用 V3.5.0，2011）。一個函式大致對應一組暫存器操作，例如 I2C_ReceiveData(I2C1) 就是讀 I2C1->DR。
ST-Link / SWD
ST-Link V2 是燒錄器兼除錯器，經 SWD（兩條線：SWDIO、SWCLK）存取 MCU 的除錯介面，可以燒 flash、停住 CPU、直接讀寫任何暫存器。11.8 會用它來除錯。
register pointer
target 記住的「目前選中的 register 位址」。I2C 本身只有「寫一串 byte」和「讀一串 byte」，哪個 byte 代表位址、哪個代表資料，是我們自己的 protocol 規定的。
ACK / NACK
每個 byte 之後的第 9 個 clock，接收方把 SDA 拉低表示收到（ACK）。controller 讀取時，最後一個 byte 回 NACK（不拉低），告訴 target「夠了，別再送」。
clock stretching
target 還沒準備好時把 SCL 拉住在低電位，controller 就會等。F103 在等 firmware 讀走或填入資料時會自動這樣做。
11.2全景一次讀取

一次 i2cget -y 1 0x42 0x20 在 bus 上發生了什麼

讀一個 register 要兩段：先「寫」一個 byte 告訴 target 要哪個 register，然後 repeated START（不放掉 bus、直接再開始）改成「讀」。Linux 的 i2cget（byte data 模式）就是這樣送的。target 這端，每一個 bus 事件都會讓 I2C1 周邊在狀態暫存器 SR1 設一個旗標、觸發中斷，firmware 在中斷裡處理：

11.3契約register map

四個 register，加上「不合法時怎麼辦」

位址 0x42 是這個專案自己挑的（bus 上沒人用）。register 都是 1 byte：

位址 · 名稱存取 · 值
0x00 DEVICE_IDRO，固定 0xED：確認接上的是這份 firmware
0x01 FW_MAJOR · 0x02 FW_MINORRO，0x00 · 0x01（版本 0.1）
0x20 LED_CONTROLRW，reset 後 0x00：0 = LED 滅、1 = 亮

規格裡最容易漏的是不合法的存取。phase05 只說「其他值不要任意解讀」，這一步把它定死：

  • 寫 RO register、寫沒定義的 register、LED_CONTROL 寫 0 / 1 以外的值：bus 上照樣 ACK，然後丟掉。
  • 讀沒定義的 register：回 0xFF。
  • 讀取不 auto-increment：一次讀 3 個 byte，3 個都是同一個 register。多 byte 的 register（ADC）在 Step 12 才出現，到時候再定義順序。

為什麼不用 NACK 拒絕不合法的值？F103 的 I2C1 在 ACK 位元打開時，收到 byte 就由硬體自動回 ACK，firmware 在中斷裡看到這個 byte 時，ACK 早就送出去了。所以 Jetson 要確認寫入有沒有生效，得把 register 讀回來看；Step 12 會加一個 STATUS register 回報錯誤。這份規格有兩份拷貝：人看的 firmware/stm32f103/docs/register-map.md，和程式用的 header：

11.5firmwareSPL 與中斷

    

      
main.c：把 I2C1 的旗標翻譯成四個呼叫

      
初始化做三件事：PB6 / PB7 設成 alternate function open drain（交給 I2C1 周邊驅動，而且只能拉低、不能推高，高電位由 Jetson 載板的上拉電阻提供）、設定自己的位址並打開 ACK、打開中斷。

      
      
I2C_OwnAddress1 要左移一位：OAR1 暫存器的 bit 0 在 7-bit 模式不用，位址放在 bit 7:1。I2C_ClockSpeed 只有當 controller 時才用到，但 SPL 的 I2C_Init() 一定會拿它算時脈分頻，所以還是要填。三種中斷：EVT（ADDR、STOPF 這類事件）、BUF（RXNE / TXE：資料暫存器滿了 / 空了）、ERR（AF、bus 錯誤）。事件與錯誤是 兩個不同的中斷向量：

      
      
幾個不看 reference manual（RM0008）就會寫錯的細節：

      
    
        
  • 清旗標的方法各不相同。ADDR 要「讀 SR1 再讀 SR2」才會清掉，I2C_GetLastEvent() 正好就是這兩次讀取（還把 SR2 放在高 16 位元，所以 TRA 要左移 16）。RXNE / TXE 靠讀寫 DR 清。STOPF 要「讀 SR1 之後寫一次 CR1」：I2C_Cmd(I2C1, ENABLE) 就是把已經是 1 的 PE 位元再寫一次。哪一個沒清掉，中斷一返回就會立刻再進來，CPU 永遠出不來。
    • 
        
  • 讀取不是以 STOP 結束的。controller 讀完最後一個 byte 回 NACK，target 這端收到的是錯誤中斷裡的 AF（acknowledge failure），而不是 STOPF。只在 STOPF 收尾的話，讀取永遠不會回到 IDLE。
    • 
        
  • TRA 決定方向。ADDR 同時有 TRA = 1（Jetson 要讀），就不呼叫 write_start()，接下來的 TXE 才是送 byte 的時機。
    • 
        
  • 同一次讀到的旗標，先處理 RXNE 再處理 ADDR。寫入的資料 byte 還沒被讀走、controller 就送了 repeated START 時，同一份 SR1 會同時有 RXNE 和 ADDR。第一版先呼叫 write_start()，那個資料 byte 就會被當成新的 pointer，LED 的寫入就這樣不見了。這是 PR #17 code review 抓到的；中斷處理這麼短，實機很難碰到，所以只用一條測試檢查原始碼裡的順序，沒有實測。
    • 
      

      
原本以為要防的 bug，實測沒有發生：BUF 中斷開著時，硬體把一個 byte 搬去送的同時 TXE 就又亮了，firmware 會在 Jetson 回 NACK 之前先放好下一個 byte。我讀 RM0008 推論：這個預先放好的 byte 會留在 DR，在下一次讀取時先被送出去，讀 0x20 會拿到上一次讀的 0x00 的值。所以第一版在讀取時關掉 BUF、改用 BTF 補 byte。實機上試了兩種沒有防護的寫法，「交替讀 400 次」都全對，所以改回最簡單的 TXE 寫法。code review 時又問到：值在兩次讀取之間改變的話呢？想清楚就知道不會出事：預先放的永遠是同一個 register 的值，而 pointer 和值只會被寫入改變，寫入收到的 byte 也經過同一個 DR，會把預先放的那個蓋掉。實機上 LED 切換 20 次、每次分別用 i2cget 和不寫 pointer 的 i2ctransfer r1 讀回，全部正確，這條也加進了硬體測試。硬體本身怎麼處理那個沒送出去的 byte，沒有查證。11.7 會說明怎麼確認這些測試真的抓得到這種錯。

      
main() 本身什麼都不做，所有事情都在中斷裡發生。主迴圈原本寫成 for (;;) __WFI();（睡到下一個中斷），後來改成空迴圈，原因在 11.8。

      
腳位的 pad 設定：沒有 pinmux，寫在 GPIO 自己的暫存器裡

      
Jetson 那邊，一根腳背後的 pad（訊號來源選擇、輸出驅動器、輸入接收器、上下拉）由獨立的 pinmux 暫存器區設定，Linux 透過 pinctrl 和 Device Tree 管它（見 Device Tree 入門 DT.9）。MCU 一樣有 pad，差在設定放在哪裡、由誰來寫：STM32F103 沒有獨立的 pinmux 區塊，每根腳的 pad 設定就放在它所屬 GPIO port 的 GPIOx_CRL（pin 0–7）／GPIOx_CRH（pin 8–15）裡，每根腳 4 個 bit。沒有作業系統替你管，firmware 初始化時自己寫。

      

        
4 個 bit意思

        
          
MODE[1:0]（低兩位）00 = 輸入；01 / 10 / 11 = 輸出，最高翻轉速度 10 / 2 / 50 MHz。速度其實是輸出驅動器的邊緣速率，也是 pad 的電氣選項

          
CNF[1:0]（高兩位），輸入時00 類比、01 浮接、10 上拉或下拉（由 ODR 那一位決定：1 上拉、0 下拉）

          
CNF[1:0]，輸出時00 推挽、01 開汲極、10 交給周邊（AF）推挽、11 交給周邊開汲極

        
      

      
欄位定義依 STM32F103 的 reference manual（RM0008）。這張表在 SPL 的原始碼裡就看得到，因為 GPIO_Mode_* 的數值就是照這些欄位編碼的：

      
      
GPIO_Init() 把這兩個值組成那 4 個 bit：模式先取低 4 bit；是輸出的話（0x10），再把速度 OR 進 MODE。

11.6建置PlatformIO

    

      
PlatformIO，但不用它的 SPL

      
PlatformIO 是建置工具：負責下載 toolchain、編譯、連結、呼叫 OpenOCD 燒錄。它的設定可以寫 framework = spl，讓它提供 SPL，但 PlatformIO 的 framework-spl 套件沒有 STM32F1（只有 F0 / F3 / F4 / L1），Blue Pill 會得到 This board doesn't support spl framework。所以照這個專案作者自己的 SPL 課程（VS Code + PlatformIO）的做法：不指定 framework，CMSIS 與 SPL 原始檔放在專案目錄裡，PlatformIO 只負責編譯它們。

      
      
和課程原本的設定差三處。前兩處是因為這次在 Jetson（aarch64）上建置：課程用的 toolchain-gccarmnoneeabi@1.70201.0（GCC 7.2.1）沒有 aarch64 版，換成 12.3.1；而 GCC 12 的 assembler 不接受 build_type = debug 傳給 .s 檔的 -g2，所以拿掉 debug 建置。第三處是 -Wall -Wextra -Werror：host 端的 CMake 只編 i2c_target.c，main.c 只有這裡會編到；實測連 SPL 的檔案在這組旗標下也沒有任何 warning。Start/、Library/、startup/、ldscript/ 的 14 個檔從課程原樣複製，SHA-256 記在 vendor.sha256，有一條測試逐檔比對；.gitattributes 把它們設成 -text，git 不會改動 CRLF 換行。

      
自己建置一次

      
起點：repo 根目錄、Jetson 或任何 Linux，有 Python 3。第一次要裝 PlatformIO Core（裝到 VS Code 擴充套件也用的 ~/.platformio/penv）：

  • tests/test_stm32_i2c_target.py：29 個。register-map.md 的表格對 header 的值；i2c_target.c 不准出現任何暫存器；main.c 用 I2C1、PB6 / PB7、0x42 << 1、PC13 低電位亮；AF 會結束 transaction；RXNE 在 ADDR 之前處理；主迴圈沒有 WFI；ini 有 -Wall -Wextra -Werror；範圍檢查（沒有 ADC、IWDG、SPI、DMA，沒有 kernel/edge_ctrl）；vendor 檔的 SHA-256。PlatformIO 和釘住的 toolchain（1.120301.0）都已經裝好時，真的建置 firmware，再用那個 toolchain 的 arm-none-eabi-nm 確認兩個中斷 handler 是我們的強符號；沒裝就 skip，不會在跑測試時上網下載。硬體測試 6 個（EDGE_STM32_HW=1），其餘不需要板子。
    • 
      

      
中斷 handler 那條是 firmware 特有的陷阱：startup 檔把每個中斷向量都先定成 weak 的 Default_Handler。handler 名字拼錯（例如寫成 I2C1_ERR_IRQHandler）照樣編譯、照樣連結，只是錯誤中斷發生時跳進 Default_Handler 的無窮迴圈。故意改錯名字，這條測試就紅。

      
測試有沒有紅過

      
實作前跑一次：7 failures、9 errors、5 個硬體 skip。先就會過的 3 個是守門測試（register map 對 header、vendor 檔雜湊），它們在 header 和 vendor 檔放進去時就成立。接著故意把 i2c_target.c 改錯 7 種（接受 LED 值 2、多餘的資料 byte 也寫、repeated START 不重設、沒定義的讀成 0……），每一種都讓向量失敗。其中「IDLE 時收到的 byte 改到 pointer」第一次沒被抓到：測試只檢查 LED 沒變，沒檢查 pointer。補上「之後讀回的仍是原 register」才紅。

      
11.5 那個交替讀的測試比較麻煩：真的 firmware 不會出錯，兩種推論會出錯的寫法實測也沒出錯，它從頭到尾沒紅過。沒紅過的測試，不知道它守不守得住。所以另外燒一個故意出錯的 firmware：每次送出「上一次算出來的 byte」，模擬 DR 裡留著舊 byte 的情況：


FAIL FW_MAJOR: reg 0x01 = '0xed', want 0x00
FAIL FW_MINOR: reg 0x02 = '0x00', want 0x01
...
== 25 rounds of alternating reads (0x00 0x01 0x02 0x20, LED on)
FAIL 75 of 100 reads wrong

      
每次都拿到上一個 register 的值；100 次裡剩下的 25 次「對」，是因為 0x02 之後接 0x20，兩個剛好都是 0x01。code review 後加的「LED 切換後讀回」測試在同一個變異版上也紅了（第一輪就讀到 0xED，要的是 0）。燒回正確的 firmware 之後全對。

    

  


  

    
11.8驗收實機與除錯

    

      
實測：接線、燒錄、一條拉住整條 bus 的線

上拉電阻不用另外加，Jetson 載板上已經有了。一支 header pin 只插得下一條杜邦線，pin 27 / 28 原本是 OLED 的，這一步先把 OLED 拔掉（腳本看到 0x3c 時會檢查它還在，沒看到就 SKIP）。ST-Link 第一次插 Jetson 時，USB 節點是 root:root 0664，OpenOCD 會報 LIBUSB_ERROR_ACCESS，要先裝 PlatformIO 的 udev 規則（指令在 firmware/stm32f103/README.md，要 sudo）。之後在 repo 根目錄：

第一次：0x42 不在，連板載晶片都不見了

      
燒錄成功，但掃描在 0x42 是空的，i2cget 全部 Read failed，i2ctransfer 是 Connection timed out。同一條 bus 上的板載 ina3221 也讀不到，kernel log 每 104 ms 一行（一共 764 行）：

「timeout」代表 transaction 沒辦法往前走：SCL 被誰拉住了。嫌疑最大的是 STM32 的 clock stretching，所以用 ST-Link 停住 CPU，直接讀 I2C1 的暫存器（0x40005400 起是 CR1、CR2、OAR1、OAR2、DR、SR1、SR2、CCR）和 GPIOB 的輸入暫存器 IDR（0x40010C08）：


0x40005400: 00000401 00000724 00004084 00000000 00000000 00000000 00000002 000000b4 «1»

  1. 1設定都對：CR1 = 0x401（PE、ACK）、CR2 = 0x724（36 MHz、三種中斷都開）、OAR1 = 0x4084（0x84 >> 1 = 0x42）。SR2 的 BUSY = 1，SR1 卻是 0：周邊沒有卡在任何事件上，不是 STM32 在 stretching。
    2. 
        
  2. 2bit 7（PB7，SDA）= 1，bit 6（PB6，SCL）= 0：SCL 真的是低的。
    3. 
        
  3. 3STM32 已經完全不驅動 PB6，它還是 0，Jetson 那邊也還是 timeout：拉低 SCL 的不是 STM32 的程式。
    4. 
      

      
接下來逐條拔線（從麵包板那一頭）：只要接到 B6 的那條線還連著 Jetson，那條 bus 線就是低的；線一離開 B6，bus 就恢復，ina3221 回 0x4954。結果是 B6 那一排在麵包板上接到了 GND。一條接地的線讓整條 bus 上的每一顆晶片都不能用，包括跟這一步毫無關係的板載晶片。第一次接線時 SDA / SCL 很可能也接反了：當時是拔掉 pin 27 那條線才恢復的。

      
第二次：SWD 也接不上了

      
排除短路的過程中重插過 ST-Link，Blue Pill 斷電又上電，接著 OpenOCD 就讀不到 MCU：


Info : SWD DPIDR 0x1ba01477
Error: Failed to read memory at 0xe000ed04
Error: [stm32f1x.cpu] Examination failed

      
DP 有回應（DPIDR 讀得到），記憶體卻讀不到。原因在我寫的 for (;;) __WFI();：DBGMCU_CR 的 DBG_SLEEP 是 0 時，Sleep mode 下 HCLK 會關掉（RM0008 DBGMCU_CR），除錯器經 AHB 就讀不到記憶體。之前接得上，是因為燒錄時 OpenOCD 設了 DBG_SLEEP，這個設定一直留到斷電。救法是讓 MCU 不跑這份 firmware：BOOT0 jumper 移到 1、按 RESET，CPU 從內建 bootloader 開機（OpenOCD 看到 PC = 0x1ffff1ec，在 system memory 裡），燒錄新版，BOOT0 移回 0、再按 RESET。主迴圈從此是空迴圈，並先加了一條「沒有 __WFI」的測試看它紅。

11.10收尾下一步

    

      
這一步做到了什麼

      
    
        
  • Blue Pill 在 Jetson 的 i2c-1 上以 0x42 回應：DEVICE_ID、版本、LED_CONTROL，不合法的存取有明確定義。
    • 
        
  • phase05 的驗收條件成立：Jetson userspace 讀得到 Device ID 與版本，寫 LED_CONTROL 讓 LED 亮、滅。驗收 0 failure。
    • 
        
  • protocol 和硬體分開：i2c_target.c 在 Jetson 上跑 11 組向量，main.c 只翻譯 I2C1 的旗標。
    • 
        
  • 測試：11 組 C++ 向量、29 個 Python 測試；故意出錯的 firmware 證明交替讀、LED 切換後讀回兩條測試抓得到舊 byte。
    • 
        
  • 沒有實測：OLED 同時在 bus 上、reset 後的預設值、400 kHz、長時間存取。規模：非空白 796 行（不含 vendor 檔），含 code review 的修正。
    • 
      

      
Step 12 把這四個 register 擴充成正式的 register map：分區（識別 / 輸入 / 輸出 / 健康狀態）、ADC 這種超過 1 byte 的值（要定義 auto-increment 與 byte 順序）、STATUS register 回報不合法的寫入，以及 protocol 版本規則。那時候「預先放好的 byte」就不再無害：多讀一個 byte 會讓 pointer 多前進一格，要重新驗證。

      
1. 為什麼讀 register 要先「寫」一個 byte？
I2C 只有「寫一串 byte」與「讀一串 byte」。target 要知道該回哪個 register，controller 只能先寫一個 byte 當 pointer，再用 repeated START 改成讀。這個「第一個 byte 是 pointer」是我們自己的 protocol 規定的，I2C 本身沒有。

      
2. LED_CONTROL 寫 2，Jetson 怎麼知道失敗了？
bus 上看不出來：F103 收到 byte 時硬體就自動回 ACK 了。只能讀回 LED_CONTROL，發現還是原來的值。Step 12 會加 STATUS register 直接回報。

      
3. 只在 STOPF 時呼叫 i2c_target_stop()，會出什麼事？
寫入沒事，但讀取以 controller 的 NACK 結束，target 收到的是錯誤中斷裡的 AF，不是 STOPF。不處理 AF 的話旗標清不掉，錯誤中斷會一直進來；狀態也回不到 IDLE。

      
4. 整條 bus 都 timeout，怎麼判斷是不是 STM32 在拉住 SCL？
用 SWD 停住 CPU，讀 I2C1 的 SR1 / SR2：SR1 是 0 就表示周邊沒卡在任何事件上。再關掉 I2C1、把 PB6 改成輸入，讀 GPIOB 的 IDR：還是 0，就是外部拉低的。這一章的答案是麵包板上一條接到 GND 的線。

      
把 PB7（SDA）誤設成 GPIO_Mode_AF_PP（推挽）會怎樣？4 個 bit 會變成多少？
4 個 bit 從 0xF 變成 0xB（CNF 10、MODE 11）。推挽會主動把線推到 3.3 V；Jetson 要把 SDA 拉低（ACK、資料 0）時，兩邊一個推高、一個拉低，等於短路，訊號也錯。I2C 的線一律用開汲極，高電位交給上拉電阻。
