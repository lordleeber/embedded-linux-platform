ioctl：給 edge_test 一條控制通道

read()/write() 搬的是資料；要「設定一個值」或「問現在的狀態」，該走的是 ioctl()。這一步在 edge_test 裡加一個 32-bit 的 value，用兩個 ioctl 命令讀寫它，並寫第一支 C++ userspace 程式來控制它。重點是那個 32-bit 的命令號碼：它是 kernel 和 userspace 之間的 ABI，一旦發佈就不能改。

3.1起點為什麼

資料通道和控制通道要分開

Step 2 的 /dev/edge_test 只有一條路：寫進去的 bytes 就是資料。如果想「把某個設定改成 123」，最直覺的做法是寫一串文字 SET 123 進去，但這樣 driver 就得自己解析文字，資料和命令也混在同一條流裡——寫入的內容剛好長得像命令時，就分不清了。

ioctl() 是 Linux 給「控制」用的專用入口：每個命令有一個號碼，參數是一個固定格式的結構，不必解析文字。之後接上 GPIO、INA219、STM32 時，「設定取樣頻率」「讀狀態暫存器」這類操作，都會走這條路。

互動雙方：C++ 程式 edge_test_cli 呼叫 ioctl()，經過 system call 和 VFS，進到 edge_test.ko 的 edge_test_ioctl()；仍然沒有外接硬體，也沒有 bus 上的 controller / target。這一步不做：GPIO / I2C、複雜的 binary protocol。

ioctl
「input/output control」。對一個已開啟的檔案送一個命令號碼加一個參數，ioctl(fd, cmd, arg)；參數通常是一個指向 struct 或整數的指標。
ABI
Application Binary Interface：編譯好的程式和 kernel 之間，在「位元層級」上的約定，例如命令號碼的數值、參數的大小與排列。改了 ABI，已經編好的舊程式就會出錯，即使原始碼看起來一樣。
CMake
產生建置檔的工具。cmake -S . -B build 讀 CMakeLists.txt 在 build/ 產生 Makefile，cmake --build build 再實際編譯。
3.2路徑user → kernel

一次 edge_test_cli set 123 往下走了幾層

和 Step 2 的 write() 是同一條路，只是最後 VFS 呼叫的是表裡的 .unlocked_ioctl，而不是 .write。

命令號碼定義在一份 kernel 和 userspace 共用的 header 裡。共用很重要：兩邊只要對號碼的理解差一個 bit，命令就會落進 default。

header 只 include <linux/ioctl.h> 與 <linux/types.h>，這兩份在 kernel 內和 userspace 都存在，所以同一個檔案兩邊都能用；參數型別用 __u32（userspace 也看得到的固定 32-bit 型別），不用 unsigned long 這種在 32-bit 和 64-bit 程式裡大小不同的型別。測試裡有一條專門檢查這件事。

3.3號碼_IOR · _IOW

一個 ioctl 號碼裡裝了什麼

_IOR、_IOW 不是函式，是把四個欄位拼成一個 32-bit 數字的巨集。這台（arm64，用 asm-generic 的定義）的配置是：方向 2 bits、參數大小 14 bits、magic（type）8 bits、序號（nr）8 bits。

magic 為什麼不能隨便挑

如果兩個 driver 用了同一個 magic 和 nr，對錯的裝置送命令時，對方可能把它當成自己的命令執行，而不是回 ENOTTY。所以 kernel 文件 Documentation/userspace-api/ioctl/ioctl-number.rst 維護一份已佔用 magic 的登記表。這次的選號過程：

  • 第一個想到的 'E'（edge）在這台的 uapi headers 裡已經被 evdev 等用了 36 次，直接排除。
  • L4T 的 kernel headers 套件沒附那份登記表，所以先搜尋本機所有 uapi header 裡的 _IO* 定義與 magic 常數，0xEB 一次都沒出現；再對照上游 v5.15 的登記表，也沒有 0xEB。

號碼一旦發佈就是 ABI：之後新增命令只能往後加 nr，不能改既有命令的號碼或參數大小。測試裡用 static_assert 把兩個數值釘死，數字是照位元格式手算的，不是從實作抄的：

3.4driverunlocked_ioctl

kernel 端：一個 switch

  • 不認得的命令一律回 -ENOTTY（第 130–131 行）。這是 ioctl 的慣例錯誤碼，意思是「這個檔案不支援這個命令」；不要回 -EINVAL，那留給「命令認得、但參數值不對」。
  • get_user() / put_user() 是搬單一個整數用的 copy_from_user() / copy_to_user()，同樣會檢查位址、碰到壞指標回 -EFAULT。NULL 也算壞指標。
  • 先讀進區域變數，成功才改狀態（第 124–125 行）：Step 2 的 copy_from_user() 坑換了個樣子出現，SET 給了壞指標時 value 必須不變——測試「failed SET leaves the value unchanged」守著這件事。
  • 讀寫 edge_test_value 都在 Step 2 那把 edge_test_lock 底下；但 put_user() 在鎖外，因為它可能因 page fault 睡眠，沒必要讓別人等。

第 141 行把 handler 掛上去。第 142 行的 compat_ioctl 給 32-bit 程式用：64-bit kernel 上跑的 32-bit 程式，指標只有 32 位元，compat_ptr_ioctl 把它轉成 kernel 的指標後，呼叫同一個 edge_test_ioctl()。能這樣共用，前提就是參數只用固定大小的 __u32，兩種程式看到的號碼和排列完全一樣。這台的 kernel 有開 CONFIG_COMPAT=y，但沒有 32-bit 的編譯器，這條路徑沒有實測。

kernel module 不會自動去 repo 的 include/ 找 header，第 5 行用 ccflags-y 把它加進搜尋路徑；$(src) 是 kbuild 提供的「這個 module 的原始碼目錄」。

踩過或差點踩的坑

症狀
選了 'E'，本機 headers 裡早已出現 36 次。
後果
命令送錯裝置時，對方可能照自己的意思執行。
正解
搜尋本機 uapi headers，再對照上游的 ioctl-number.rst（3.3 節）。

以為號碼只看 magic 和 nr

_IOR(0xEB, 1, __u64) 回 ENOTTY。

3.10收尾step 3 → 4

這一步做到了什麼

  • C++ 程式能透過 ioctl() 讀寫 driver 的狀態，一般使用者也能用。
  • 未知命令回 ENOTTY、NULL / 壞指標回 EFAULT 且不改狀態、reload 後 value 歸零，三輪驗收都通過。
  • 命令號碼用固定大小型別，並以 static_assert 釘住 ABI。
  • Step 2 的資料通道沒有退化。
  • 沒有實測：32-bit 程式走 compat_ptr_ioctl 的路徑；4 個 ENOTTY／不動 buffer 的守門測試沒有紅過。

到這裡，edge_test 還是一個純軟體的裝置。Step 4 開始接上真正的硬體：GPIO 與 LED，同樣用 character device 當入口，並換成 platform driver 加 Device Tree 的寫法。

1. 為什麼「設定一個值」該用 ioctl，而不是往 /dev/edge_test 寫一串 SET 123？

寫入的是資料通道，driver 得自己解析文字，資料和命令也會混在一起；ioctl 用號碼區分命令、參數格式固定，不需要解析。

2. EDGE_TEST_GET_VALUE 為什麼是 _IOR 而不是 _IOW？

方向是從 userspace 的角度看：GET 要把 kernel 的值讀回 userspace，所以是 READ。

3. 把參數型別從 __u32 改成 __u64，舊程式會發生什麼事？

參數大小被編在號碼裡，新號碼和舊程式送來的號碼不同，舊程式的呼叫會落進 default 拿到 ENOTTY。這就是 ABI 被打破。

4. 為什麼那 4 個「預期 ENOTTY／不動 buffer」的測試，對 Step 2 的 module 也會 PASS？

Step 2 的 module 沒有 unlocked_ioctl，VFS 對任何 ioctl 都回 ENOTTY，也不會動到 buffer。所以它們沒有真正紅過，只能算守門測試。
