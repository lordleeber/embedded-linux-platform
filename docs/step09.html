OLED：先在 userspace 點亮 EDGE

Phase 3 的 INA219 是「讀 sensor」，這一步換成「控制 peripheral」：一片 128x64 的 OLED，控制器是 SSD1306。和 6-b 一樣，寫 driver 之前先用 userspace 工具證明三件事：晶片在哪條 bus、哪個位址，送過去的 byte 該長什麼樣，以及每次執行都從頭初始化，不靠上一次留下的狀態。這片螢幕不能讀回內容，所以畫面對不對最後要靠人眼確認，每張測試圖都特別設計成「一眼看得出方向對不對」。

9.1起點為什麼

寫 driver 之前，先知道該送什麼 byte

直接寫 kernel driver 也能點亮螢幕，但出問題時不知道是哪一層錯了：是位址不對、初始化少了一個指令、像素的排列方式誤會了，還是 driver 本身的 bug？每改一次就要 rmmod、insmod。userspace 工具改完重編只要一秒，錯了也不會讓 kernel 出事。所以 phase04 先安排這一步，等協定確定了，Step 10-a 再把同一串 byte 搬進 driver。

互動雙方：controller（master）是 Jetson 的 c240000.i2c（Linux 叫它 i2c-1，接 40-pin header 的 pin 27 SDA、pin 28 SCL），target（slave）是 OLED 模組上的 SSD1306，位址 0x3C。資料只有一個方向：Jetson 寫、OLED 收。這一步不做：kernel driver（Step 10-a）、完整字型與文字排版（Step 10-b，這裡只有畫 EDGE 需要的 D、E、G 三個字）、顯示 INA219 的數值（Step 10-c）。

SSD1306
OLED 控制器晶片。它內建一塊顯示記憶體，畫面就是這塊記憶體的內容；Jetson 透過 I2C 寫記憶體與設定。
GDDRAM
Graphic Display Data RAM，就是上面那塊顯示記憶體：128 × 64 個點，一個 bit 一個點，共 1024 byte。
page
GDDRAM 按水平條分成 8 個 page，每條 8 列高。一個 byte 是某個 page 裡某一欄直的 8 個點（9.5）。
control byte
每個 I2C 寫入的第一個 byte，告訴晶片後面是 command（設定）還是 data（像素）。
charge pump
晶片內部的升壓電路。OLED 面板要比 3.3 V 高的電壓，模組只給 3.3 V 時要靠它產生；初始化時得自己打開。
power-on reset
晶片剛上電時的狀態，所有設定回到 datasheet 規定的預設值，其中一項是 display OFF（螢幕不亮）。9.8 用它判斷晶片有沒有真的斷過電。
i2c-dev
讓 userspace 直接操作 I2C bus 的 kernel 模組，提供 /dev/i2c-N。6-b 的 ina219_raw 用的就是它。

接線

OLED 腳位Jetson 40-pin header
VCCpin 17（3.3 V）
GNDpin 20
SDApin 27（i2c-1 = c240000.i2c）
SCLpin 28

為什麼不用 Phase 3 的 pin 3/5（i2c-7）？那兩支 pin 已經插著 UPS 模組的線，要並聯得另外分接。pin 27/28 空著，而這條 bus 上本來就有兩顆板載晶片（0x25、0x40），和 OLED 的 0x3C 不衝突。這兩組 I2C pin 都直接接 SoC，不經 4-a 遇過的 TXB0108 電平轉換。

9.2全景一張畫面的旅程

oled_probe edge：11 個 I2C 寫入

這和 6-b 的 ina219_raw 走同一條路（i2c-dev + I2C_RDWR），方向相反：ina219_raw 每次是「寫 1 byte pointer + 讀 2 byte」，oled_probe 只有寫。

9.3格式control byte

同一條線上，怎麼分辨「設定」和「像素」

SSD1306 的 I2C 介面沒有 register 位址可指，每個寫入的第一個 byte 是 control byte，由它決定後面整串的解讀方式：

  • bit 7 Co（continuation）= 0：後面全部是同一種東西，一路串到 STOP。Co = 1 的寫法是「一個 control byte 配一個 byte」，每個 command 前面都要再放一次 control byte，這個工具不用。
  • bit 6 D/C#：0 是 command、1 是 data。所以 0x00 = 一串 command、0x40 = 一串像素。

把 ASCII "EDGE"（45 44 47 45）直接寫過去不會出現文字。放在 0x00 後面，晶片會把它們當成 command；放在 0x40 後面，就是四欄各 8 個點的亂碼。SSD1306 不認得字，文字得先在 Jetson 這邊畫成點（9.6）。

9.4初始化25 個 command

每次都送完整的初始化

幾個沒寫就會出事的設定（出處 SSD1306 datasheet 的 command table；表的左欄是「沒寫或寫錯會怎樣」，除了「打亂測試」那三項有實機驗過，其餘是照 datasheet 推論）：

沒寫 / 寫錯指令與原因
全部 ACK，螢幕全黑8D 14：charge pump 沒開，面板沒有高壓。或最後沒送 AF。
畫面左右鏡像A1：column 127 對到 SEG0。這片模組要這樣設，方向才對（實機確認）；不寫就是鏡像。
畫面上下顛倒C8：COM 反向掃描，page 0 在最上面。
畫面錯位、從中間開始20 00：上一個程式可能留在 vertical addressing（9.8 的打亂測試故意這樣做）。
反白、很暗A6、81 CF：同上，上一個程式可能留下反白與 contrast 0。
隔一行才有點A8 3F、DA 12：128x64 和 128x32 的值不同，這裡固定 128x64。

AF（Display ON）不在這串裡。上電後 GDDRAM 的內容是隨機的，如果初始化完就開顯示，會先閃一下雜點，再被新畫面蓋掉。所以順序是 init → 寫整張畫面 → AF（9.7 的 main()）。靜態測試 test_every_drawing_mode_inits_first 確認原始碼裡這三者的順序。

9.6文字5x7 glyph

    

      
EDGE 是畫出來的

      
字型表用的是流傳很廣的 5x7 點陣：每個字 5 欄，一欄一個 byte，bit 0 在上。這和 GDDRAM 的 byte 方向一樣，所以 scale 1 時字型的 byte 可以原封不動放進 page 0（向量 test_text_at_scale_1_lands_in_page_0 就是在比對這件事）。這一步只收 EDGE 用得到的 D、E、G 和空白，完整字型是 Step 10-b 的事。

      
      
    
        
  • 先檢查、後畫：遇到不支援的字元回 false，而且什麼都沒畫，不會留下半個字串。
    • 
        
  • 字距 6 × scale：5 欄字加 1 欄空白。scale 4 時 EDGE 寬 (4 × 6 − 1) × 4 = 92 點、高 28 點，draw() 把它放在 (18, 18)，正好置中。
    • 
        
  • 放大後一個字跨兩個 page：28 點高，從 y = 18 到 45，橫跨 page 2 到 5。set_pixel() 逐點處理，所以畫的時候不用管 page 邊界。

9.7送出I2C_RDWR

    

      
window 指令 + 8 個 page

      
      
21 設 column 範圍、22 設 page 範圍。SSD1306 內部有一個「下一個 byte 寫到哪」的位址指標，寫入時自動前進，在 horizontal addressing 下寫滿 page 的 128 欄就換下一個 page。上一個程式寫到一半結束時，指標就停在那裡；不先送 window 指令，這次的畫面會從那裡開始寫，整片錯位。變異測試把這行拿掉，向量會紅。

      
一個 page 一個訊息（1 + 128 = 129 byte）。i2c-dev 允許一個 I2C_RDWR 訊息最長 8192 byte，整張 1024 byte 一次送也可以，分成 8 個是為了錯誤訊息能指出「第幾個訊息」失敗。SMBus 的 block write 一次只能 32 byte，所以這裡不用 SMBus API。

      
      
不用 I2C_SLAVE 有一個副作用要記住。Step 7 踩過：位址被 kernel driver 綁定後，I2C_SLAVE 會回 EBUSY，這是 kernel 的保護；I2C_RDWR 不做這個檢查。所以 Step 10-a 的 driver 綁定 0x3C 之後，這個工具照樣寫得進去，會在 driver 底下重新 init 控制器、蓋掉 driver 的狀態。code review 指出了這點，已排進 Step 10-a：工具要先看 0x3C 有沒有被 driver 綁定，有的話就拒絕，除非加 --force。

      
      
沒有 ACK 時，i2c-tegra 回 EREMOTEIO，strerror 印成 Remote I/O error，和 6-b 一樣。錯在第 1 個訊息就代表位址根本沒人回應。

    

  


  

    
9.8狀態不靠上一次

    

      
證明它不依賴「剛好留下的狀態」

      
phase04 對這一步只有一條硬性驗證：斷電再上電後，程式仍能重新初始化 OLED。換句話說，不能因為上一次已經設定好了，這次才剛好正常。驗收腳本用兩種方式驗。

      
用另一支工具把晶片弄亂

      
      
w9@0x3c 是「對 0x3C 寫 9 byte」，第一個 0x00 就是 control byte。用 i2ctransfer 而不是 oled_probe 自己來弄亂，是為了讓「弄亂」和「修復」來自不同的程式：如果兩者共用同一份 byte 表，表裡漏了某項設定，兩邊會一起漏掉，測試就看不出來。弄亂後先問人畫面有沒有真的變（反白、鏡像、變暗），再跑 edge，畫面要和之前完全一樣。先問「變了沒」是 code review 補的：i2ctransfer 收到 ACK 只代表 byte 送到了，如果弄亂其實沒生效，「看起來和之前一樣」就什麼也證明不了。這和「只拔 VCC」是同一類錯誤：只驗了「修好了」，沒先確認「真的壞過」。

      
斷電：四條線全拔

      
      
第一版腳本只叫人拔 VCC，並期望工具回 Remote I/O error。實測工具結束碼 0，每個 byte 都有 ACK，使用者看到螢幕變暗但 EDGE 還在。最可能的原因是 SDA、SCL 上的 pull-up 電流經晶片腳位的 ESD 保護二極體流進 VDD，晶片的邏輯部分靠這點電繼續運作（推論，沒有量電壓）。所以「拔 VCC」根本不算斷電，之後 EDGE 又出現，也證明不了重新初始化。

      
修正後的腳本有兩個改變：

      
    
        
  1. 四條線全拔，這時工具一定要 Remote I/O error。
    2. 
        
  2. 接回後先不送任何指令，問人「螢幕是不是全黑」。power-on reset 的狀態是 display OFF，晶片如果真的斷過電，接回後一定是黑的；還看得到 EDGE，就代表它沒斷過電。這個判準不靠「我拔了線所以一定斷電」的假設，而是讓晶片自己證明。
    3. 
      

      
接回時先接 GND：先接訊號線或 VCC 的話，電流可能找不到正常的地回路，從別的腳位繞（一般的熱插拔習慣，這次沒有試反過來的順序）。

  3. 3問題故意問方向：從左上角往右下。鏡像時對角線會從右上角出發，顛倒時從左下角出發（9.5 的模擬器可以看）。
    4. 
        
  4. 4硬體測試 3 個在這裡跑：每個模式結束碼 0、edge 連跑 50 次都成功。
    5. 
        
  5. 5打亂後畫面完全恢復：init 寫回了反白、兩個方向、addressing mode、contrast，沒有漏掉任何一項。
    6. 
        
  6. 6真的拔掉後是第 1 個訊息就沒有 ACK，和 0x3D 的錯誤一樣。第一輪只拔 VCC 時這裡是結束碼 0（9.8）。
    7. 
        
  7. 7接回後螢幕全黑：這是 power-on reset 的 display OFF，證明晶片確實斷過電。
    8. 
        
  8. 8從 reset 狀態重新初始化成功，phase04 的驗收條件「穩定顯示 EDGE，斷電後仍可重新初始化」成立。
    9. 
      

      
你的輸出會在 y/n 的答案上不同（那是你看到的東西），其餘應該一樣。如果 OLED 接在別的 bus，加 --bus N；是 0x3D 的模組，加 --addr 0x3d，「absent address」那項會改測 0x3C。不方便拔線時加 --no-power-cycle，最後一段會整個跳過，這時「斷電後重新初始化」就沒有驗到。

      
沒有實測：熱插拔 OLED 時，同一條 bus 上的 ina3221、fusb301 有沒有記到 I2C 錯誤（要 root 看 dmesg，這次沒看）；128x32 的面板（手上沒有）；長時間顯示的穩定性（只連跑了 50 次）。

    

  


  

    
9.11常見錯誤

    

      
踩過的坑

      

        
以為拔 VCC 就是斷電
症狀
拔掉 VCC 後，工具結束碼 0、全部 ACK，螢幕變暗但 EDGE 還在。
後果
晶片經 SDA/SCL 仍然有電（推論），插回後 EDGE「又出現」什麼也證明不了。
正解
四條線全拔；接回後送任何指令前，先確認螢幕全黑（power-on reset）。

        
以為結束碼 0 就代表畫面對
症狀
工具全部成功，螢幕卻可能是鏡像、顛倒或全黑。
後果
SSD1306 在 I2C 下不能讀回 GDDRAM，程式只知道 ACK。
正解
畫有方向的圖（左上角起的對角線、四角的點），由人回答方向對不對。

        
以為 pin 3/5 最順手
症狀
INA219 已經在 i2c-7，想把 OLED 也接上去。
後果
pin 3/5 插著 UPS 的線，要並聯得分接；而且 Step 10-a 的 DT 節點會以為能沿用 &hdr40_i2c1。
正解
接 pin 27/28（c240000.i2c），10-a 的節點要掛在 i2c@c240000。

        
用 grep 在 i2cdetect 輸出裡找位址
症狀
grep -w 30 找 0x30，bus 上明明沒東西也判定有回應。
後果
比對到的是列標籤 30:；位址是 0x10 的倍數時，斷電檢查永遠過（code review 找到，已重現）。
正解
跳過標題列和每列第一欄，只比對格子裡的值。

        
以為 ASCII 寫過去就有字
症狀
想 echo EDGE 到 bus 上。
後果
在 0x00 後面是一串 command，在 0x40 後面是四欄亂點（照協定推論，沒有實機試）。
正解
先用字型表在 framebuffer 畫成點，再用 0x40 送。

        
拿同一份 byte 表去打亂再修復
症狀
用 oled_probe 自己的設定來製造「壞狀態」。
後果
表裡漏的設定，兩邊都會漏，測試看不出來。
正解
用獨立的 i2ctransfer 寫入反白、鏡像、vertical addressing、contrast 0。

      

    

  


  

    
9.12收尾9 → 10-a

    

      
這一步做到了什麼

      
    
        
  • OLED 接上 i2c-1（pin 17/20/27/28），0x3C 回應；build/oled_probe 以 i2c-dev 的 I2C_RDWR 只寫不讀，每次送完整 init → window → 8 page → Display ON。
    • 
        
  • 人眼確認 clear、pixel、pattern、edge 四種畫面方向正確；edge 連跑 50 次都成功。
    • 
        
  • 不依賴前一次狀態：i2ctransfer 打亂後恢復；四條線全拔再接上，先看到 power-on reset 的全黑，再重新顯示 EDGE。驗收 0 failure。
    • 
        
  • 測試：協定向量 9 組（6 種改法都會紅）、25 個 Python 測試（3 個要接 OLED）。
    • 
        
  • 沒有實測：熱插拔時同 bus 其他晶片的錯誤、128x32 面板、長時間顯示；硬體測試沒看過紅燈。
    • 
      

      
Step 10-a 把同一串 byte 搬進 kernel：一個 I2C client driver 在 probe 時初始化、持有一份 1024 byte 的 framebuffer，提供最小的 userspace 介面（clear、fill、寫整張 raw framebuffer）。ssd1306.h 是 C++，driver 要用 C 重寫；這一章的向量和畫面就是它的對照組，同一張 pattern 由 driver 畫出來必須長得一樣。

      
1. 想在 (10, 20) 點亮一個點，要改 GDDRAM 的哪個 byte、哪個 bit？
page = 20 / 8 = 2，byte 索引 2 × 128 + 10 = 266，bit 20 % 8 = 4。也就是 frame[266] |= 0x10。

      
2. 為什麼 0xAF（Display ON）不放在 init_sequence() 裡？
上電後 GDDRAM 是隨機內容。init 完就開顯示，會先閃一下雜點；先寫好整張畫面再送 AF，第一眼看到的就是正確畫面。

      
3. 斷電測試裡，為什麼「接回後螢幕全黑」比「接回後 EDGE 能再出現」更重要？
EDGE 再出現只說明工具能畫；如果晶片根本沒斷電（只拔 VCC 時就是這樣），它本來就設定好了，畫得出來不代表能從 reset 狀態初始化。全黑是 power-on reset 的 display OFF，證明晶片真的回到了初始狀態，接下來的成功才有意義。

      
4. 每個訊息第一個 byte 是 0x00 或 0x40，它們各代表什麼？為什麼 "EDGE" 的 ASCII 不能直接送？
0x00：後面是一串 command；0x40：後面是一串 GDDRAM 像素。SSD1306 沒有字型，ASCII 送過去不是被當成 command 就是被當成 8 個點一欄的像素，文字必須先在 Jetson 端畫成點。
