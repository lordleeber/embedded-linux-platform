STEP 2 · PHASE 1

最小 character device：/dev/edge_test

寫第一個 kernel module。它在 /dev 底下長出一個裝置節點，背後是一塊 256 bytes 的 kernel buffer：echo 寫進去、cat 讀出來。這一章要看懂的是：userspace 一個普通的 write()，怎麼一路走進你自己寫的 kernel function。

一句話

character device 就是 kernel 借用「檔案」這個介面：userspace 照常 open/read/write，VFS 依裝置號碼把呼叫轉給 driver 登記的 file_operations。

這一章的互動雙方

  • 呼叫端：userspace 程式（echo、cat、Python 測試）。被呼叫端：edge_test.ko。中間經過 system call 和 VFS。
  • 沒有外接硬體，也沒有 bus 上的 controller / target——資料只在 userspace 記憶體和 kernel 記憶體之間搬。
  • 這一步不做：ioctl（Step 3）、interrupt、任何真實硬體控制。

.ko / insmod / rmmod

.ko（kernel object）是編好的 kernel module，相當於可以在系統執行中插進 kernel 的一段程式。insmod edge_test.ko 載入它並呼叫它的初始化函式；rmmod edge_test 呼叫它的結束函式後卸載。兩者都要 root。

VFS

Virtual File System：kernel 裡處理所有「檔案」操作的那一層。不管背後是 ext4 的檔案、pipe 還是裝置，read()/write() 都先到 VFS，再由它轉給真正負責的程式碼。

file_operations

一個裝滿函式指標的 struct：「有人對這個檔案 open / read / write 時，請呼叫這些函式」。driver 填好一張，登記給 kernel。

devtmpfs / uevent / udev

devtmpfs 是掛在 /dev 的記憶體檔案系統，kernel 每登記一個裝置就在裡面建節點。同時 kernel 送出 uevent（「有新裝置」的通知），userspace 的 udev 收到後可依規則（udev rule）再調整權限、群組或建立別名。

class 與 /sys/class

class 是 kernel 的裝置分類（例如 tty、input），會出現在 /sys/class/<名稱>/。device_create() 要掛在某個 class 底下，devtmpfs 才會替它建 /dev 節點。

dmesg 與 Oops

dmesg 印出 kernel 的 log；module 裡的 pr_info() 就寫到這裡。Oops / BUG / WARNING 是 kernel 偵測到自己出錯時印的訊息，driver 寫壞了常會在這裡看到。

2.1　為什麼需要這一步

後面每一個 driver——GPIO、INA219、OLED、STM32 的 SPI 通道——最後都要給 userspace 一個入口。最原始、也最直接的入口就是 /dev 底下的 character device。先用一個完全不碰硬體的 driver 把這條路走通，之後換成真的硬體時，出問題就能分得清是「入口沒接好」還是「硬體沒回應」。

這一步同時收掉 Step 1 留下的一個未驗證項目：Step 1 只確認了 /lib/modules/$(uname -r)/build 目錄存在。這次真的用它編出 module 並載入成功，才算證明 headers 和正在跑的 kernel 對得上。

先看 module 怎麼編出來。kernel module 不是用一般的 gcc 指令編，而是交給 kernel 自己的建置系統（kbuild）：

obj-m := edge_test.o 告訴 kbuild「把 edge_test.c 編成 module」。第 9 行切換到 KDIR（Step 1 檢查過的 headers 目錄）去執行它的 Makefile，再用 M= 指回這個目錄。編譯輸出裡的 CC [M]、LD [M] 就是「編譯 / 連結一個 module 檔」。load.sh 與 unload.sh 各只有一行實際動作：insmod 這個目錄下的 edge_test.ko、rmmod edge_test。

kernel 怎麼知道載入時要呼叫哪個函式？靠檔尾這兩行：

module_init() / module_exit() 把函式登記成 insmod / rmmod 時的進入點。__init 標記的函式只在載入時用一次，之後那段記憶體可以回收；__exit 同理是卸載專用。初始化函式回傳 0 代表成功，回傳負的錯誤碼則 insmod 失敗、module 不會留下來。

kernel 慣例裡，函式失敗時回傳負的 errno（例如 -ENOMEM），成功回 0。回傳 pointer 的函式則把錯誤碼塞進 pointer 本身：IS_ERR(p) 判斷它是不是錯誤，PTR_ERR(p) 取出錯誤碼。所以這裡不是檢查 NULL。

  • 動態號碼：alloc_chrdev_region() 讓 kernel 挑一個沒人用的 major，不用自己猜一個號碼去撞別人。代價是號碼每台機器、每次開機可能不同，所以驗收腳本不寫死 major，而是比對 /proc/devices 和節點兩邊是否一致。
  • 節點不用自己 mknod：device_create() 會送出 uevent，devtmpfs 立刻建出 /dev/edge_test。很多舊教學要你手動 mknod，那是因為它們沒建 class/device。
  • goto 反向拆除：每一步失敗都跳到「拆掉前面已建好的東西」的標籤，順序剛好和建立相反。edge_test_exit() 也是同一個順序。少拆一步的後果是殘留：下次 insmod 可能因為名字已存在而失敗（這一點是推論，本 step 沒有刻意製造 init 失敗去驗證）。

2.4　write()：截斷、ENOSPC，以及 copy_from_user() 的陷阱

ubuf 帶著 __user 標記：它是 userspace 的位址，kernel 不能直接 dereference——那個位址可能根本沒對應到記憶體，也可能是惡意指向 kernel 的位址。copy_from_user() 會檢查位址範圍，碰到 page fault 也能安全收場，回傳「沒複製成功的 byte 數」（0 代表全部成功）。

回傳值的規則：成功回寫入的 byte 數，失敗回負的 errno。syscall 那一層會把負值轉成 userspace 熟悉的形式：write() 回 -1，errno 設成對應的正值（ENOSPC、EFAULT）。容量處理沿用一般檔案的語意：

  • 寫 300 bytes 到空的 buffer：第 84 行把 count 截成 256，回傳 256。這叫 short write，呼叫端要自己處理「只寫了一部分」。
  • 像 head 這種會把資料寫完的程式，收到 short write 後會把剩下的 44 bytes 再送一次。這時 *ppos 已經是 256，第 80–82 行回 -ENOSPC，head 就印出 head: write error: No space left on device（2.7 節有實測）。

真的踩到的坑：失敗的寫入把資料清成 0

第一版第 90 行是 copy_from_user(edge_test_buf + *ppos, ubuf, count)，直接以 kernel buffer 當目的地。測試 test_bad_user_pointer_returns_efault_and_keeps_buffer 先寫入 safe，再透過 Python 的 ctypes 直接呼叫 libc 的 write()，傳入位址 1 這個無效 pointer，預期回 EFAULT、內容不變。實機跑出來是這樣：

EFAULT 有正確回傳，但 safe 變成了四個 \0。原因在 kernel headers 裡：

複製失敗時，沒複製到的那段目的端會被清成 0。這是刻意的安全設計：避免呼叫端拿到一段半初始化、含有舊 kernel 資料的 buffer。但它代表「目的端」不能是你還想保留的狀態。修法是第 73、90、94 行：先複製到 stack 上的 tmp，成功才 memcpy 進 edge_test_buf。修完後同一支測試通過。

為什麼要在意 256 bytes？kernel 裡每個執行緒的 stack 是固定大小、不會自動長大，和 userspace 動輒 8 MB 的 stack 不同，用太多會直接把 kernel 弄壞。這顆 kernel 是 16 KiB（arch/arm64/include/asm/memory.h 的 MIN_THREAD_SHIFT = 14）；kbuild 對單一函式超過 CONFIG_FRAME_WARN = 2048 bytes 的 stack 用量會發出警告，這次編譯沒有。兩個值都可以在 headers 裡查：grep CONFIG_FRAME_WARN /lib/modules/$(uname -r)/build/.config。之後若 buffer 變成數 KB，就要改用 kmalloc（kernel 版的 malloc）配一塊暫存區。

2.5　read() 與 open()：讓它像一個小檔案

*ppos 是這個 open 的讀寫位置，每個 open() 各有一份（存在 struct file 的 f_pos），VFS 把它的位址傳進來，driver 只要更新 *ppos。cat 會一直 read() 到回傳 0 為止，所以第 54–55 行的 EOF 一定要有；如果每次都從頭回傳內容，cat 就會無限迴圈印出 hello。

inode 代表檔案本身（這裡就是 /dev/edge_test 節點），file 代表「這一次 open」。這個 driver 只有一個裝置，用不到 inode。f_mode 是 kernel 整理過的讀寫權限（FMODE_WRITE），f_flags 是 userspace 傳給 open() 的原始旗標（O_TRUNC 只在這裡看得到）。pr_debug() 在這顆 kernel 不會印出任何東西：它沒開 CONFIG_DYNAMIC_DEBUG，pr_debug 只有在編譯時定義 DEBUG 才會生效。

shell 的 > 是用 O_WRONLY | O_CREAT | O_TRUNC 開檔。對一般檔案，O_TRUNC 由檔案系統處理；對 character device，VFS 不會幫你清，O_TRUNC 只是一個旗標，driver 要自己決定它的意義。這裡選擇「清空」，所以先 echo hello world 再 echo hi，讀到的是 hi。如果不處理，舊內容不會被清掉，讀到的會是 hi\nlo world\n：新寫的 3 bytes 蓋在前面，後面還接著舊資料。

所有存取 edge_test_buf 和 edge_test_data_len 的地方都在 edge_test_lock 這個 mutex 底下。兩個程式同時寫入時，不會讀到「長度更新了、內容還沒寫完」的狀態。kernel 有兩種常見的鎖：mutex 拿不到時讓執行緒去睡、讓出 CPU，跟 pthread mutex 類似；spinlock 拿不到時原地空轉，持有期間不准睡。copy_from_user() 碰到還沒載入記憶體的 user page 時會觸發 page fault，等 kernel 把資料讀進來，這段等待就是「睡眠」。所以持鎖期間會呼叫它的地方只能用 mutex。

2.6　權限：為什麼一般使用者也能 echo

devtmpfs 建出來的節點預設是 root 所有、權限 0600，一般使用者 echo 會得到 Permission denied。第 138 行（2.3 節的 init 節錄）把這個 callback 掛到 class 上，節點建立時就是 0666。回傳 NULL 表示節點名稱不改，沿用 device_create() 給的 edge_test。這在學習用的 buffer 裝置上是方便；控制真實硬體的節點不要開成 0666，那種情況應該用 udev rule 指定 group。

2.9　常見錯誤

以為 copy_from_user 失敗不動目的端

症狀
write() 回 EFAULT，但原本存的資料變成 \0。
後果
一次錯誤的呼叫就毀掉裝置狀態；之後的 driver 若直接 copy 進共用結構，同樣會中。
正解
先 copy 到暫存區，成功才寫入真正的狀態（2.4 節）。

read 不回 EOF

症狀
cat /dev/edge_test 一直印、不會結束。
後果
所有「讀到結尾」的工具都卡住。
正解
依 *ppos 判斷已讀完就回 0，並更新 *ppos（2.5 節）。這條是推論，本 step 沒有實際做出這個錯誤版本。

用 sudo make

症狀
之後一般使用者 make / make clean 出現 Permission denied。
後果
tree 裡留下 root 所有的 .o、.cmd。
正解
只有 insmod/rmmod 用 sudo；腳本用 sudo -u "$SUDO_USER" make。

以為 headers 版本隨便都行

症狀
insmod: ERROR: could not insert module: Invalid module format。
後果
module 是對著別的 kernel 編的，根本載不進去。
正解
對 /lib/modules/$(uname -r)/build 編譯。在 repo 根目錄跑 modinfo -F vermagic kernel/edge_test/edge_test.ko，第一個欄位要和 uname -r 一樣（這台是 5.15.148-tegra）。

照抄新版 kernel 的範例

症狀
class_create 參數個數不符，編譯失敗。
後果
網路上 6.4 以後的範例寫 class_create(name)；這台的 5.15 要 class_create(THIS_MODULE, name)。
正解
以本機 headers 的宣告為準：/lib/modules/$(uname -r)/build/include/linux/device/class.h。

  • /dev/edge_test 可以被 echo 寫、被 cat 讀，一般使用者也能用。
  • 反覆 insmod/rmmod 三次都乾淨，dmesg 沒有警告。
  • 超量寫入會先 short write、再 ENOSPC；無效 pointer 回 EFAULT 且不破壞內容。

目前限制（下一章的預告）

  • 只能整塊讀寫，沒有「控制」通道：想清空 buffer、查目前長度，都只能靠 O_TRUNC 或讀到底。Step 3 會加 unlocked_ioctl() 和一個 C++ userspace client。
  • 還沒有任何硬體。Step 4 開始，同一套 character device 骨架會接上 GPIO 和 LED。
1. /dev/edge_test 節點本身存了什麼，讓 kernel 找得到 edge_test_write()？

只存 major/minor 號碼（以及權限）。open 時 kernel 用號碼查到 cdev_add() 登記的 cdev，從中拿到 file_operations。

2. 寫 300 bytes 進空的 buffer，write() 第一次回傳多少？head -c 300 /dev/zero > /dev/edge_test 為什麼會報錯？

第一次回 256（short write）。寫入的程式（例如 head）再送剩下的 44 bytes，這時位置已是 256，driver 回 -ENOSPC，程式印出 No space left on device。

3. 為什麼不能直接 copy_from_user(edge_test_buf + *ppos, …)？

複製失敗時，_copy_from_user 會把沒複製到的目的端清成 0，原有內容就被破壞了。先複製到暫存區，成功才寫入。

4. 這裡為什麼用 mutex 而不是 spinlock？

持鎖期間會呼叫 copy_from_user()/copy_to_user()，它們可能因 page fault 而睡眠；spinlock 底下不能睡眠。
