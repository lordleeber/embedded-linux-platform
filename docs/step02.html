edge_test 字元裝置

第一個 kernel module 只做一件事：在 /dev/edge_test 放一塊 256 bytes 的記憶體。echo 寫進去，cat 讀出來。功能很小，但走過的路，就是之後每一個硬體 driver 和 userspace 溝通的同一條路。

kernel 5.15.148-tegra · L4T R36.4.7 · 新增 kernel/edge_test/{edge_test.c, Makefile, load.sh, unload.sh, README.md}、scripts/verify_edge_test.sh、tests/test_edge_test_device.py

userspace 程式 kernel 核心（syscall、VFS、devtmpfs） 我們寫的 driver 資料與資料流向
2.1起點為什麼

先寫一個不碰硬體的 driver

後面每一個 driver——GPIO、INA219、OLED、STM32 的 SPI 通道——最後都要給 userspace 一個入口，最直接的入口就是 /dev 底下的 character device。先用一個完全不碰硬體的 driver 把路走通，之後換成真的硬體時，出問題才分得清是「入口沒接好」還是「硬體沒回應」。這一步也收掉 Step 1 留下的未驗證項目：用 /lib/modules/$(uname -r)/build 真的編出 module 並載入成功。

互動雙方：userspace 程式（echo、cat、Python 測試）呼叫 edge_test.ko，中間經過 system call 和 VFS；沒有外接硬體，也沒有 bus 上的 controller / target。這一步不做：ioctl（Step 3）、interrupt、真實硬體控制。

.ko / insmod / rmmod
.ko（kernel object）是編好的 kernel module，可以在系統執行中插進 kernel。insmod 載入、rmmod 卸載，都要 root。
VFS
Virtual File System：kernel 裡處理所有「檔案」操作的那一層，read()/write() 都先到這裡，再轉給真正負責的程式碼。
dmesg / Oops
dmesg 印出 kernel 的 log，module 的 pr_info() 寫到這裡；Oops / BUG / WARNING 是 kernel 偵測到自己出錯時印的訊息。
2.2路徑user → kernel

一次 echo hello 往下走了幾層

對 echo 來說，/dev/edge_test 就是一個檔案。它呼叫 write()，VFS 看到這個節點記錄的裝置號碼（major / minor，這台是 489 / 0），找到我們在 insmod 時登記的 file_operations 表，再呼叫表裡的 .write，也就是 edge_test_write()。

file_operations 是一個裝滿函式指標的 struct，driver 填好一張交給 kernel：

最後兩行 .unlocked_ioctl / .compat_ioctl 是 Step 3 加的控制通道，下一章再講。沒填的欄位是 NULL，VFS 會替你回錯誤。release 在最後一個使用者 close() 時呼叫。THIS_MODULE 指向這個 module 自己：只要還有人開著 /dev/edge_test，kernel 就不讓 rmmod 卸掉它。

2.4寫入write()

截斷、ENOSPC 與一把 mutex

ubuf 帶著 __user 標記：它是 userspace 的位址，kernel 不能直接 dereference。copy_from_user() 會檢查位址範圍、碰到 page fault 也能安全收場，回傳沒複製成功的 byte 數。driver 成功回寫入的 byte 數、失敗回負的 errno；syscall 那層再轉成 write() 回 -1、errno 設成 ENOSPC 或 EFAULT。

  • 寫 300 bytes 到空的 buffer：第 91 行把 count 截成 256，回傳 256。這叫 short write。
  • 像 head 這種會把資料寫完的程式會再送剩下的 44 bytes；這時 *ppos 已經是 256，第 87–89 行回 -ENOSPC，head 印出 No space left on device（2.9 節實測）。

所有存取 buffer 的地方都在 edge_test_lock 底下。kernel 的 mutex 拿不到時讓執行緒去睡，跟 pthread mutex 類似；spinlock 拿不到時原地空轉、持有期間不准睡。copy_from_user() 碰到還沒載入記憶體的 user page 會觸發 page fault 並等待（也就是「睡眠」），所以這裡只能用 mutex。

2.5讀取read() · open()

讓它像一個小檔案

*ppos 是這一次 open 的讀寫位置，存在 struct file 的 f_pos，每個 open() 各有一份。cat 會一直 read() 到回傳 0，所以第 61–62 行的 EOF 一定要有，否則 cat 會無限迴圈。

shell 的 > 用 O_WRONLY | O_CREAT | O_TRUNC 開檔。對 character device，VFS 不會替你清空，O_TRUNC 的意義由 driver 決定；這裡選擇清空，所以先 echo hello world 再 echo hi 讀到的是 hi，不處理的話會是 hi\nlo world\n。inode 代表檔案本身、file 代表這一次 open；f_mode 是整理過的讀寫權限，f_flags 是原始旗標。pr_debug() 在這顆 kernel 不會印東西（沒開 CONFIG_DYNAMIC_DEBUG）。

2.6權限devnode

為什麼一般使用者也能 echo

devtmpfs 建出來的節點預設是 root 所有、權限 0600。第 172 行（2.3 節的 init 節錄）把這個 callback 掛到 class 上，節點建立時就是 0666；回傳 NULL 表示節點名稱不改。學習用的 buffer 裝置這樣方便；控制真實硬體的節點不要開成 0666，應該用 udev（收到 uevent 後依規則調整節點的 userspace 程式）的 rule 指定 group。

2.8踩坑EFAULT

失敗的寫入，把原本的資料清成了 0

測試 test_bad_user_pointer_returns_efault_and_keeps_buffer 先寫入 safe，再透過 Python 的 ctypes 直接呼叫 libc 的 write()，傳入位址 1 這個無效指標，預期回 EFAULT、內容不變。第一次在 Jetson 上跑，EFAULT 有正確回傳，內容卻變了：

FAIL: test_bad_user_pointer_returns_efault_and_keeps_buffer (test_edge_test_device.EdgeTestDeviceTest)
----------------------------------------------------------------------
Traceback (most recent call last):
  File "/home/nvidia/GitHubLL/embedded-linux-platform/tests/test_edge_test_device.py", line 127, in test_bad_user_pointer_returns_efault_and_keeps_buffer
    self.assertEqual(read_all(), b"safe")
AssertionError: b'\x00\x00\x00\x00' != b'safe'

原因在 kernel headers 的 _copy_from_user()：複製失敗時，它會把沒複製到的那段目的地清成 0，避免呼叫端拿到半初始化的資料。

第一版（已不存在於 repo）
if (copy_from_user(edge_test_buf + *ppos, ubuf, count)) {
	ret = -EFAULT;
	goto out;
}
修正版 · 見 2.4 節第 97–101 行
if (copy_from_user(tmp, ubuf, count)) {
	ret = -EFAULT;
	goto out;
}
memcpy(edge_test_buf + *ppos, tmp, count);

規則：不要把還想保留的狀態當成 copy_from_user() 的目的地。先複製到暫存區，成功了才寫進去；修完後同一支測試通過。tmp 只有 256 bytes，放得進這顆 kernel 16 KiB 的 kernel stack（arch/arm64/include/asm/memory.h 的 MIN_THREAD_SHIFT = 14；kbuild 的 CONFIG_FRAME_WARN=2048 也沒有警告，可用 grep CONFIG_FRAME_WARN /lib/modules/$(uname -r)/build/.config 自己查）。kernel stack 固定大小、不會自動長大；之後 buffer 若變大，就改用 kmalloc。

2.12收尾step 2 → 3

這一步做到了什麼

  • 一般使用者也能對 /dev/edge_test 執行 echo 和 cat。
  • 反覆 insmod / rmmod 三次都乾淨，dmesg 沒有警告。
  • 超量寫入先 short write、再回 ENOSPC；壞指標回 EFAULT，而且不破壞內容。
  • Step 1 記下的 kernel headers 確實能編出、並載入相符的 module。
  • 沒有實測：init 中途失敗的拆除路徑、vermagic 不符時的錯誤訊息。

目前只能整塊讀寫，沒有「控制」用的通道，例如清空 buffer 或查詢長度。Step 3 會加上 ioctl 和一個 C++ userspace client；Step 4 起，同一套骨架會接上真正的 GPIO 與 LED。

1. /dev/edge_test 節點本身存了什麼，讓 kernel 找得到 edge_test_write()？

只存 major/minor 號碼（以及權限）。open 時 kernel 用號碼查到 cdev_add() 登記的 cdev，從中拿到 file_operations。

2. 寫 300 bytes 進空的 buffer，第一次 write() 回傳多少？head 為什麼會報錯？

第一次回 256（short write）。head 再送剩下的 44 bytes，這時位置已是 256，driver 回 -ENOSPC。

3. 為什麼不能直接 copy_from_user(edge_test_buf + *ppos, …)？

複製失敗時，_copy_from_user 會把沒複製到的目的端清成 0，原有內容就被破壞了。

4. 這裡為什麼用 mutex 而不是 spinlock？

持鎖期間會呼叫 copy_from_user()/copy_to_user()，它們可能因 page fault 而睡眠；spinlock 底下不能睡。
