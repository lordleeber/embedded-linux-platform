UEFI 與開機：誰把 kernel 和 Device Tree 放進記憶體

到 Step 3 為止，我們都是從「kernel 已經在跑」開始看。這一章往前走一步：按下電源之後、kernel 的第一行 C code 執行之前，是誰在做事？UEFI 是什麼？extlinux.conf 是誰讀的？為什麼改了 overlay 一定要重開機？下一章的 Device Tree 會直接用到這些答案。

UEFI.1起點為什麼需要

kernel 是一個檔案，它不會自己跑起來

/boot/Image 只是儲存裝置上的一個檔案。電源接上之後，必須有別的程式把它讀進記憶體、把 initrd（一個小型的暫時 root 檔案系統，kernel 先用它載入 driver，才能掛上真正的 rootfs）和 Device Tree 也準備好、再跳到它的入口，這份工作叫 bootloader。PC 上是 BIOS 或 UEFI 加上 GRUB；這台 Jetson（JP6 / L4T R36）用的也是 UEFI。

UEFI（Unified Extensible Firmware Interface）是一份規格：它規定韌體要把哪些服務提供給後面的程式，例如「找開機項目」「讀 FAT 分區上的檔案」「配記憶體」「讀寫存在韌體裡的變數」。照這份規格寫成的韌體就叫 UEFI firmware；NVIDIA 的這份是以開源的 EDK II 為基礎（後面 UEFI.4 會在 BOOTAA64.efi 裡看到 edk2-nvidia 的路徑）。

互動雙方：交出的一方是 UEFI 韌體，以及它載入的開機程式 L4TLauncher；它們都在 kernel 之前執行，交接完就退場。接手的一方是 kernel（開頭的 EFI stub 先接手）。交出的東西有三樣：

  • kernel 映像和 initrd 在記憶體裡的位置；
  • 已經疊好 overlay 的 Device Tree；
  • kernel 命令列。

交接之後韌體不再主動做事，只剩 kernel 需要時可以呼叫它的 Runtime Services，例如讀寫韌體變數（UEFI.6）。這一章不做：不改任何開機設定，不碰 UEFI 的設定畫面，不講 Secure Boot、韌體更新（capsule）與 A/B slot。

UEFI firmware
板子上最先跑起來的一層可擴充韌體。它依序做：初始化硬體、依 BootOrder 找開機項目、載入並執行一個 .efi 程式。
.efi（EFI application）
一種可以被 UEFI 載入執行的 PE 格式程式。開機程式（GRUB、L4TLauncher）和 Linux kernel 本身（帶 EFI stub 時）都可以是 .efi。
rootfs
root filesystem（根檔案系統）：以 / 為起點、整個 Linux 目錄樹掛在上面的那個檔案系統，系統檔、使用者檔案和 /boot 都在裡面。這台板子上是 NVMe 的 nvme0n1p1（ext4）。kernel 靠命令列的 root=PARTUUID=… 找到它。
ESP
EFI System Partition，一個 FAT 格式的分區，規格規定韌體一定要讀得懂它。開機用的 .efi 放在這裡。
L4TLauncher
NVIDIA 寫的 UEFI 應用程式，是這台板子上實際讀 extlinux.conf、疊 overlay、啟動 kernel 的那一個（UEFI.4）。
extlinux.conf
開機選單的設定檔，一個 LABEL 是一個開機項目，記錄 kernel、initrd、Device Tree、overlay 與 kernel 命令列（UEFI.5）。名字來自 syslinux 家族的 extlinux 開機程式，格式沿用至今。
UEFI variable
存在韌體非揮發儲存裡的「名字 → 值」。BootOrder、Boot0001 都是。kernel 開機後透過 efivarfs 把它們當檔案開放在 /sys/firmware/efi/efivars。
EFI stub
編進 kernel 映像開頭的一小段程式，讓 UEFI 能把 Image 當成 .efi 載入，並把 UEFI 的資訊整理後交給 kernel 本體（UEFI.6）。
UEFI.2全景電源 → kernel

一次開機經過的七站

下圖是這台板子從上電到 /proc/device-tree 出現的路。每個方框都可以點，會跳到講那一站的小節。最上面一站是照 NVIDIA 文件寫的，從執行中的系統看不到，細節放在上一章UEFI 之前，本章只當作背景；從第二站開始，後面每一站都有一段只讀指令可以自己確認。

誰把 kernel 叫起來？是 L4TLauncher，不是 UEFI 韌體本體。圖裡每一站叫起下一站：UEFI 韌體叫起 ESP 上的 L4TLauncher（UEFI.3、UEFI.4），L4TLauncher 讀完 extlinux.conf、把 Image、initrd 載入記憶體、裝好合併後的 Device Tree，再啟動 Image（UEFI.4 的字串證據、UEFI.6 的交接）。啟動之後韌體與 L4TLauncher 都退場，kernel 自己往下跑。

UEFI.3韌體BootOrder

UEFI 韌體不在 NVMe 上，開機項目存在它自己的變數裡

PC 的 GRUB 是裝在硬碟上的程式；UEFI 韌體不是。它是板子上另外一塊非揮發儲存（QSPI flash）裡的映像，由更早的 bootloader 載入（UEFI 之前），不在 rootfs 裡，所以從執行中的 Linux 用 ls 找不到它。看得到的是它留給 OS 的變數，用 efibootmgr 讀：

efibootmgr | head -3
efibootmgr -v | grep Boot0000
mount | grep efivarfs
xxd -p /sys/firmware/efi/efivars/BootOrder-*

2026-10-19 在這台板子上的輸出：

$ efibootmgr | head -3
BootCurrent: 0001 «1»
Timeout: 5 seconds «2»
BootOrder: 0001,0004,0003,0002,0005,0000,0006,0007 «3»
$ efibootmgr -v | grep Boot0000
«4» Boot0000* Enter Setup	FvVol(49a79a15-8f69-4be7-a30c-a172f44abce7)/FvFile(462caa21-7614-4503-836e-8ab6f4662331)
$ mount | grep efivarfs
efivarfs on /sys/firmware/efi/efivars type efivarfs (rw,nosuid,nodev,noexec,relatime) «5»
$ xxd -p /sys/firmware/efi/efivars/BootOrder-*
0700000001000400030002000500000006000700 «6»
  1. 1BootCurrent：這次開機用的是 Boot0001。它的名稱是「UEFI」加上 NVMe 的型號，也就是從這顆 NVMe 開機。
  2. 2Timeout: 5 seconds 是 UEFI Boot Manager 的等待時間（按鍵進設定畫面用）。它和 extlinux.conf 的 TIMEOUT 是兩件事，後者是 L4TLauncher 的選單（UEFI.5）。
  3. 3BootOrder：依序嘗試 0001（NVMe）、0004 與 0003、0002、0005（HTTP / PXE 網路開機）、0000（進設定）、0006、0007（開機選單、UEFI Shell）。第一個能成功的就用它；這台第一個就成功。
  4. 4Boot0000 的裝置路徑是 FvVol/FvFile：韌體映像內部的一個檔案，不是任何磁碟上的檔案。這是「UEFI 本體不在 rootfs」的直接證據。
  5. 5kernel 把這些變數用 efivarfs 掛成檔案。能掛，代表 kernel 是靠 UEFI 開機、而且拿得到 UEFI 的 Runtime Services（UEFI.6）。
  6. 6BootOrder 這個檔案的內容：開頭 4 byte 07000000 是變數屬性（UEFI 規格：非揮發、開機服務與 runtime 都可存取），後面是一串 16-bit little-endian 的編號：0100 0400 0300 0200 0500 0000 0600 0700 正是上面的 0001,0004,0003,0002,0005,0000,0006,0007。

跑出來和這裡不一樣時：開機項目的編號與名稱會隨你的儲存裝置（NVMe、SD 卡）和網卡 MAC 而不同，BootOrder 的順序也可能因為你進過設定畫面而變；只要 BootCurrent 那一項是你的開機碟就對了。efibootmgr 沒有安裝時 sudo apt install efibootmgr（讀取不需要 root）。

UEFI.4ESPL4TLauncher

Boot0001 沒有檔名，韌體執行的是 ESP 上的預設路徑

上一節 Boot0001 的裝置路徑只指到「這顆 NVMe」，沒有指到哪個檔案。UEFI 規格對這種項目有固定的做法：到磁碟上的 ESP 找預設路徑 \EFI\BOOT\BOOT<架構>.EFI，AArch64 的架構字串是 AA64，所以是 BOOTAA64.efi。ESP 在哪、裡面有什麼，直接看：

  1. 1rootfs 是 nvme0n1p1（ext4，分區名 APP），/boot/Image、/boot/extlinux 都在這裡。
  2. 2ESP 是 nvme0n1p10（vfat），掛在 /boot/efi。注意它只掛在 /boot/efi，不是整個 /boot。
  3. 3esp_alt 是備用 slot 的 ESP，本章不展開。
  4. 4ESP 裡只有一個開機用檔案 BOOTAA64.efi；UpdateCapsule 是韌體更新用的目錄，現在是空的。沒有 Image、沒有 .dtb、沒有 extlinux.conf。
  5. 5BOOTAA64.efi 的 UTF-16 字串裡有 boot\extlinux\extlinux.conf 和處理失敗時的錯誤訊息：讀這份設定檔的是這支程式。
  6. 6一般的 ASCII 字串裡有 ExtLinuxBoot、ProcessExtLinuxConfig 這兩個函式名；同一個檔案裡還有原始碼路徑 edk2-nvidia/Silicon/NVIDIA/Application/L4TLauncher/L4TLauncher.c，所以 BOOTAA64.efi 就是 L4TLauncher。
  7. 7還有兩則訊息：Installing Kernel DTB（把合併好的 Device Tree 裝進去）和 Failed to boot image（啟動 kernel 映像失敗時的錯誤）。意思是 L4TLauncher 自己負責「把 Device Tree 裝好、再啟動 kernel」。實際用哪個 UEFI 呼叫啟動，這章沒有逐行追原始碼，從訊息文字判斷。

結論：ESP 裡沒有 extlinux.conf，它在 rootfs 的 /boot/extlinux/；L4TLauncher 是一支能讀 rootfs 的 UEFI 應用程式（推論：因為 ESP 裡沒有，而改 rootfs 這份檔案開機行為確實會變，Step 4-b 的 overlay 就是這樣生效的）。所以 Device Tree 一章的圖 0.1 寫的「UEFI 讀 extlinux.conf」是簡寫，精確的說法是「UEFI 載入的 L4TLauncher 讀 extlinux.conf」。

跑出來和這裡不一樣時：用 SD 卡開機的板子，儲存裝置是 /dev/mmcblk0，分區編號也不同；把指令裡的 /dev/nvme0n1 換成你的裝置。strings 在 binutils 套件裡。

UEFI.5設定檔extlinux.conf

extlinux.conf：一個 LABEL 就是一個開機項目

L4TLauncher 讀到的設定檔，這台板子目前的 JetsonIO 項目如下（指令裡的 sed -n '/^LABEL JetsonIO/,$p' 是「只印出從以 LABEL JetsonIO 開頭的那一行，到檔案最後一行」：-n 關掉 sed 預設的每行都印，/…/,$ 指定範圍，p 是印出。JetsonIO 剛好是檔案裡最後一個 LABEL，所以這個範圍就是它的全部內容，不會印出前面的 primary 項目和註解）：

sed -n '/^LABEL JetsonIO/,$p' /boot/extlinux/extlinux.conf
ls /boot/extlinux
$ sed -n '/^LABEL JetsonIO/,$p' /boot/extlinux/extlinux.conf
LABEL JetsonIO
	MENU LABEL Custom Header Config: <CSI Camera IMX219-A>
	LINUX /boot/Image
	FDT /boot/dtb/kernel_tegra234-p3768-0000+p3767-0005-nv-super.dtb
	INITRD /boot/initrd
	APPEND ${cbootargs} root=PARTUUID=07c26928-d45b-4e5b-8c02-fc06ea41fecc rw rootwait rootfstype=ext4 mminit_loglevel=4 console=ttyTCU0,115200 firmware_class.path=/etc/firmware fbcon=map:0 video=efifb:off console=tty0 nv-auto-config
	OVERLAYS /boot/tegra234-p3767-camera-p3768-imx219-A.dtbo,/boot/edge-gpio-overlay.dtbo
$ ls /boot/extlinux
extlinux.conf
extlinux.conf.edge-gpio.bak
extlinux.conf.jetson-io-backup
extlinux.conf.nv-update-extlinux-backup

為什麼說「一個 LABEL 是一個開機項目」：因為每個 LABEL 區塊裡有開機要決定的每一件事（kernel、initrd、Device Tree、overlay、命令列），L4TLauncher 選定一個 LABEL，就拿到完整的一組。檔案裡 JetsonIO 前面還有一個 LABEL primary，兩個項目逐欄對照如下：

欄位LABEL primaryLABEL JetsonIO差別
MENU LABELprimary kernelCustom Header Config: <CSI Camera IMX219-A>不同（只是選單上的名字）
LINUX/boot/Image/boot/Image相同
INITRD/boot/initrd/boot/initrd相同
FDT沒有這一行/boot/dtb/kernel_tegra234-p3768-0000+p3767-0005-nv-super.dtb不同：JetsonIO 指定了 Device Tree
OVERLAYS沒有這一行/boot/tegra234-p3767-camera-p3768-imx219-A.dtbo,/boot/edge-gpio-overlay.dtbo不同：JetsonIO 疊上相機與 edge-gpio 兩個 overlay
APPEND${cbootargs} root=PARTUUID=…${cbootargs} root=PARTUUID=…相同（整行逐字相同）

兩個項目用同一個 kernel、initrd 和命令列，差別只在 Device Tree：JetsonIO 指定了 FDT 並疊上 overlay，primary 沒有指定。開機時用哪一個，由檔案開頭的 DEFAULT JetsonIO 決定，所以本專案的安裝腳本只改 DEFAULT 那個 LABEL 的 OVERLAYS。primary 的內容用 sed -n '/^LABEL primary/,/^LABEL JetsonIO/p' /boot/extlinux/extlinux.conf 可以看到；沒有實際看過開機選單畫面，選單怎麼顯示是依 extlinux 的慣例推的。

欄位這台板子上的值與作用
DEFAULT（檔案開頭）JetsonIO：不選的話開哪個 LABEL。本專案的 overlay 一律裝在這個 LABEL（scripts/install_edge_gpio_overlay.py）。
LABEL / MENU LABEL項目的內部名稱與選單上顯示的文字。JetsonIO 這個 LABEL 是 jetson-io 工具寫的，所以選單文字是「Custom Header Config: …」。
LINUXkernel 映像 /boot/Image。
INITRD初始 ramdisk /boot/initrd，kernel 掛真正的 rootfs 之前先用它。
FDT原廠 Device Tree 的 .dtb。沒有這行時用什麼，這章沒有查證。
OVERLAYS要疊在 FDT 上的 .dtbo，用逗號分隔、不加空白。這是 NVIDIA 的擴充，不在原本的 extlinux 格式裡。
APPEND傳給 kernel 的命令列。其中 ${cbootargs} 不是 kernel 看得懂的字，要由 L4TLauncher 替換（UEFI.6 看結果）。

兩件要記住的事。第一，所有路徑都是 rootfs 上的路徑（/boot/…），和 ESP 無關。第二，這個檔案會被好幾個工具改：目錄裡的三個備份檔，從檔名看分別是本專案的安裝腳本（.edge-gpio.bak，第一次安裝時存一份，腳本裡有寫）、jetson-io（.jetson-io-backup）和 NVIDIA 的更新腳本（.nv-update-extlinux-backup）留下的；後兩個這章只依檔名判斷，沒有追它們的原始碼。你自己手改之前，也先 cp 一份。

UEFI.6交接韌體 → kernel

kernel 從 /chosen 和 /sys/firmware/efi 拿到韌體留下的東西

L4TLauncher 把 Image 當成 .efi 啟動；Image 開頭的 EFI stub 先跑，把韌體的資訊整理好，才進 kernel 本體。整理的結果有兩處看得到：Device Tree 的 /chosen 節點，以及 /sys/firmware/efi。

  1. 1linux,uefi-* 這組屬性是 kernel 的 EFI stub 寫進 /chosen 的（記憶體地圖與 UEFI system table 的位址；依 kernel 的 EFI stub 文件）。它們存在，表示這個 kernel 是被當成 EFI 應用程式啟動的。
  2. 2/proc/cmdline 是 APPEND 替換之後的結果：沒有 ${cbootargs} 這個字面；結尾多了兩個 bl_prof_*。
  3. 3bl_prof_* 不在 extlinux.conf 裡（計數 0），所以是韌體那一側加的。推論：${cbootargs} 被換成韌體提供的那串參數；這章沒有追 L4TLauncher 的實際替換流程。
  4. 4kernel 能列出 55 個 UEFI 變數，代表 kernel 拿到了 UEFI 的 Runtime Services，可以在開機後繼續讀寫韌體變數。
  5. 5L4TDefaultBootMode 有 i（immutable）旗標，BootOrder 沒有。efivarfs 對重要變數預設加這個旗標，擋掉不小心的修改。

為什麼改了 overlay 要重開機：疊 overlay 的是 L4TLauncher，而它在 kernel 開始之前就做完了。之後 kernel 手上只有一份記憶體裡的合併結果，/boot/*.dtbo 不會再被讀一次。這台 kernel 也沒有 CONFIG_OF_CONFIGFS，沒有 runtime overlay 可以用（Step 4-b 會查這個設定）。cmdline 也是同樣的道理：改了 APPEND，/proc/cmdline 要到下次開機才會變。

ESP 只掛在 /boot/efi，裡面只有 BOOTAA64.efi。extlinux.conf 裡的 /boot/… 路徑都是 rootfs 的。

改了 APPEND 就查 /proc/cmdline

症狀
在 extlinux.conf 加了 kernel 參數，/proc/cmdline 沒有變。
後果
以為存檔失敗，反覆再改。
正解
/proc/cmdline 是上次開機時交給 kernel 的那一份，重開機才會換。

手改 extlinux.conf 沒備份

症狀
打錯字或漏掉 LINUX 行。BOOTAA64.efi 裡有 Unable to process extlinux config 這類訊息（沒實測）。
後果
可能開不了機，要接序列 console 或進 recovery 模式才能救（沒實測）。
正解
用 install_edge_gpio_overlay.py：它用暫存檔加 rename 原子替換，第一次安裝存 .edge-gpio.bak。手改前先 cp。

把 efivars 當一般檔案刪

症狀
為了「清理」對 /sys/firmware/efi/efivars 底下的檔案下 rm。
後果
efivarfs 的刪除是真的刪韌體變數。沒有 i 旗標的（如 BootOrder）不會擋你（沒實測，也不建議試）。
正解

把兩個 timeout 當成同一個

症狀
efibootmgr 說 5 秒，extlinux.conf 開頭卻是 TIMEOUT 30。
後果
要縮短選單等待卻改錯地方。
正解
前者是 UEFI Boot Manager 等待的秒數；後者是 L4TLauncher 的選單，單位依 extlinux 的慣例是 1/10 秒（沒實測）。

以為 Boot0001 是 NVMe 裡的一個檔案

症狀
想用 find 找 Boot0001。
後果
找不到而困惑，甚至懷疑 NVMe 壞了。
正解
Boot#### 是存在韌體變數區的一筆設定；它的裝置路徑只指到磁碟，檔案由規格的預設路徑 \EFI\BOOT\BOOTAA64.efi 補上。
UEFI.8收尾UEFI → DT

這一章讀懂了什麼

  • 開機是一串接力：UEFI 韌體（不在 rootfs）→ ESP 上的 BOOTAA64.efi（L4TLauncher）→ rootfs 的 extlinux.conf → kernel。
  • UEFI 的開機項目存在韌體變數裡（BootOrder、Boot####），kernel 開機後透過 efivarfs 當檔案讀。
  • extlinux.conf 的 LABEL 描述一個開機項目；FDT 加 OVERLAYS 就是 Device Tree 的來源，路徑都在 rootfs。
  • 韌體用 /chosen（bootargs、linux,uefi-*）和 /sys/firmware/efi 把資訊交給 kernel；疊 overlay 發生在 kernel 之前，所以要重開機。
  • BootROM、MB1 / MB2 等更早的階段、Secure Boot、capsule 更新、A/B slot：這章沒有展開。
  • Device Tree 本身的格式、/proc/device-tree 怎麼讀、overlay 怎麼找到要改的節點：下一章與 4-b。

下一章 Device Tree 入門會從這一章的終點接手：韌體交到 kernel 手上的那份樹，裡面有什麼、怎麼讀、driver 怎麼用它。

1. 你在 extlinux.conf 的 APPEND 加了 loglevel=7，存檔後 cat /proc/cmdline 沒看到它。下一步做什麼？

重開機。/proc/cmdline 是 L4TLauncher 在上次開機時替換好、交給 kernel 的那一份；重開機後再看。如果仍沒有，才去檢查你改的是不是 DEFAULT 指到的那個 LABEL。

2. efibootmgr 顯示 Boot0001 沒有檔名，韌體怎麼知道要執行哪個 .efi？這台板子上它執行的是什麼？

UEFI 規格規定：項目只指到磁碟時，去那顆磁碟的 ESP 找預設路徑 \EFI\BOOT\BOOT<架構>.EFI。AArch64 是 BOOTAA64.efi，在這台板子上就是 L4TLauncher。

3. ESP 為什麼要是 FAT 格式，而不是 rootfs 用的 ext4？

UEFI 規格只要求韌體一定要讀得懂 FAT，所以放 .efi 的 ESP 用 FAT。L4TLauncher 能讀 rootfs 上的 extlinux.conf 是它自己的能力（見 UEFI.4 的推論），不是規格保證的。

4. /proc/device-tree/chosen 裡的 linux,uefi-system-table 是誰寫的？它和 /sys/firmware/efi/efivars 能讀有什麼關係？

kernel 的 EFI stub 寫的，內容是 UEFI system table 的位址。kernel 有了它才找得到 UEFI 的 Runtime Services，才能在開機後讀寫韌體變數，efivarfs 才有東西可以開放出來。
