7.1起點為什麼

同一個晶片，為什麼要再寫一次 kernel driver

ina219_raw 能讀，但每支想知道電池狀態的程式都得自己知道「bus 7、位址 0x41、register 0x02 右移 3 位乘 4 mV」，也都要有開 /dev/i2c-7 的權限。driver 把這些知識收進 kernel：晶片是什麼、在哪裡由 Device Tree 描述，怎麼讀、怎麼換算由 driver 負責，userspace 只看到一個已經換算好的數字。這也是之後 Step 8 接上標準 hwmon 介面的前提。

互動雙方：controller 仍是 Jetson 的 c250000.i2c（i2c-7，header pin 3 / 5），target 仍是 UPS 模組上的 INA219（0x41）。不同的是發起讀取的一方：從 userspace 程式換成 kernel 裡的 edge_ina219。這一步不做：不註冊 hwmon（Step 8）；userspace 介面是這個 driver 私有的五個 sysfs 檔，Step 8 會換掉。

I2C client
kernel 裡代表「某條 bus 上某個位址的一顆裝置」的物件（struct i2c_client），在 sysfs 叫 <bus>-<4 位位址>，這裡是 7-0041。它可以先存在、之後才有 driver 來接管。
struct i2c_driver
I2C driver 向 I2C core 註冊的結構：支援哪些裝置（match 表）、綁定時呼叫的 probe、解除時呼叫的 remove。4-b / 5-b 的 platform driver 是同一個模式，只是換成 I2C bus。
bind / unbind
把一個 driver 接到一個 device 上（之後 probe 會被呼叫）或拆開（呼叫 remove）。/sys/bus/i2c/devices/7-0041/driver 這個連結存在，就代表已綁定。
i2c_device_id
第二種 match 表：用名字比對，給沒有 DT 節點、由 userspace 寫 new_device 建立的 client 用（7.10 用它造一個「沒人回應」的 client）。
sysfs attribute
/sys 底下的一個檔案，讀它時 kernel 呼叫 driver 的 show 函式，函式把文字寫進一頁 buffer 回傳。DEVICE_ATTR_RO(x) 宣告一個唯讀檔 x，對應 x_show()。
UU
i2cdetect 在位址已被某個 driver 綁定時印的標記：它不去探測，直接顯示 UU。

7.3描述Device Tree

在 header I2C 底下加一個 ina219@41

INA219 不會自己報到：I2C 沒有「列舉」機制，kernel 不知道 bus 上有什麼，得有人告訴它「這個位址有一顆什麼晶片」，kernel 才會建立 client、driver 才有東西可以 probe。告訴它的方法不只一種（本節最後比較），這一步用 Device Tree。節點加在 4-b / 5-b 用的同一份 overlay 裡，第五個 fragment：

  • target = <&hdr40_i2c1>：hdr40_i2c1 是基底 DT 裡的標籤，指向 /bus@0/i2c@c250000，也就是 i2cdetect -l 的 c250000.i2c（6b.3）。用標籤而不寫路徑，overlay 編譯時留下一筆 __fixups__，由 bootloader 合併時解析。在這台板子上可以自己查：tr -d '\0' < /proc/device-tree/__symbols__/hdr40_i2c1 印出 /bus@0/i2c@c250000。
  • #address-cells = <1>; #size-cells = <0>;：I2C 子節點的 reg 只有一格位址、沒有長度。基底 DT 的控制器節點已經這樣寫了，但 dtc 單獨編 overlay 時看不到基底，會用預設的 2 和 1，報 reg_format 等一串 warning（把這兩行刪掉實測過），所以 overlay 裡再寫一次。
  • reg = <0x41>：phase03.md 的範例寫 ina219@40，這塊模組實際掃到的是 0x41（6a），節點名稱 @ 後面要和 reg 一致。
  • compatible = "edge,edge-ina219"：不只廠商前綴要是自己的，逗號後面的名字也要獨一無二。I2C core 拿 compatible 去掉廠商前綴當 client 的名稱（下面輸出的 edge-ina219），而且配對時 DT compatible 比不到，還會拿這個名稱去比每個 driver 的 i2c_device_id 表。第一版寫成 edge,ina219，名稱就是 ina219；這台 kernel 的上游 ina2xx.ko（CONFIG_SENSORS_INA2XX=m）的 id 表正好有它，modinfo ina2xx 看得到 alias: i2c:ina219。它不會被自動載入（client 的 uevent modalias 是 of: 開頭，只對得到 ti,ina219），但只要有人 modprobe ina2xx，它就能接管 7-0041、寫入它自己的設定。這是 code review 指出的，依 kernel 的配對規則推論，沒有真的載入 ina2xx 試；改名後由測試從 modules.alias 確認沒有任何 module 認領 edge-ina219。

改完 overlay 要重新編、安裝、重開機（這台沒有 runtime overlay，4-b 的做法）。安裝前先在本機用 fdtoverlay 把「基底 FDT + NVIDIA 的相機 overlay + 我們的 overlay」合併一次，確認節點真的落在 /bus@0/i2c@c250000 底下；這件事寫成了 test_overlay_applies_to_the_boot_fdt。重開機後，在 repo 根目錄看兩個地方：

ls /proc/device-tree/bus@0/i2c@c250000/ina219@41/
ls /sys/bus/i2c/devices/7-0041/ && cat /sys/bus/i2c/devices/7-0041/name
compatible  name  reg «1»
modalias  name  of_node  power  subsystem  uevent «2»
edge-ina219 «3»
  1. 1節點進了開機時的 DT。
  2. 2I2C core 依節點建立了 client 7-0041，但目錄裡沒有 driver 連結：還沒有人接管它。這是 edge_ina219.ko 沒載入時的樣子，載入後會多出 driver 和五個屬性檔。
  3. 3client 的名字是 compatible 去掉廠商前綴 edge,，不是節點名（節點名的 @ 前面是 ina219）。

你的板子如果還沒裝這份 overlay，第一行會是 No such file or directory，7-0041 也不存在；裝 overlay 的指令在 7.10。

一定要 overlay 嗎？

6-b 的 ina219_raw 沒有裝任何 overlay 就讀得到晶片，是因為它打開的 /dev/i2c-7 代表的是整條 bus（控制器 c250000.i2c），這個控制器本來就在 NVIDIA 的基底 DT 裡。「0x41 是一顆 INA219、register 怎麼換算」這些知識寫在程式自己身上，kernel 只負責送 byte。換成 kernel driver，這些知識搬進了 kernel，kernel 就得先知道「哪裡有一顆什麼晶片」，也就是要先有一個 client。建立 client 有三種方法：

建立 client 的方法要 overlay？要重開機？特點
DT 節點（這一步）要；這台沒有 runtime overlay，所以也要重開機開機就有 client，不用任何指令；節點可以帶屬性（例如之後的 shunt 電阻值）；Phase 10 的 Yocto image 也是這樣把硬體描述打包進去
userspace 寫 new_device都不用echo <名字> <位址> > /sys/bus/i2c/devices/i2c-7/new_device，driver 靠 i2c_device_id 的名字配對。重開機就消失，也沒有 DT 屬性可讀
另一段 kernel 程式呼叫 i2c_new_client_device()都不用位址和名字寫死在 C 裡（DT 普及前的 board file 做法），換板子就要改 code

第二種在這一章用過：7.10 的驗收腳本就是用 new_device 在 0x45 建 client，沒有任何 DT 節點，edge_ina219 的 probe 照樣被呼叫（只是沒人回應而失敗）。所以想快速試 driver 時，echo edge_ina219 0x41 > /sys/bus/i2c/devices/i2c-7/new_device 不必改 overlay、不必重開機，就能把 driver 接到真的晶片上（這個指令在 0x41 上沒有實測，0x45 實測過）。這一步仍選 DT，是因為 phase03 規劃要求 Device Tree binding，之後 Step 8、Phase 10 也都假設硬體描述在 DT 裡、driver 不寫死位址。

前幾章也對得上這個分界：

  • Step 2 / 3 的 edge_test：沒有硬體，module 載入時自己建 /dev/edge_test，不需要 DT。USB、PCI 這類能自己列舉的 bus 也不需要，插上就有裝置。
  • 4-a 的 userspace GPIO 沒有 overlay：/dev/gpiochip0 本來就在，但 pin 29 的 pad 開機是 tristate，得另外跑 scripts/pad_pin29.py 直接改 pad register，重開機就失效。4-b 改用 overlay，pad 設定就寫在節點的 pinctrl 狀態裡，driver probe 前由 kernel 自動套用。
7.4配對i2c_driver

i2c_driver：兩張 match 表、probe、remove

  • of_match_table：client 7-0041 有 DT 節點（of_node），I2C core 拿節點的 compatible 和這張表比，相符就呼叫 probe。比不到時，I2C core 還會拿 client 名稱（edge-ina219）去比 id_table，這就是 7.3 說名字要獨一無二的原因。MODULE_DEVICE_TABLE(of, …) 讓 client 的 modalias（cat /sys/bus/i2c/devices/7-0041/modalias 印出 of:Nina219T(null)Cedge,edge-ina219）可以對到這個 module；這個 module 沒有裝進 /lib/modules，所以不會自動載入，要手動 insmod。
  • id_table：沒有 DT 節點的 client 只能靠名字配對。驗收腳本用它在 0x45 建一個 client，證明位址沒回應時 probe 會失敗（7.10）。
  • .dev_groups：屬性檔由 driver core 在 probe 成功後建立、在 remove 時刪除，driver 不必自己呼叫 sysfs_create_group，也就不會漏刪。probe 失敗的 client 不會有這些檔。
  • .probe_new：5.15 的 struct i2c_driver 有兩種 probe：舊的 probe(client, id) 和新的 probe_new(client)。我們不需要 id，用新的（較新的 kernel 已把 probe_new 改名回 probe）。
  • module_i2c_driver()：展開成 module init / exit，分別呼叫 i2c_add_driver / i2c_del_driver。
7.5綁定probe()

probe：先確認有人回應，再寫 Calibration 和 Config

  • 第一次讀就是存在檢查：DT 說 0x41 有裝置，不代表線有接、模組有電。位址沒 ACK 時 read_reg16 回 -EREMOTEIO，probe 回傳錯誤，I2C core 就不綁定、不建屬性檔。dev_err_probe() 印錯誤並原樣回傳錯誤碼，dmesg 會出現 error -EREMOTEIO: cannot read Config（7.10 實測）。
  • 為什麼 probe 要寫入：INA219 上電時 Calibration 是 0，這時晶片不算 Current / Power（6b.7）。6-b 的工具只讀不寫，要靠先跑過廠商範例。driver 在 probe 把範例的值（Cal 26868、Config 0x0EEF）寫進去，之後不依賴範例。兩個值放在共用 header，和 6-a 讀範例時一致（7.8 的 header）。
  • 順序：先寫 Calibration，再寫 Config。Calibration 從下一次轉換開始生效，而寫 Config 會重新開始轉換，這樣第一筆新轉換就用到新的 Calibration。測試把這個順序寫死（反過來會紅）。這個順序的效果沒有在晶片上單獨量過，理由取自 datasheet 的描述。
  • 寫完讀回比對：INA219 沒有 ID register，有 ACK 只代表「有東西回應」。寫入後把 Calibration 和 Config 讀回來，和剛寫的不一樣就以 -ENODEV 失敗（code review 後加的）。限制是寫入仍然發生在確認之前，沒有 ID register 就沒辦法先確認。dmesg 出現 probed: 那行，代表讀回已經相符。
  • 沒有 private data：這個 driver 不存任何狀態，所以沒有 devm_kzalloc、i2c_set_clientdata。換算要用的 Calibration 每次都從晶片讀（7.7）。

這次 probe 的寫入其實沒有改變任何值：dmesg 是 Config 0x0EEF -> 0x0EEF，insmod 前 Calibration 也已經是 0x68F4。UPS 模組一直供電給 INA219，Jetson 重開機不會讓它斷電，前幾章範例寫的值一直留著。要看到 probe 從 Cal 0 寫起的效果，得讓 UPS 本身斷電（拔電池），這次沒做。

7.7helper錯誤往上傳

helper：讀不到就回傳 errno，不回舊值

  • 錯誤一路往上：read_reg16 的負數由 helper 回傳，再由 show 函式回傳給 sysfs，最後變成 userspace read() 的錯誤（cat 會印 Remote I/O error）。沒有快取，所以不會有「I2C 斷了但檔案還印上一次的值」的情況。讀屬性途中 I2C 失敗這一路沒有實測，只實測了 probe 時的 -EREMOTEIO。
  • read_calibrated()：Current 和 Power 要乘 Current_LSB，而 Current_LSB 由 Calibration 算出，所以先讀 Calibration。它是 0 時回 -ENODATA，不然換算會除以 0（6-b 的工具在這時印 n/a）。每次都從晶片讀，而不是相信 probe 寫進去的常數：有人在 driver 綁定時用 i2cset -f 或範例改了 Calibration，driver 和 ina219_raw 也還是用同一個值換算。
  • 不是同一次轉換：讀 Current 和讀 Calibration 是兩筆 I2C 傳輸，和 6-b 的六次讀一樣，中間可能跨過一次轉換（約 34 ms 一次）。Calibration 不會自己變，所以這裡沒問題；但 current_ua 和 shunt_uv 分兩次 cat 時可能來自不同轉換，registers 的六個值也是六筆傳輸，不是同一瞬間的快照。driver 裡加 mutex 也只擋得住自己的並行讀取，擋不住外面用 i2cset -f 寫入。
7.8介面sysfs

五個唯讀屬性，換算在共用 header

檔案（0444）內容
registers六個 register 原始值，給和 ina219_raw 逐格比對用
bus_mvBus Voltage，mV，去掉 CNVR / OVF 兩個狀態位
shunt_uvShunt Voltage，µV，有號（放電為負，6-b 實測）

測試：從 6-b 的規格和實測值長出來

7.12收尾7 → 8

這一步做到了什麼

  • overlay 的 ina219@41 讓 kernel 開機時建立 client 7-0041；edge_ina219.ko 以 compatible edge,edge-ina219 綁定，probe 寫完讀回相符；client 名稱 edge-ina219 沒有別的 module 認領。
  • byte order 用 i2c_smbus_read_word_swapped() / write_word_swapped() 處理；換算放在 kernel 和 userspace 共用的 header，和 6-b 的 decoder 逐值相同。
  • driver 讀到的六個 register、電壓和 ina219_raw 完全一致；驗收 0 failure。
  • 位址沒回應時 probe 失敗（-EREMOTEIO），不綁定、不建屬性檔；rmmod 後屬性檔消失、client 留著。
  • 測試 25 個（不需硬體）加 7 個（需綁定），3 組換算向量；實作前 21 個紅。
  • 沒有實測：非 0 電流經 driver 讀出、INA219 斷電後 probe 的寫入、讀屬性途中 I2C 失敗。
  • 沒有查證：shunt 電阻值（0.01 Ω 是範例註解的假設）。

這一步的 userspace 介面（/sys/bus/i2c/devices/7-0041/bus_mv 這些檔名）是 driver 自己發明的，別的程式得先知道這個 driver 才會讀。下一章 Step 8 把它接到 Linux 標準的 hwmon subsystem：同樣的讀取與換算，改由 /sys/class/hwmon/hwmonX/in1_input、curr1_input、power1_input 提供，sensors 這類通用工具就認得；也要測重複讀 1000 次、I2C 錯誤時回 errno、卸載後不留 stale node。

1. 沒載入 edge_ina219.ko 時，/sys/bus/i2c/devices/7-0041 存在嗎？為什麼？

存在（裝了 overlay 的話）。client 是 I2C core 在開機時依 DT 節點建立的，和 driver 無關；只是目錄裡沒有 driver 連結和屬性檔。

2. driver 綁定後，為什麼 i2cget 失敗而 ina219_raw 可以讀？

i2cget 先 ioctl(I2C_SLAVE, 0x41)，i2c-dev 發現 0x41 已被 driver 綁定就回 EBUSY。ina219_raw 用 I2C_RDWR，位址寫在每個 message 裡，i2c-dev 不做這個檢查。

3. 有人在 driver 綁定時把 Calibration 改成 13434，current_ua 會算錯嗎？

不會算錯。read_calibrated() 每次都從晶片讀 Calibration，用讀到的值算 Current_LSB，和 ina219_raw 一樣。換了 Calibration，Current register 的值和 Current_LSB 一起變，乘起來的電流不變（只差解析度）。

4. 0x45 的 client 為什麼能和 edge_ina219 配對？它沒有 DT 節點。

腳本寫 echo edge_ina219 0x45 > .../new_device，client 的名字是 edge_ina219；driver 的 id_table 有這個名字，I2C core 就用名字配對並呼叫 probe。probe 讀不到 Config，回 -EREMOTEIO，所以不綁定。
