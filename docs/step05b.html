按下按鍵，叫醒睡著的 read()

Step 4 的 LED 是輸出：userspace 說亮就亮。這一步反過來接一顆按鍵當輸入，而且 userspace 不去一直問「按了沒」，而是呼叫 read() 之後睡著等。按下的那一刻，GPIO 觸發中斷，driver 把事件放進佇列，再用 wake_up_interruptible() 叫醒睡在 wait queue 上的 reader。沒有按鍵時，這個程式 3 秒用掉 0 個 CPU tick。

5b.1起點為什麼

不要一直問，按了再叫我

最直覺的寫法是迴圈裡一直讀 GPIO：讀到 0 就是按下。問題是要多久讀一次？讀太慢會漏掉短按，讀太快就是 CPU 一直空轉，大部分時間都在問「按了沒？沒有。按了沒？沒有。」

Linux 的做法是讓硬體主動通知：GPIO controller 偵測到電位變化（邊緣）時發出中斷，CPU 暫停手邊的事去執行 driver 的 IRQ handler。另一邊，userspace 的 read() 在 driver 裡找不到事件時，就把自己掛在一個 wait queue 上睡覺，排程器不再分 CPU 給它；事件來了，driver 叫醒這個 queue 上的人，read() 才返回。

同樣的事其實完全可以在 userspace 做：GPIO character device 本身就支援邊緣事件，請求 line 時要求 rising / falling 並設 debounce，對 line 的 fd 呼叫 read() 一樣會睡，事件裡也有時間戳和序號。那一版是 Step 5-a（學習順序排在這章前面）；它背後的 IRQ handler、佇列、wait queue 是 kernel 的 gpiolib-cdev 寫好的。這一章刻意把這些在自己的 driver 裡親手寫一遍。實務上要做成 kernel driver，通常是因為事件要交給其他 kernel 子系統（例如 gpio-keys 把按鍵變成鍵盤輸入），或 policy 必須留在 kernel 裡。

互動雙方：硬體端是按鍵和 GPIO controller（中斷來源），中間是我們的 kernel driver edge_button.ko（處理中斷、排事件），另一端是 userspace 的 edge_button_wait（blocking read()）。kernel 這邊沒有 master / slave 的匯流排關係，是「硬體通知 driver、driver 通知 reader」。這一步不做：poll() / select()（Phase 8 的 Step 19）。

IRQ
中斷請求。GPIO controller 偵測到邊緣時發出，CPU 跳去執行登記好的 handler。每個中斷源有一個號碼，這次是 278（/proc/interrupts 看得到）。
邊緣（edge）
電位從低變高（rising）或從高變低（falling）的那一瞬間。這個 driver 兩種都要：按下是一個邊緣，放開是另一個。
hard IRQ context
IRQ handler 執行的環境：它打斷了別人，不屬於任何 process，不能睡：不能等鎖、不能配會等待的記憶體、不能用名字帶 _cansleep 的 GPIO 函式。
彈跳（bounce）
機械按鍵的金屬片碰上的瞬間會彈幾下，一次按壓可能產生好幾個邊緣。實測一次按壓 2～4 個 IRQ。
debounce
去彈跳。這裡的做法：每個邊緣都把計時器往後推 20 ms，等訊號安靜 20 ms 之後才讀一次電位。
delayed work
「一段時間後，在 process context 執行這個函式」。kernel 的 workqueue 執行緒會跑它，所以裡面可以睡。
wait queue
一串正在等某個條件的 process。wait_event_interruptible() 把自己掛上去睡，wake_up_interruptible() 叫醒它們重新檢查條件。
kfifo
kernel 內建的環形佇列。這裡放最多 16 筆按鍵事件。
5b.2路徑按下 → read()

一次按壓的六站

為什麼要分三段？IRQ handler 打斷了 CPU 上正在跑的東西，越快返回越好，而且不能睡；讀 GPIO 的 gpiod_get_value_cansleep() 名字就寫明了可能會睡。所以 handler 只記一筆、排一個延後的工作，讀電位留給可以睡的 work 去做。延後 20 ms 正好順便做了 debounce（5b.5）。

5b.3接線TXB0108

為什麼 Jetson 的按鍵比 STM32 多一顆電阻

按鍵本身只是兩片金屬，按下導通、放開斷開，不會產生 0 或 1。放開時 GPIO 腳要有東西把它「拉」到一個確定的電位，這就是上拉電阻。在 STM32 上設 GPIO_PULLUP，用的是晶片內建的電阻，因為 header 的腳直接連到晶片。第一版 overlay 也照這個想法，開了 SoC pad 的內部上拉（nvidia,pull = <TEGRA_PIN_PULL_UP>），pinconf 也確實顯示 pull=2。結果：

  • 放開時 pin 讀到 0；probe 時 dmesg 就印出 pressed。
  • 按了 30 多秒，irq_count=0：一個邊緣都沒有。
  • 把按鍵拔掉，pin 33 什麼都不接，gpioget 也讀到 0。（Step 5-a 後來發現：請求 line 之後約 20 ms 內 pin 一律讀到 0，單次 gpioget 就是在這段時間讀的，所以這一條不能當證據。前兩條是 driver 持有 line 好幾秒時的結果，不受影響。）

原因在載板。Orin Nano devkit 載板規格書（SP-11324-001 v1.3，Table 3-3）的 40-pin 表，pin 33 那一列是 GPIO13 … PH.00 … ±20uA … z … Note 3，Note 3 寫著：「These pins connect to TI TXB0108 level translators. Due to the design of these devices, the output drivers are very weak…」。SoC 是 1.8 V、header 是 3.3 V，中間隔了一顆電平轉換晶片。整張表裡，除了 I2C 的 pin 3/5/27/28，所有 GPIO 都是這樣。

電阻要多小？

按下再放開的那一瞬間，TXB 兩側都還記得「低」，B 側的 buffer 用約 4 kΩ（TI 的典型值）往下拉。上拉電阻 R 和這 4 kΩ 拔河，形成分壓：

放開瞬間的 pin 電壓 = 3.3 V × 4 kΩ / (4 kΩ + R)
TXB 要認成「高」：  > 0.65 × 3.3 V ≈ 2.15 V
上拉電阻 R放開瞬間結果
51 kΩ（照規格書「> 50 kΩ」）0.24 V卡在 0
10 kΩ0.94 V卡在 0
2.2 kΩ2.13 V門檻邊緣
1.5 kΩ2.40 V可以
1 kΩ2.64 V可以
330 Ω（這次用的，原本是 LED 的限流電阻）3.05 V可以，實測通過
放開瞬間 3.05 V　門檻 2.15 V　翻回 1計算，非實測

這張表是推論：4 kΩ 和 0.65 × VCC 是 TI 的典型值，我沒有量過這台板子上的實際數字。但它和三篇論壇回報對得上：有人在 Orin Nano 用 10 k～150 kΩ 都失敗、「放開後約 1 V」（表上 10 kΩ 是 0.94 V）；有人在同樣用 TXB0108 的 Jetson Nano 上加 1.5 kΩ 就好了；用 51 kΩ 的那篇回報會卡在低電位。最後用手邊的 330 Ω 實測：放開 1、按下 0、放開又回到 1，驗收全過。

規格書確實寫著「上拉 / 下拉要 > 50 kΩ」。那條規定保護的是 pin 當輸出的時候：太強的上拉會和 TXB 的 buffer 拉扯，讓 Jetson 輸出的低電位不夠低。按鍵 pin 只當輸入，我們要的正是「拉贏 TXB」，所以刻意偏離。按下時 330 Ω 的電流是 10 mA，3.3 V 電源（1 A）和電阻都承受得了。

為什麼是 pin 33

第一版選的是 pin 31（PQ.06），只因為它和 LED 的 PQ.05 是同一個 port、編號相鄰。實體上 pin 31 和最近的 GND（pin 34）是斜對角，pin 33 和 34 才是左右並排，按鍵直接跨上去就好。至於「直接接 SoC、模組上已有上拉」的 I2C pin：27/28 是 i2c-1，上面有板上的電源監測 ina3221 和 USB-C 控制器 fusb301，不能挪用；3/5 是 i2c-7，留給 Phase 3 起的 INA219、OLED、STM32。完整接線見 hardware-wiring.md。

接好之後用 Step 5-a 的 userspace 程式確認，不需要 root（使用者在 gpio 群組即可）、也不需要載入 driver（載入時 line 43 被它佔用，這個程式會拿到 busy）。執行後按兩下按鍵：

./build/edge_gpio_button 4
ignored 1 edge(s) while the line settled
seq=1 pressed t=1396.230767131
seq=2 released t=1396.393764653
seq=3 pressed t=1397.585802443
seq=4 released t=1397.750802063

（2026-10-10 實測，重開機後、沒有載入 driver。）每按一下要有一筆 pressed、一筆 released；完全沒有輸出，就是上拉不夠，或四腳按鍵接到同一側、內部永遠導通的兩支腳。第一行的原因見 5-a。不要用單次 gpioget gpiochip0 43 確認：它在請求 line 後立刻讀，放開時也常常讀到 0（5-a 實測）。

5b.4overlayfragment@2/3

同一份 overlay，多一個節點

按鍵節點直接加在 Step 4-b 那份 dts/edge-gpio-overlay.dts 的尾端，沿用同一支 installer、同一次重開機。形狀和 LED 一模一樣：一個裝置節點、一組 pad 設定。

  • compatible = "edge,gpio-button" 配對新的 driver edge_button.ko；LED 的 edge_gpio.ko 不受影響。
  • TEGRA234_MAIN_GPIO(H, 0) = 7 × 8 + 0 = 56（binding header 裡 PORT_H = 7）。gpiochip0 裡則是 line 43：和 4-b 說的一樣，DT 編號和 line 編號不同。
  • GPIO_ACTIVE_LOW：按下是低電位，宣告成 active-low 之後，driver 讀到的邏輯值 1 就是「按下」，C code 裡不用自己反相。
  • pad：tristate 開（pad 不輸出，萬一 GPIO 被設成輸出也不會在按下時短路）、enable-input 開（要讀腳位）。內部上拉留著不礙事，但真正的上拉是外接電阻（5b.3）。

反組譯確認編號，在 repo 根目錄執行（不需要 root）：

make -C dts
dtc -q -I dtb -O dts dts/edge-gpio-overlay.dtbo | grep -m1 -A4 'edge-button {'
			edge-button {
				compatible = "edge,gpio-button";
				button-gpios = <0xffffffff 0x38 0x01>; «1»
				pinctrl-names = "default";
				pinctrl-0 = <0x02>;
  1. 10x38 = 56，flags 0x01 = active-low；第一格是等開機時由 __fixups__ 填入的 &gpio phandle（4-b 詳述）。dtbo 從 999 bytes 變成 1589 bytes。

改完 overlay 要重新安裝並重開機（4-b 的 4b.4）：

sudo python3 scripts/install_edge_gpio_overlay.py install dts/edge-gpio-overlay.dtbo

重開機後 ls /proc/device-tree/edge-button 應該看到 button-gpios compatible name pinctrl-0 pinctrl-names。

5b.5IRQdebounce

IRQ handler 只做兩件事，讀電位交給 work

driver 的狀態全放在一個 struct 裡，probe 時配置：

中斷進來時執行的就是這個函式。整個函式只有兩行實際動作：

  • delayed_work_pending() 是假的話，代表這是一串彈跳的第一個邊緣，記下 ktime_get_ns() 當事件的時間戳：真正按下的時刻。第一版在 work 裡才取時間，比按下晚 20 ms 以上（code review 指出後修正）。
  • atomic_inc()：原始邊緣數，含彈跳。用 atomic 是因為 sysfs 的讀取可能同時發生，而 handler 裡不能拿會睡的鎖。
  • mod_delayed_work()：如果 work 還沒排，就排在 20 ms 後；如果已經排了，就把時間改成從現在起 20 ms。所以彈跳期間每個邊緣都把期限往後推，work 只會在訊號安靜 20 ms 之後執行一次。
  • 回傳 IRQ_HANDLED 告訴 kernel 這個中斷有人處理了。

修正前後的實測時間戳可以看出差別。這台 CONFIG_HZ=250，delayed work 的計時器只在 4 ms 一次的 tick 上觸發。修正前（work 裡取時間）的 14 個時間戳，毫秒數除以 4 的餘數全都在 0.022～0.051 ms，例如 483.596029563：每一個都落在 tick 之後幾十微秒。修正後（IRQ 裡取時間）的 12 個，餘數分散在 0.9～4.0 ms，例如 3667.401418590：那是手指按下的隨機時刻。

20 ms 後，workqueue 執行緒跑這個函式。它在 process context，可以呼叫會睡的 GPIO 函式：

  • 一開頭先讀出 IRQ 記的 edge_ns，再讀電位：讀電位可能會睡，這段時間如果又開始一串新的彈跳，edge_ns 會被改成新的時間。
  • gpiod_get_value_cansleep() 回傳邏輯值：DT 寫了 active-low，所以按下（實體低電位）讀到 1。
  • val == eb->last：彈跳結束後電位回到原本的狀態（例如很短的雜訊），就不產生事件。所以按一下一定是 pressed、released 各一筆，不會連續兩筆 pressed。
  • seq 每次狀態改變都加一，不管有沒有放進佇列，也不管有沒有人開著裝置。佇列滿了，kfifo_put 回 0，事件被丟掉，dropped 加一：同一次 open 之內，reader 看到 seq 從 7 跳到 9，就知道中間掉了一筆。
  • 沒有人開著裝置時不排事件（test_bit(EDGE_BUTTON_OPEN, …)）：不然昨天按的十下會在今天打開時一口氣湧出來。
  • 最後 wake_up_interruptible() 叫醒睡在 eb->wq 上的 reader。

鎖用 spinlock 而不是 mutex：保護的只是幾個欄位的讀寫，持有時間很短。work 和 read() 都在 process context，用一般的 spin_lock() 就夠；IRQ handler 完全不碰這些欄位（它只寫 edge_ns，用 WRITE_ONCE / READ_ONCE，以及 atomic 的 irq_count），所以不需要關中斷的 spin_lock_irqsave()。

5b.6read()wait queue

read() 沒有事件就睡

  • buffer 小於 16 bytes 回 EINVAL：一筆事件不能拆成兩次讀。一次 read() 只回一筆，給再大的 buffer 也一樣。
  • O_NONBLOCK：用非阻塞模式開檔的人不想睡，沒有事件就回 EAGAIN。
  • wait_event_interruptible(wq, 條件)：條件不成立就把自己掛到 wq、狀態設成可中斷睡眠（ps 看到的 S），讓出 CPU。被 wake_up_interruptible() 叫醒後重新檢查條件，成立才返回 0。收到 signal 會提早返回非 0（-ERESTARTSYS），這裡直接往上傳：userspace 沒有用 SA_RESTART 的話就看到 EINTR。
  • 醒來後回到迴圈頂端重新 kfifo_peek：醒來不保證佇列裡一定有東西，所以「看」和「等」寫成迴圈。
  • 先 peek、複製成功才 kfifo_skip：userspace 給了壞的 buffer（EFAULT）時，事件還留在佇列裡，下一次 read() 拿得到。第一版是先 kfifo_get 取出再複製，失敗就丟了（code review 指出）。這條路徑要先有一筆事件才測得到，需要人按，所以沒有自動測試。
  • read_lock（mutex）：獨占 open 只擋得住第二次 open，擋不住同一個 fd 被兩個執行緒同時讀。兩邊 peek 到同一筆、各 skip 一次，就會重複一筆、跳過一筆。peek 到 skip 之間只允許一個人。這裡用 mutex 而不是 spinlock，因為中間的 wait_event_interruptible() 和 copy_to_user() 都可能睡。

只允許一個 reader：兩個程式同時讀，一筆事件只會被其中一個拿走，兩邊都看到殘缺的序列。第二個 open() 回 EBUSY，比默默分走事件好除錯。test_and_set_bit() 是原子操作，兩個 open 同時進來也只有一個成功。

事件格式與語意

和 Step 3 的 ioctl header 同一個原則：只用固定大小的型別，64-bit 欄位放最前面，32-bit 和 64-bit 程式看到的排列完全一樣。靜態測試用 C 和 C++ 各編一次，static_assert 大小是 16、offset 是 0／8／12。

情況會收到什麼
時間戳一串彈跳的第一個邊緣（IRQ 時記錄），不是 20 ms 後 work 執行的時間
按一下pressed、released 各一筆，seq 連號
長按一筆 pressed，放開時一筆 released；中間沒有重複事件（不像鍵盤會連發）
短於 20 ms 的點按、彈跳可能被合併掉；電位最後回到原狀就不產生事件
按太快，佇列（16 筆）滿了新事件被丟掉、dropped 加一，seq 照算，所以 seq 會跳號
沒有人開著裝置時按不排事件（seq 照算，所以兩次 open 之間的 seq 不連號，那不是遺失）；open() 時佇列清空
按住按鍵時才 open()第一筆是 released（按下那筆發生在 open 之前）
第二個程式同時 open()EBUSY。節點是 0444，所以任何使用者都能開著不放、讓真正的 reader 拿不到（已知限制，見下）
reader 正在睡時 rmmodrmmod 被拒（.owner 讓開著的檔案持有 module）；reader 要靠 signal 離開

最後一列是規劃裡「driver unload 時要安全終止等待者」的答案：只要檔案開著，module 就卸載不掉，所以 remove() 執行時不可能有人睡在 wait queue 上；sysfs 手動 unbind 則和 4-b 一樣用 suppress_bind_attrs 關掉。驗收腳本兩件事都會測。

已知限制（code review 指出）：kernel 裡的 misc device 只能設 mode、不能設群組，所以這裡是 0444 加獨占 open。對照 /dev/gpiochip0 是 root:gpio 0660，只有 gpio 群組能用。要比照它，需要一條 udev rule（GROUP="gpio", MODE="0440"）。這排進 Phase 10 的 Step 26，和 module 的打包、modules-load.d 一起做。開發板只有一個使用者，暫時沒有影響。

5b.7probe順序

probe：先準備好接中斷的東西，最後才開中斷

  • devm_gpiod_get(dev, "button", GPIOD_IN)：去 DT 找 button-gpios，拿到時就設成輸入。
  • 順序很重要：devm_request_irq() 一成功，中斷隨時可能進來，handler 會用到 work；所以 spinlock、wait queue、kfifo、work 都要在它之前初始化好。
  • 初始狀態在登記 IRQ 之後才讀：第一版先讀再登記，兩者之間如果剛好按下，那個邊緣沒有中斷，last 卻已經是舊值；之後放開時 work 讀到的值等於 last，整組 pressed / released 就默默消失，seq 也沒有缺口（code review 指出）。改成登記之後才讀，從那一刻起每個邊緣都會在 20 ms 後重新比對，不會漏。讀電位可能會睡，所以先讀進區域變數，再在 spinlock 裡寫入 last。
  • devm_add_action_or_reset() 登記一個「卸載時呼叫 cancel_delayed_work_sync()」的動作。devm 的資源在 remove 之後倒序釋放：這個動作登記在 IRQ 之前，所以會先釋放 IRQ（不會再有新的 work 被排），再取消、等完還在跑的 work。順序反過來的話，work 取消之後 IRQ 還可能又排一個，在 eb 被釋放後執行。
  • gpiod_to_irq()：把 GPIO descriptor 換成中斷號碼（這次 278），不用自己查。IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING：按下、放開都要。
  • 初始狀態也印在 dmesg。第一次驗收印出的是 pressed，那時 pin 卡在 0（5b.3），看 dmesg 第一行就知道接線有問題。
  • 節點權限 0444：這個裝置只能讀（限制見 5b.6 的方框）。mutex_init() 放在 misc_register() 之前，節點一出現就可能有人 read。

規劃寫的是 request_threaded_irq()：中斷進來先跑一個很短的 hard handler，再由專屬的 kernel 執行緒跑可以睡的部分。這裡改用一般的 devm_request_irq() 加 delayed work，因為 debounce 本來就需要「最後一個邊緣後再等 20 ms」：threaded IRQ 的執行緒在每個中斷後立刻執行，要延後只能在裡面睡，每次彈跳都會各睡一輪；delayed work 則可以用 mod_delayed_work() 不斷把期限往後推。kernel 自己的 gpio-keys driver 也是用 delayed work 做 debounce。

此外還有三個唯讀的 sysfs 屬性，掛在 platform device 上（/sys/bus/platform/devices/edge-button/）：irq_count（原始邊緣數）、event_count（debounce 後的狀態變化數，就是目前的 seq）、dropped。兩個數字一比，就看得出彈跳被合併了多少。

5b.8userspaceC++

userspace：一個 read() 迴圈

  • read(fd, &ev, sizeof(ev))：就是規劃裡那一行。沒有事件時這個呼叫不會返回，程式不佔 CPU。
  • sigaction 沒有設 SA_RESTART：Ctrl-C 或 kill 時，睡著的 read() 回 -1、errno == EINTR，程式印 interrupted 結束（結束碼 1）。如果用 std::signal()，glibc 預設會自動重啟 read()，程式就醒不過來。
  • handler 設旗標，每次 read() 前檢查：signal 不一定落在 read() 裡。第一版的 handler 是空的，如果 signal 剛好在印輸出時到達，處理完就沒了，下一次 read() 照樣睡下去，驗收腳本的 timeout 就可能永遠等不到它結束（code review 指出）。檢查旗標和進入 read() 之間仍有極小的空隙，所以腳本的 timeout 也加了 -k 2：2 秒後還沒結束就送 SIGKILL。
  • 結束碼：讀滿 N 筆回 0；裝置錯誤或被中斷回 1；參數錯誤回 2。EDGE_BUTTON_DEV 可以換裝置路徑，給測試用。

用 CMake 建置，在 repo 根目錄執行（不需要 root）：

cmake -S . -B build && cmake --build build --target edge_button_wait
5b.9測試red → green

不按按鍵能測的，都先寫成測試

  • tests/test_edge_button_static.py：26 個案例，不需要硬體。overlay 用 cpp + dtc 實際編譯再反組譯：兩個 dtbo 都有 edge-button 節點、button-gpios 是 56 加 flags 1、&gpio 留成 fixup、pad 狀態是 soc_gpio21_ph0 的 pull=2 / tristate=1 / input=1、pad 名稱和 /boot 裡 NVIDIA 自家 overlay 的 pin 33 一致、LED 節點還在。driver 原始碼：of_match、devm_gpiod_get(dev, "button", GPIOD_IN)、gpiod_to_irq 加雙邊緣、hard IRQ handler 的函式本體裡不能有會睡的呼叫（_cansleep、mutex_lock、GFP_KERNEL…）、有 wait queue 和 O_NONBLOCK、有 cancel_delayed_work_sync、沒有舊式整數 GPIO API、有 suppress_bind_attrs。header 在 C 和 C++ 下各編一次檢查大小與 offset。edge_button_wait 的用法錯誤回 2、找不到裝置回 1，再用一個 named pipe 假裝成 /dev/edge_button：寫進兩筆 16 bytes 的事件，檢查印出來的格式；睡在 read() 時送 SIGTERM 要印 interrupted；讓 stdout 的 pipe 塞滿、程式卡在印輸出時送 SIGTERM，排空之後 3 秒內一定要結束。
  • tests/test_edge_button_device.py：8 個案例，對真的 /dev/edge_button，不需要有人按：權限 0444、O_NONBLOCK 沒事件回 EAGAIN、buffer 小於 16 回 EINVAL、第二個 open 回 EBUSY、關掉後能再開、blocking read 1.5 秒內用掉的 CPU 少於 0.1 秒並被 signal 打斷、打斷後 fd 還能用、三個 sysfs 計數器讀得到。裝置不存在時 skip；EDGE_BUTTON_REQUIRE=1 時改成 fail。

紅燈紀錄：實作前靜態測試 17 個 failure、2 個 error；device 測試在 EDGE_BUTTON_REQUIRE=1 下 8 個 failure。「LED 節點還在」和「pad 名稱和 NVIDIA 一致」在實作前就會過，只能當守門測試。後來把 pin 31 改成 pin 33 時，也是先改期望值、看到 3 個 failure，再改 overlay。變異測試：flags 改成 active-high、編號改錯、tristate 關掉、上拉拿掉、pad 名稱寫錯、在 IRQ handler 裡呼叫 gpiod_get_value_cansleep、改用不等待的 cancel_delayed_work、只留 falling、header 的欄位型別改掉，每一種都讓測試失敗。

code review 後補的 6 個案例：初始狀態要在 IRQ 之後讀、read 要先 peek 再 skip、時間戳要在 IRQ handler 裡取、signal 落在兩次 read 之間不能遺失，這 4 個先紅再修；named pipe 的格式和「睡在 read 時被打斷」2 個在修之前就會過，是守門測試。驗收腳本的快速連按改成：佇列滿時，缺的 seq 數目要等於 dropped 的增量（第一版只看 dropped > 0，比 baseline 寫的容差寬鬆）。

5b.13收尾Phase 2 → 3

這一步做到了什麼

  • 按下按鍵 → IRQ → driver → wake_up_interruptible() → 睡著的 read() 返回；等待時 0 CPU tick。
  • 按一下一筆 pressed、一筆 released；長按不重複；快速連按 39 筆交替、seq 連號；debounce 把 52 個 IRQ 合併成 46 次狀態變化（code review 修正後重跑）。
  • reader 睡著時 rmmod 被拒，signal 能叫醒它；卸載後 GPIO、IRQ、節點都釋放；驗收 0 failure。
  • 沒有實測：佇列滿（dropped 增加、seq 跳號）只有程式邏輯；copy_to_user 失敗時事件留在佇列（review 後的新行為）沒有測試。
  • 5b.3 的電阻計算用的是 TI 典型值，沒有量測 TXB 的實際 buffer 強度；330 Ω 偏離規格書的「> 50 kΩ」（理由見 5b.3）。
  • LED 為了接按鍵已經拆除；重跑 Step 4 的驗收要先接回。
  • 新增約 1031 行，超過約 800 行的上限：實作前估約 775 行，又一次把測試和驗收腳本估低了。原本叫 Step 5，驗收後改名 5-b，另補 userspace 版的 5-a 對照。

Phase 2 到這裡結束：GPIO 輸出（LED）和輸入加中斷（按鍵）都由 Device Tree 描述、descriptor API 取得。Phase 3 換到 I2C：Step 6 先不寫 driver，用 userspace 工具確認 INA219 電流感測器接在 pin 3/5 的 i2c-7 上、讀得到暫存器，再進 kernel。

1. 為什麼 IRQ handler 裡不能直接呼叫 gpiod_get_value_cansleep() 讀電位？

handler 在 hard IRQ context 執行，不能睡；_cansleep 版本可能會睡（例如 GPIO 在 I2C 擴充晶片上時要等匯流排）。所以 handler 只排 work，在 work 裡讀。靜態測試會檢查 handler 的本體裡沒有這類呼叫。

2. 一次按壓彈跳了 5 個邊緣，為什麼只有一筆 pressed？

每個邊緣都用 mod_delayed_work() 把 work 的期限推到「現在 + 20 ms」，所以 work 只在最後一個邊緣之後安靜 20 ms 時執行一次；它讀到 1，和上次的 0 不同，才產生一筆事件。

3. reader 睡在 read() 裡時執行 rmmod edge_button，會發生什麼？怎麼讓 reader 離開？

rmmod 失敗（module 使用中）：開著的檔案透過 .owner = THIS_MODULE 持有 module 的參考。送 signal（Ctrl-C、kill）給 reader，wait_event_interruptible() 返回非 0，read() 回 EINTR，程式關檔之後 rmmod 才會成功。

4. 把上拉電阻從 330 Ω 換成 10 kΩ，第一次按下和放開會看到什麼？

（推算，沒有實測。）按下時 pin 被直接接地，TXB 翻成低；放開時 10 kΩ 和 TXB 約 4 kΩ 的 buffer 分壓只有約 0.94 V，低於 2.15 V 的門檻，TXB 繼續保持低電位，所以收不到 released，之後也不會再有事件。如果開機時 TXB 就停在低電位，連第一個 pressed 都不會有。驗收腳本的「按一下」會因為少了 released 而 FAIL。
