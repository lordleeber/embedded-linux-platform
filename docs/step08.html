INA219 接上 hwmon

Step 7 的 edge_ina219 已經會讀晶片、會換算，但交給 userspace 的是它自己取名的五個檔（bus_mv、current_ua…），別的程式要先認識這個 driver 才讀得懂。這一步讀取與換算的部分一行都沒改，只換掉交出數值的方式：driver 向 hwmon subsystem 註冊「我有兩個電壓、一個電流、一個功率」，/sys/class/hwmon/hwmonN/ 底下的檔名、單位、格式都由 kernel 規定，和這台板子上 NVIDIA 的 ina3221 是同一套。驗收除了讀得到值，還要證明出錯時回 errno、卸載後不留舊的檔案。

8.1起點為什麼

值是對的，介面是私有的

Step 7 結束時，cat /sys/bus/i2c/devices/7-0041/bus_mv 已經能讀到和 ina219_raw 一致的電壓。問題在路徑和檔名：想顯示電池狀態的程式得知道「這台有個叫 edge_ina219 的 driver、它掛在 7-0041、電壓檔叫 bus_mv、單位是 mV」。換一顆晶片、換一個 driver，這些全部要重學。Linux 對「量電壓、電流、溫度、風扇轉速的晶片」早就有一套共同的介面，叫 hwmon：每個裝置一個 /sys/class/hwmon/hwmonN 目錄，檔名和單位由 kernel 文件 Documentation/hwmon/sysfs-interface.rst 規定。通用程式只要掃這個目錄，不必認識任何 driver。

互動雙方：和 Step 7 相同，controller 是 c250000.i2c（i2c-7），target 是 UPS 模組上的 INA219（0x41），DT 節點、probe 寫入的 Calibration / Config 都沒變。多出來的一方是 kernel 的 hwmon core（drivers/hwmon/hwmon.c）：它替 driver 建 sysfs 檔，有人讀檔時再回頭呼叫 driver。這一步不做：OLED（Phase 4）、任何依電量做決定的 application policy（Phase 9）；也不做 hwmon 的 alarm、shunt_resistor、update_interval。

hwmon
hardware monitoring subsystem。driver 註冊後得到一個 class device hwmonN（N 依註冊順序），底下的 name 檔是 driver 給的名字。
channel
同一種量測的第幾路。電壓叫 in、電流 curr、功率 power；檔名是「種類 + 編號 + _ + 屬性」，例如 in1_input 是第 1 路電壓的讀值、in1_label 是它的名字。電壓從 0 編號，電流和功率從 1 編號（文件規定）。
hwmon_chip_info
driver 交給 hwmon core 的描述：有哪些 channel、每個 channel 有哪些屬性（HWMON_CHANNEL_INFO），以及讀取時要呼叫的函式（hwmon_ops）。hwmon core 依它產生檔案，driver 不必自己寫 show 函式。
devm_
device-managed：用 devm_ 開頭的函式申請的資源，在這個 device 和 driver 解除綁定時由 driver core 自動釋放（4-b 的 devm_gpiod_get() 是同一套）。
stale node
裝置已經不在、檔案卻還留著（或讀到舊值）的 sysfs / /dev 節點。
ENODATA / ENODEV
errno：「沒有資料」（這一章用在 Calibration 為 0、晶片算不出電流時）／「裝置不存在」（檔案打開後裝置被移除，sysfs 回這個）。

8.4宣告chip_info

告訴 hwmon core 有哪些 channel

  • HWMON_CHANNEL_INFO(in, …, …)：兩項，代表電壓有 channel 0 和 1，每路都有 INPUT（讀值）和 LABEL（名字）。hwmon core 據此產生 in0_input、in0_label、in1_input、in1_label。
  • in0 = shunt、in1 = bus：hwmon 沒規定哪路是什麼，這裡照上游 ina2xx driver 的順序，讀過那個 driver 的人不必重新對照。label 寫出 shunt / bus，就不必猜。
  • HWMON_CHANNEL_INFO(curr, HWMON_C_INPUT)：一項，產生 curr1_input（電流從 1 編號，所以第一項是 1）。功率同理，產生 power1_input。
  • 沒寫進去的就沒有檔案：不宣告 HWMON_C_MAX，就不會有 curr1_max。device 測試 test_only_the_declared_channels 確認目錄裡只有這六個 channel 檔。

每個檔案的權限由 is_visible 回答。這個 driver 全部唯讀，所以一律回 0444；有可寫屬性（例如 alarm 門檻）的 driver 才需要依 attr 分開回答：

8.5讀取read callback

一個函式回答所有讀值

  • dev_get_drvdata(dev)：這裡的 dev 是 hwmon 裝置，不是 I2C client。註冊時把 client 當成 drvdata 交給 hwmon core（8.6），這裡再取回來，後面就是 Step 7 的 helper。
  • channel ? read_bus_voltage : read_shunt_voltage：hwmon_in 有兩路，用 channel 分。attr 不用看：每路只宣告了 INPUT 一種數值屬性，LABEL 走另一個 callback（read_string，回傳 "shunt" / "bus"）。
  • 錯誤直接 return：I2C 失敗時 helper 回負的 errno（例如 -EREMOTEIO），這裡原樣交出去，hwmon core 再交給 read()，cat 印出錯誤訊息。函式裡沒有任何地方記住上一次的值，所以不可能「讀不到就給舊值」。Calibration 為 0 時 read_calibrated() 回 -ENODATA（Step 7 就有），8.7 用它實際走一次這條路。
  • default: return -EOPNOTSUPP：hwmon core 只會用 chip_info 宣告過的種類呼叫，這行照理到不了，是防呆。

單位換算放在 Step 7 的共用 header，多了兩個函式。hwmon 規定 in*_input 是 mV、curr*_input 是 mA，而 INA219 的 shunt 一格 10 µV、電流一格約 0.152 mA，都比整數 mV / mA 細，必須捨去或進位：

  • 為什麼四捨五入、而不是直接整數除法：C 的整數除法往 0 截斷，−6.99 mV 會變成 −6。上游 hwmon driver 普遍用 kernel 的 DIV_ROUND_CLOSEST()；這份 header 也要在 userspace 編譯，不能用 kernel 的巨集，所以自己寫了一個同樣規則的 edge_ina219_div_round()。
  • 電流直接從 raw 算到 mA：40960000 µA 除以 1000 是 40960，整除，所以 edge_ina219_current_ma() 不先算出 µA 再捨入，避免捨入兩次。
  • 功率不另外捨入：hwmon 的功率單位是 µW，Step 7 的 edge_ina219_power_uw() 原樣使用。它的整數除法同樣往 0 截斷，但 Power register 一格約 3049 µW，截掉的不到 1 µW，四捨五入也只差這 1 µW；上游 ina2xx 的功率也是整數相乘、不做捨入。

新的向量在 tests/test_edge_ina219_conv.cpp：6-b 放電實測的 0xFD9B（−6.130 mV）要變成 −6、0xF04B（−612.997 mA）要變成 −613；6.50 / −6.50 / 6.49 mV 三個邊界；另外對 65536 個值 × 4 個 Calibration 檢查「mV / mA 結果和 µV / µA 結果差不超過半個單位」。把捨入改成截斷、只往正向進位、shunt 當無號、常數少一個 0，四種改法都讓它失敗。在 repo 根目錄自己跑：

cmake -S . -B build >/dev/null && cmake --build build --target test_edge_ina219_conv >/dev/null && build/test_edge_ina219_conv
all edge_ina219_conv checks passed
8.6註冊probe()

probe 最後一步：註冊 hwmon，交給 devm 收尾

  • 放在最後：檔案一建立，userspace 就可能來讀，所以要等 Calibration / Config 寫好、讀回確認之後才註冊。probe 前面任何一步失敗，hwmon 裝置根本不會出現。
  • "edge_ina219"：成為 hwmonN/name 的內容。注意不是 client 名稱 edge-ina219：hwmon 的文件規定 name 不能有 -、空白等字元（libsensors 用 - 分隔晶片名稱）。這一步沒有試過用帶 - 的名字註冊會怎樣。
  • _with_info：這是目前建議的 API，driver 給 chip_info，hwmon core 產生檔案。舊的 hwmon_device_register() 要 driver 自己建屬性，靜態測試禁止使用。
  • devm_：hwmon 裝置和這次綁定同生共死。unbind、rmmod、甚至整條 I2C adapter 消失時，driver core 解除綁定，就自動 unregister，所以 remove() 裡什麼都不用寫，也不會忘了寫。8.7 的 unbind / bind 和 rmmod 驗的就是這件事。
  • dev_name(hwmon)：dmesg 的 probed: 那行多印出 hwmon4，方便對照是哪一個。
8.7錯誤errno 與 stale node

證明出錯時不回舊值、拔掉後不留檔案

phase03 對這一步列了三項驗證：讀 1000 次、I2C 出錯時回 errno、移除或卸載後不留 stale node。第一項是 device 測試的 test_1000_reads_of_every_input（四個檔各 1000 次）。後兩項寫進驗收腳本。

讓晶片「算不出來」：Calibration 寫 0

理想的測法是讓 I2C 傳輸在讀到一半時失敗。這台板子做不到：kernel 沒有 i2c-stub（CONFIG_I2C_STUB 沒開，它能模擬一顆 I2C 晶片）、也沒開 CONFIG_FAULT_INJECTION，而 UPS 模組正在供電給 Jetson，不能拔。能在實機上製造的錯誤是 Calibration = 0：INA219 上電時就是這個值，這時晶片不算電流與功率，driver 回 -ENODATA。它和 I2C 錯誤走的是同一段 if (ret) return ret;：

i2cset ... w 的值要 byte 對調，6-b 踩過這個坑：要寫進晶片的 Calibration 是 0x68F4，命令列上要寫 0xf468。腳本開頭的 cleanup 也會在中途中斷時寫回這個值。靜態測試 test_i2cset_only_zeroes_and_restores_calibration 確保腳本裡的 i2cset 只做這兩種寫入。

1. 為什麼 driver 裡找不到任何 sysfs_emit()，cat in1_input 卻讀得到 11764？

印字串的是 hwmon core。driver 的 edge_ina219_read() 只把 11764 填進 *val，hwmon core 依 chip_info 產生的屬性把它印成十進位加換行。

2. 為什麼 remove() 裡沒有 unregister hwmon，rmmod 後 hwmon 目錄還是會消失？

註冊用的是 devm_ 版本，hwmon 裝置是這個 client 綁定期間的資源；解除綁定時 driver core 會自動釋放它。

3. 晶片的 shunt 是 −6.66 mV，in0_input 應該印什麼？為什麼不是 −6660？

−7。hwmon 規定電壓單位是 mV，四捨五入（半數遠離 0）後是 −7；−6660 是 µV，那是 Step 7 私有屬性 shunt_uv 的單位。

4. 驗收腳本為什麼要用 pread 從 offset 0 讀，而不是對同一個 fd 再 read 一次？

第一次讀完後 offset 在檔尾，第二次 read 直接回 EOF，不會呼叫 driver，也就測不到移除後的行為。pread(fd, n, 0) 每次從頭讀，sysfs 才會再走一次讀取，這時裝置已不在，回 ENODEV。
