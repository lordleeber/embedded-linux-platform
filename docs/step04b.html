讓 Device Tree 描述 LED，driver 去找它

4-a 用 userspace 程式點亮了 pin 29，但 pad 是用 /dev/mem 硬改的，「這根腳接了 LED」也只寫在程式碼裡。這一步把硬體描述移到 Device Tree：一個 overlay 說「這裡有一顆 LED，接在 PQ.05，pad 要這樣設」，kernel 開機後依照 compatible 找到我們的 platform driver，在 probe() 裡拿到 GPIO，再開一個 /dev/edge_gpio 給 userspace 開關。換一根腳、換極性，只改 overlay，不改 C code。

userspace 程式 kernel 核心（platform bus、pinctrl、gpiolib、VFS） 我們寫的 driver 硬體（SoC、板子、麵包板） 資料與資料流向
4b.1起點為什麼

硬體描述不該寫死在程式裡

4-a 的 edge_gpio_blink 把「gpiochip0 的 line 105」寫死在 C++ 裡，pad 要另外用 root 跑 pad_pin29.py 打開。換一塊板子、LED 改接別根腳、改成反向接法，就得改程式、重新編譯，而 pad 的設定 kernel 完全不知道。

Linux 在 ARM 板子上的做法是把「板子上有什麼、接在哪裡」寫成 Device Tree，driver 只說「我認得哪一種裝置」。開機時 kernel 讀 Device Tree，為每個節點建立一個 device；platform bus 拿 device 的 compatible 去比對已註冊 driver 的清單，對上了就呼叫那個 driver 的 probe()。driver 在 probe() 裡向 kernel 要「這個 device 的 led GPIO」，拿到的已經是 DT 裡寫好的那根腳和極性。

互動雙方：controller 是 Jetson 上的 kernel driver edge_gpio.ko，target 是 GPIO controller 與 pin 29 的 pad，最後是麵包板上的 LED。userspace 只看到 /dev/edge_gpio：寫 1 亮、寫 0 暗。這一步不做：IRQ、按鈕（Step 5）。

Device Tree
描述硬體的一棵樹，編譯成二進位的 .dtb，開機時交給 kernel。每個節點描述一個裝置：它是什麼（compatible）、用到哪些資源（暫存器、GPIO、中斷）。
overlay
疊在原廠 .dtb 上的補丁（.dtbo）。不改原廠檔案，開機時由 bootloader 合併；kernel 看到的是合併後的樹，在 /proc/device-tree 可以查看。
compatible
一個字串，例如 "edge,gpio-led"，格式是「廠商,型號」。driver 的 of_match_table 列出它認得的字串，兩邊相同才會 probe。
platform driver
給「不在可自動偵測的 bus 上」的裝置用的 driver（不像 USB、PCI 插上去會自己報名）。裝置從 Device Tree 來，配對靠 compatible。
probe / remove
配對成功時 kernel 呼叫 probe()，driver 在這裡取得資源、建立介面；device 和 driver 分開時呼叫 remove()。
phandle
DT 裡節點的編號。&gpio 這種寫法編譯後變成「指向 GPIO controller 節點的 phandle」。
pinctrl state
4-a 用 devmem 改的那組 pad 設定，寫成 DT 節點。device 節點用 pinctrl-0 指向它，kernel 在 probe() 之前自動套用。
4b.2路徑開機 → LED

從開機到 LED 亮起的六站

和 4-a 相比，pad 的設定從「root 手動寫暫存器」變成第三站：kernel 在每次 probe 前依 DT 套用。driver 的 C code 裡完全沒有 pad、tristate 這些字。

4b.3overlay兩個 fragment

overlay：一個裝置節點、一組 pad 設定

overlay 的開頭先 include 三份 kernel 附的 binding header，把 GPIO 編號、極性、pinctrl 常數都寫成有名字的巨集：

/plugin/ 表示這是 overlay，不是完整的 DT。頂層的 compatible 是給 bootloader 看的：這份補丁只適用這個板型（和 /proc/device-tree/compatible 的第一個字串一致）。極性由編譯時的巨集決定，dts/Makefile 會同時編出 active-high 和 active-low 兩個版本。

  • fragment@0 疊到根節點 /，新增 edge-led 裝置。compatible = "edge,gpio-led" 是 driver 配對用的字串；led-gpios 有三格：哪個 controller（&gpio）、第幾根腳（TEGRA234_MAIN_GPIO(Q, 5)）、極性。屬性名稱的 led 會在 driver 裡出現（4b.5）。
  • fragment@1 疊到原廠的 pinmux 節點底下，新增一個 pad 狀態：和 4-a 的 devmem 改的是同樣三件事，tristate 關、input 關、不上拉。
  • pinctrl-names = "default" 加 pinctrl-0 = <&edge_led_pins> 把兩者連起來：這個裝置的 default 狀態就是那組 pad 設定。

編號 125 和 phandle 是怎麼解出來的

TEGRA234_MAIN_GPIO(Q, 5) 展開成 15 × 8 + 5 = 125（4-a 說過：DT 的編號一律把每個 port 當 8 支腳算，和 gpiochip0 的 line 105 不同）。&gpio 則是編譯時還不知道的值。在 repo 根目錄執行（不需要 root；dtc 由 device-tree-compiler 套件提供，Step 1 的環境檢查有確認）：

make -C dts
dtc -q -I dtb -O dts dts/edge-gpio-overlay.dtbo | grep -m1 -A4 'edge-led {'
dtc -q -I dtb -O dts dts/edge-gpio-overlay.dtbo | grep -A3 '__fixups__'
			edge-led {
				compatible = "edge,gpio-led";
				led-gpios = <0xffffffff 0x7d 0x00>; «1»
				pinctrl-names = "default";
				pinctrl-0 = <0x01>; «2»
	__fixups__ {
		gpio = "/fragment@0/__overlay__/edge-led:led-gpios:0"; «3»
		pinmux = "/fragment@1:target:0";
	};

（make -C dts 自己的輸出這裡省略。）開機、overlay 合併之後，再看 kernel 實際拿到的值：

od -An -tx1 /proc/device-tree/edge-led/led-gpios
cat /proc/device-tree/__symbols__/gpio; echo
od -An -tx1 /proc/device-tree/bus@0/gpio@2200000/phandle
 00 00 00 f3 00 00 00 7d 00 00 00 00 «4»
/bus@0/gpio@2200000
 00 00 00 f3
  1. 1第一格還是 0xffffffff（佔位），第二格 0x7d = 125，第三格 0 = active-high。
  2. 2指向同一份 overlay 裡的 edge-led-pins，編譯時就能決定（合併時會整體重新編號）。
  3. 3dtc 在這裡記下「edge-led 的 led-gpios 第 0 格要換成 gpio 這個符號的 phandle」。原廠 DT 的 __symbols__ 裡有 gpio。
  4. 4合併後佔位變成 0xf3，正好是 gpio@2200000 的 phandle。phandle 的數值每個原廠 DT 版本都可能不同，你看到的不一定是 f3，但前後兩行應該相同。
4b.4安裝extlinux.conf

把 overlay 交給 bootloader

這台 kernel 有 CONFIG_OF_OVERLAY=y，但沒有 CONFIG_OF_CONFIGFS，開機後不能動態載入 overlay。overlay 要寫進 /boot/extlinux/extlinux.conf 裡 DEFAULT 那個 label 的 OVERLAYS 行，由 UEFI 在開機時合併，所以每改一次 overlay 都要重開機。

這台的 DEFAULT 是 jetson-io 建立的 JetsonIO label，裡面已經有 IMX219 相機的 overlay。scripts/install_edge_gpio_overlay.py 做的事：

你可能以為要自己做實際上
手動編輯 extlinux.conf腳本找出 DEFAULT 指到的 label，把 /boot/edge-gpio-overlay.dtbo 用逗號接在既有的 OVERLAYS 後面（和 jetson-io 的格式相同）；沒有這行就補一行。其他 label 不動。
先備份第一次安裝時自動存成 extlinux.conf.edge-gpio.bak，之後不覆蓋。
把 dtbo 複製到 /boot腳本會複製；重複執行不會加第二次（冪等）。
移除時手動清理remove 會把那一項拿掉（行空了就刪行）並刪除 /boot 裡的 dtbo。
 
sudo python3 scripts/install_edge_gpio_overlay.py install dts/edge-gpio-overlay.dtbo

⚠ 之後如果再跑 jetson-io 設定 40-pin header，它會重寫整個 JetsonIO label，我們加的那一項可能被洗掉。症狀是 /proc/device-tree/edge-led 不見了、insmod 後沒有 probe。重跑一次 install 再重開機即可。

4b.5driveredge_gpio.c

driver：認得一個 compatible，要一個 GPIO

driver 的最後一段宣告「我認得哪些裝置」：

of_match_table 裡的字串和 overlay 的 compatible 一模一樣，靜態測試會比對兩邊。MODULE_DEVICE_TABLE 把這張表寫進 .ko，讓 udev 之類的工具知道這個 module 支援哪些裝置。module_platform_driver() 展開成 module 載入時註冊 driver、卸載時取消註冊。suppress_bind_attrs 關掉 sysfs 的手動 unbind：unbind 會釋放 driver 的資料，而那時可能還有人開著 /dev/edge_gpio；rmmod 則已經由 .owner 擋住（檔案開著時 module 不能卸載，驗收會測）。

  • devm_gpiod_get(dev, "led", GPIOD_OUT_LOW)：kernel 去這個 device 的 DT 節點找 led-gpios 屬性（函式名稱 "led" 加上 -gpios），解出 controller、腳位、極性，回傳一個 descriptor。不用、也不能自己算 GPIO 編號。這就是 CLAUDE.md 規定的 descriptor-based API，不用舊式的 gpio_request(整數)。
  • GPIOD_OUT_LOW 是邏輯的 0（LED 熄）。active-high 時實體輸出 low；active-low 時 gpiolib 會輸出實體 high。拿到 GPIO 的同時就設好方向和初值，LED 不會在 probe 的瞬間亮一下。
  • devm_ 開頭的資源（記憶體、GPIO）綁在 device 上，remove() 之後或 probe 失敗時由 kernel 自動釋放，所以錯誤路徑可以直接 return。dev_err_probe() 印出錯誤，遇到 -EPROBE_DEFER（GPIO controller 還沒準備好）時則安靜地讓 kernel 稍後重試。
  • misc_register() 建立 /dev/edge_gpio。Step 2 是自己配 major 號、建 class；misc device 共用 major 10、自動配 minor，一個簡單的控制節點用它就夠。mode = 0666 讓一般使用者也能開關。

kstrtouint_from_user() 從 userspace 複製字串並解析成整數，會接受結尾的換行（shell 的 echo 1 送來的是 "1\n"），空字串、on、1 1 都回 -EINVAL。先解析到區域變數、檢查範圍，成功才動 GPIO：這是 Step 2 那個 copy_from_user 坑的老規矩，壞的寫入不能改到狀態。gpiod_set_value_cansleep() 收的是邏輯值，極性反相由 gpiolib 處理，所以這段 code 對 active-high、active-low 都一樣。

先 misc_deregister()，之後就不會再有新的 open；再把 LED 寫成 0。4-a 量過：Tegra 釋放 line 時不會把輸出歸零，而且這一步也實測到 pinctrl 的 default 狀態在 unbind 後不會還原，pad 仍然開著。如果不寫 0，rmmod 之後 LED 可能一直亮著。驗收腳本在 rmmod 前會故意先寫 1。

4b.6測試red → green

不開機也能測 overlay，開機後再測裝置

overlay 要重開機才生效，所以大部分檢查做成不需要硬體的靜態測試：

  • tests/test_edge_gpio_static.py：13 個案例。用 make -C dts 真的編出 dtbo，再用 dtc 反組譯檢查：binding header 裡 port Q 還是 15、兩種極性都編得出來、板型 compatible、led-gpios 是 125 加 flags 0／1、&gpio 和 &pinmux 留成 fixup、pinctrl-0 指到的狀態節點設了 soc_gpio32_pq5 的 tristate=0／input=0，而且這個 pad 名稱和 /boot 裡 NVIDIA 自家 40-pin overlay 的 pin 29 一致。driver 端則檢查 of_match 字串和 overlay 相同、devm_gpiod_get(dev, "led", GPIOD_OUT_LOW)、沒有用舊式整數 GPIO API、有 suppress_bind_attrs。期望值來自 binding header 和 NVIDIA 的 overlay，不是從我們的 overlay 抄的。
  • tests/test_install_overlay.py：8 個案例，對照這台實際的 extlinux.conf 版面做假檔：接在既有 OVERLAYS 後面、只動 DEFAULT label、沒有 OVERLAYS 時補一行、重複安裝不重複、備份是原檔、remove 還原原文、找不到 DEFAULT label 時不動檔案。
  • tests/test_edge_gpio_device.py：6 個案例，對真的 /dev/edge_gpio：權限 0666、寫 1/0 讀回、接受結尾換行、重開檔案狀態還在、讀到 2 bytes 後 EOF、2 -1 on 空字串 \n 10 1 1 都回 EINVAL 且狀態不變。裝置不存在時 skip；設了 EDGE_GPIO_REQUIRE=1 時改成 fail。

紅燈紀錄：靜態和 installer 測試在實作前全紅（11/11、8/8；pinctrl 的 2 個案例是後來加的，在 overlay 加 fragment@1 前也是紅的）。device 測試在 overlay 開機後、insmod 之前用 EDGE_GPIO_REQUIRE=1 跑，6 個全部 failure。變異測試：overlay 的 compatible 改錯、port 改成 P、tristate 改回 enable、pad 名稱寫錯、拿掉 pinctrl-0，每一種都讓測試失敗。

其中「空字串回 EINVAL」也順便確認了一件事：寫 0 個 byte 一樣會進到 driver 的 write()，VFS 不會替你擋掉。

python3 -m unittest discover -s tests -p 'test_edge_gpio_static.py' -v
python3 -m unittest discover -s tests -p 'test_install_overlay.py' -v

兩支都不需要 root，也不需要 overlay 已經安裝；靜態測試需要 dtc、cpp 和 kernel headers，缺一樣就整組 skip。

4b.7實機insmod

手動跑一次：載入、開燈、搶 line、卸載

起點狀態：LED 照 hardware-wiring.md 接好；overlay 已安裝並重開機（/proc/device-tree/edge-led 存在）；4-a 的 build/edge_gpio_blink 已建置；module 沒有載入；站在 repo 根目錄。

make -s -C kernel/edge_gpio
sudo insmod kernel/edge_gpio/edge_gpio.ko
sudo dmesg | tail -n 1
ls -l /dev/edge_gpio
gpioinfo gpiochip0 | grep 'line 105:'
echo 1 > /dev/edge_gpio; cat /dev/edge_gpio
./build/edge_gpio_blink; echo "exit=$?"
echo 2 > /dev/edge_gpio; echo "exit=$?"
echo 0 > /dev/edge_gpio; cat /dev/edge_gpio
sudo rmmod edge_gpio
gpioinfo gpiochip0 | grep 'line 105:'

4b.8驗收× 3 cycles

驗收：有節點就完整測，沒節點就確認不 probe

scripts/verify_edge_gpio.sh 先看 /proc/device-tree/edge-led 在不在：

  • 不在（overlay 沒裝）：insmod 後確認 driver 註冊在 platform bus、沒有任何 device 綁定、/dev/edge_gpio 不存在、line 105 沒被動到，再 rmmod。overlay 安裝前實測 10 項 PASS。
  • 在：從 DT 讀出極性（led-gpios 的第三格），決定「寫 1 時 pin 應該是 hi 還是 lo」，然後跑指定的輪數。

  4. 4LED 閃了 5 次（人眼確認）：第一次由我們的 kernel driver 點亮。其他步驟（on/off 檢查、device 測試、rmmod 前的寫 1）間隔只有幾毫秒，看起來是快閃。
  5. 5腳本以 fd 7 開著 /dev/edge_gpio 時 rmmod 被拒絕：.owner = THIS_MODULE 讓開著的檔案持有 module 的參考。
  6. 6rmmod 之後 pad 仍是 tristate=0：pinctrl 狀態不會在 unbind 時還原。另外注意 gpio-mode：driver 持有 line、LED 正常閃時是 0，rmmod 後才變 1。這推翻了 4-a 原本「bit 10 在請求 line 時設定」的推論（4-a 的章已更正）。
  7. 7probe 次數 = 輪數，每次 probe 都配一次 remove。腳本只印最後 4 行。
4b.9常見錯誤

踩過或差點踩的坑

driver 全 PASS，LED 不亮

症狀
第一版 overlay 只有裝置節點：33 項 PASS，只有 pad tristated 那項 FAIL。
後果
以為 driver 有 bug；這就是拆出 4-a 的原因。
正解
pad 設定也寫進 DT：pinctrl-names + pinctrl-0，probe 前自動套用。

以為 rmmod 會把 pad 還原

症狀
rmmod 後 pinconf 仍是 tristate=0。
後果
若 remove() 沒寫 0，最後的值會一直輸出。
正解
remove() 先關節點、寫 0，再交給 devm 釋放 GPIO。

以為 overlay 能隨時載入

症狀
找不到 configfs 的 overlay 介面。
後果
改了 overlay 卻沒生效。
正解
沒有 CONFIG_OF_CONFIGFS：寫進 extlinux.conf 的 OVERLAYS，重開機。再跑 jetson-io 要重新安裝。

DT 編號當成 line 編號

症狀
在 DT 寫 105，或在 gpioset 用 125。
後果
控制到別根腳。
正解
DT 用 TEGRA234_MAIN_GPIO(Q, 5)（125）；gpiochip0 的 line 是 105。

用 raw 值控制 GPIO

症狀
改用 gpiod_set_raw_value()，active-high 時看不出差別。
後果
換成 active-low 接法後亮滅顛倒。

4-a 的推論被推翻

症狀
driver 持有 line、LED 正常閃時，gpio-mode 仍是 0。
後果
以 bit 10 當作「GPIO 在用」的依據會判錯。
正解

4b.10收尾step 4 → 5

這一步做到了什麼

  • probe() 由 DT 的 compatible 配對觸發；沒有節點時 insmod 不會 probe。
  • pad 由 DT 的 pinctrl 狀態在 probe 前打開，不再需要 devmem；LED 由 kernel driver 控制（人眼確認）。
  • driver 持有 line 時 userspace 拿到 busy；rmmod 後 line 釋放；開著檔案時 rmmod 被拒。三輪驗收0 failure。
  • 沒有實測：active-low。只有靜態測試（active-low dtbo 的 flags 是 1）和程式邏輯（全用邏輯值 API）支持它；沒有改接線（3.3 V → 電阻 → LED → pin 29）驗證。
  • pad 暫存器 bit 10 的意義與設定時機仍不清楚（沒有對照 TRM）。

到這裡 LED 是「輸出」：userspace 叫它亮它就亮。Step 5 反過來，接一顆按鈕當「輸入」：按下時 GPIO 觸發中斷，driver 在 IRQ handler 裡喚醒正在 read() 等待的 userspace 程式。同樣是 DT 描述、descriptor API，只是多了 gpiod_to_irq() 和 wait queue。

1. overlay 裝好了，insmod 也成功，但 /dev/edge_gpio 沒出現。先查哪兩件事？

/proc/device-tree/edge-led 在不在（overlay 有沒有被合併，例如被 jetson-io 洗掉）；在的話看它的 compatible 和 driver 的 of_match_table 是否一字不差。dmesg 有沒有 cannot get led gpio 也要看。

2. devm_gpiod_get(dev, "led", ...) 去 DT 找的是哪個屬性？如果 overlay 把屬性名稱寫成 led-gpio 會怎樣？

找 led-gpios。gpiolib 也接受舊式單數 led-gpio，所以通常還是找得到；但靜態測試和本書都以 -gpios 為準。寫成完全不同的名字（例如 gpios-led）就會 probe 失敗，dmesg 印出 cannot get led gpio。

3. 改成 active-low 接法時，driver 要改哪裡？

一行都不用改。只換成 active-low 的 dtbo（GPIO_ACTIVE_LOW）並重開機；gpiod_set_value_cansleep(led, 1) 會由 gpiolib 輸出實體 low，GPIOD_OUT_LOW 的初值會輸出實體 high（LED 熄）。

4. 為什麼 remove() 要在 misc_deregister() 之後才寫 0，而不是之前？

先取消註冊，就不會再有新的 open 或 write 進來；如果先寫 0，中間仍可能有人寫 1，LED 就在 remove 之後保持亮著。
