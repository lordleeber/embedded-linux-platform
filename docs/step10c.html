10c.1起點為什麼

顯示策略放在 userspace

「每秒顯示一次電壓」聽起來簡單，但它包含一連串決定：幾秒刷新一次、數字取到小數第幾位、讀不到時顯示什麼、舊的數字多久算不可信。這些都是策略，phase04 刻意把它放在 userspace：driver 只負責「把 INA219 的暫存器變成標準單位」（Step 8 的 hwmon）和「把 1024 byte 送上面板」（Step 10-a/b）。策略寫在 driver 裡，改一個顯示格式就要重編 kernel module；寫在 app 裡，換一支程式就好。

互動雙方：兩條 I2C，controller 都是 Tegra。一條是 i2c-7 上的 INA219（0x41），由 edge_ina219 讀；另一條是 i2c-1 上的 SSD1306（0x3C），由 edge_oled 寫。新的 telemetry_display 夾在中間，只碰 sysfs 檔案和 /dev/edge_oled，不直接碰任何 I2C。這一步不做：低電量時採取任何動作（low-battery policy）、網路通知。

hwmon sysfs ABI
kernel 規定的感測器檔案格式（Documentation/hwmon/sysfs-interface.rst）：每個值一個檔案、內容是十進位整數加換行；in*_input 單位 mV、curr*_input mA、power*_input µW。Step 8 的 edge_ina219 照這個格式提供 in1（bus 電壓）、curr1、power1。
stale（過時）
最後一次成功讀到的值已經太舊、不該再當成現況顯示。這裡的規則：超過 3 秒沒讀到新值就顯示 --.--。
process group
一組行程共用的 id。kill -TERM -- -PGID 一次送給整組；setsid 讓程式開一個新的 group，驗收腳本用它確保收得乾淨。
sigtimedwait()
「等一段時間，或等到指定的訊號先到」。訊號必須先用 sigprocmask() 擋住（block），它才會留著等這個函式來拿，而不是觸發預設動作（10c.6）。

10c.3分層顯示什麼

telemetry.h 決定文字，沒有 I/O、沒有時鐘

程式分成兩半。apps/telemetry.h 只回答「現在這些數值該顯示成什麼」：解析 sysfs 的整數、四捨五入到 0.01、判斷是否過時、排出 8 行文字。它不讀檔、不看時鐘，時間是參數傳進來的。所以 tests/test_telemetry.cpp 可以直接寫「1000 ms 時讀到 −555 mA、4001 ms 時還沒有新值，畫面應該是什麼」，不用真的等 3 秒。apps/telemetry_display.cpp 是另一半：讀檔、寫裝置、等待、訊號。

四捨五入用整數做（hundredths()，0.01 為一格、距離 0 遠的方向進位，沒有 -0.00）：浮點數在 −0.555 這種值上的進位方向會因為二進位表示而不可預期，整數不會。狀態行最後的計數器每次刷新加一，人在板子旁才分得出「畫面是活的」和「程式卡住、面板停在最後一張」。

10c.4百分比廠商公式

BAT %：照抄廠商範例，連它的缺點一起

原本的規劃只有 V / I / P。驗收時使用者要求加上電量百分比，「就像原本的 ina219.py 提供的資訊」。廠商範例（Step 6-a 原樣收在 third_party/waveshare_ups_c/）的算法只有兩行：p = (bus_voltage - 9) / 3.6 * 100，再夾在 0 到 100 之間。也就是 9.0 V 算 0 %、12.6 V 算 100 %，中間是直線。換成整數：每 36 mV 是 1 %。

模擬：瀏覽器裡用同一個公式計算，不是實機輸出

測試的期望值不是自己算的，是這台板子上廠商範例實際印出來的：Step 6-a 的 baseline 記錄了 12.364 V → 93.44 %、12.192 V → 88.67 %、11.86 V → 79.44 %，加上這次驗收時的 12.528 V → 98.00 %。整數算法會不會和 Python 的浮點 {:6.2f} 在進位上分歧？不會：x × 25 / 9 的小數部分只可能是 k/9，永遠不會剛好落在 0.5 上。

這個百分比不是剩餘電量。它只看電壓，而電壓會被充電器往上推：Step 6-a 實測，電池在 11.86 V（79 %）時一插上 adapter，同一個公式立刻顯示 93 %。驗收當天的 98 % 也是在充電（+0.96 A）時讀的。phase04 排除的「low-battery policy」是指依電量採取動作；這裡只顯示、不判斷，所以放進來，限制寫在這裡和 telemetry.h 的註解裡。

10c.5錯誤讀不到、過時

讀不到不是錯誤，是一種狀態

這支程式要一直跑，任何一個錯誤都不該讓它結束。可能出錯的地方有四個：

情況怎麼處理
一個值讀不到（檔案不見、ENODATA、內容不是數字）保留最後一筆好值，照樣顯示；超過 --stale-ms（預設 3000）才變 --.--，狀態行列出是哪個。stderr 只在「開始失敗」那一次寫原因。
sensor 不見了（rmmod、unbind）hwmon 目錄消失 → 重新找；找不到就全部 --.--、狀態 NO SENSOR，每秒再找一次。stderr 寫一行 no edge_ina219 under …，並把各 channel 的「正在失敗」重設：sensor 回來後如果還是讀不到，會再報一次（code review 後加的）。
sensor 換了號碼不寫死 hwmon4，每次刷新都用 name 檔案確認，對不上就重找（Step 8：重新綁定可能換號）。為什麼不是「讀取失敗才重找」：號碼會被重用，消失的 hwmon4 可能換成別的感測器，它的 in1_input 照樣讀得到。
OLED 寫不進去關掉 fd，下一秒重開重寫；也只報一次（10c.6 的節錄）。

10c.6收尾寫入失敗與訊號

寫不進去就重開；被要求結束就清空畫面

為什麼寫入失敗要關掉 fd：Step 10-a 的 driver 被 unbind 之後，已經開著的 fd 永遠回 ENODEV，即使 driver 又綁回來；只有重新 open() 才會拿到新的那一個。OLED 只是拔線（driver 還在）時，同一個 fd 本來就能繼續用，關掉重開也無妨。

為什麼落後時要重新排程：第一版是 next += interval，沒有上限。程式被 Ctrl-Z 停住 60 秒、或某次寫入卡了幾秒，next 就落在過去，之後每次等待都是 0，一口氣補刷 60 次（code review 找到；測試用 SIGSTOP 停 1 秒再 SIGCONT 重現）。現在只要落後就從「現在」重新起算。

為什麼用 sigtimedwait() 而不是 signal handler + sleep()。常見的寫法是 handler 設一個旗標，主迴圈每次 sleep() 醒來檢查。它有一個縫：訊號剛好在「檢查旗標」之後、「開始 sleep」之前到，handler 設了旗標，程式卻照樣睡滿一整秒才發現。這裡的做法是先把 SIGINT / SIGTERM / SIGHUP 擋住（block），訊號到了只會被記成 pending；等下一秒的那個呼叫就是 sigtimedwait()，pending 的訊號會讓它立刻回來。訊號什麼時候到都一樣，沒有縫，也不需要 handler。

收到訊號後，程式寫一張全黑的畫面才結束：一個停住的程式留下一張看起來正常的數字畫面，比黑屏更誤導人。所以 SIGHUP（SSH 斷線時前景程式收到的）也照這樣處理，SIGPIPE 則忽略：stdout 接到 | head 之類、讀的那端先關掉時，程式照樣顯示，不會被殺掉而留下舊數字（兩者都是 code review 後加的）。試試看（接著上面的指令；第一行先清空檔案，讓「最後 1024 byte」就是這個程序寫的）：

python3 -c "import sys; d = open(sys.argv[1], 'rb').read(); print(len(d) // 1024, 'frames, last one blank:', not any(d[-1024:]))" build/oled.bin
#1 V=12528 I=- P=12064814 oled=ok
#2 V=12528 I=- P=12064814 oled=ok
[1]+  Done                    build/telemetry_display --hwmon-root build/fake --dev build/oled.bin 2> /dev/null

10c.8驗收實機

實測：兩個 driver、一支 app、一個人

前提：overlay 有 ina219@41 與 oled@3c（Step 10-a 起），UPS 模組與 OLED 都接著，兩個 module 都沒有載入（腳本自己 insmod，結束時 rmmod）。在 repo 根目錄的終端機裡跑：

你可能以為要自己做實際上
insmod 兩個 module、找 hwmon 號碼腳本建置並載入 edge_ina219 與 edge_oled，用 name 找 hwmon；結束時（含 Ctrl-C）rmmod。

10c.9常見錯誤

踩過的坑

以為 read 只讀到發問後的按鍵

症狀
3 分鐘觀察期間多按的一次 Enter 留在 tty 緩衝裡，問題一印出就被當成空白答案讀走：[y/n] 後面直接接 FAIL、沒有換行。
後果
畫面明明沒閃，卻記成 FAIL；人是事後口頭回報的。
正解
每次發問前 drain_tty，把積著的輸入讀掉；用 script 開 pty 先送一行再發問，確認被丟掉。

驗收要人看太久

症狀
3 分鐘的觀察，使用者看完說太久。
後果
站在板子旁盯著看，注意力撐不住，答案也就不可靠。
正解
--watch-seconds，預設 30；3 分鐘那次照實記成口頭回報。

以為百分比算 policy

症狀
範圍測試一開始禁止 percent 這個字。
後果
使用者要的、廠商範例本來就有的資訊被當成範圍外。
正解
policy 是依電量採取動作；只顯示不算。改成禁止門檻、警報、通知，並寫明這個百分比的限制。

pgrep 找不到程式

症狀
pgrep -x telemetry_display 永遠沒有結果。
後果
「沒有殘留程序」這項檢查永遠會過，等於沒檢查。
正解
kernel 的程序名稱只留 15 字元：用 telemetry_displ（腳本裡的 COMM）。

指令把 & 套在整串上

症狀
寫章時試 : > f && app &，kill $! 之後結束碼 143，app 沒寫空白畫面。
後果
$! 是子 shell，訊號沒送到 app。
正解
清空檔案拆成獨立一行，讓 & 只套在 app 上。

測試抓字面而不是行為

症狀
驗收腳本的測試要找 edge_ina219/unbind，腳本寫的是 $INA_DRV/unbind。
後果
紅燈不是腳本錯；照紅燈改腳本只會讓它更難讀。
正解
改測試：確認 INA_DRV 指向 edge_ina219，再找 $INA_DRV/unbind。
10c.10收尾Phase 4 → 5

這一步做到了什麼

  • telemetry_display：每秒讀 edge_ina219 的 hwmon，顯示 BAT % / V / I / P 與狀態行；兩個 driver 都沒改。
  • phase04 的驗收條件成立：OLED 持續顯示 BAT / Voltage / Current / Power，數值和 hwmon 一致。驗收 0 failure。
  • 讀不到、過時、sensor 消失與換號、OLED 寫入失敗、stdout 被關掉都不會讓程式結束；SIGINT / SIGTERM / SIGHUP 立刻停、清空畫面；停住之後不會連續補刷。
  • Step 10-b 帶過來的：每次重送設定，人眼看 3 分鐘與 30 秒都沒有閃爍，不改 driver。
  • 測試：8 組 C++ 向量、23 個 Python 測試，app 的期望畫面由 10-b 的工具產生。
  • 沒有實測：實機 hwmon 換號、長時間執行、app 端的 ENODATA。規模 798 行，貼著 800 行上限。

Phase 4 到這裡結束：從 userspace 送 byte（Step 9）、driver 骨架（10-a）、字型（10-b），到一支實際有用的程式（10-c）。Step 11 換到另一端：在 STM32F103 上寫一個 I2C slave，讓 Jetson 這邊的 driver 有一個自己設計的周邊可以對話。

1. 電流讀取失敗了一次、下一秒又成功，畫面會怎樣？

不會變：失敗那一次 Value 保留上一筆和它的時間，還不到 3 秒，照樣顯示；stderr 會有一行原因。下一秒成功就換成新值。只有連續失敗超過 3 秒才變 --.--。

2. 為什麼 app 不把 hwmon4 寫死在程式裡？

號碼依註冊順序分配。開機時 hwmon0–3 被其他 driver 佔走，edge_ina219 才拿到 4；unbind / bind 或 rmmod / insmod 之後可能換號。用 name 找，目錄消失就重找。

3. 如果改成 signal handler 設旗標、主迴圈 sleep(1)，最壞要等多久才結束？

將近一秒：訊號剛好在「檢查旗標」之後、「開始 sleep」之前到達時，要睡滿這一秒才會再檢查。block 訊號後用 sigtimedwait() 等，pending 的訊號讓它立刻回來，沒有這個縫。

4. 接上 adapter 的瞬間 BAT 從 79 % 跳到 93 %，是 bug 嗎？

不是 app 的 bug，是廠商公式的限制：它只看 bus 電壓，充電器把電壓往上推，百分比跟著變高。要真正的剩餘電量需要累計電流（庫侖計）或電池管理晶片，不在這一步的範圍內。
