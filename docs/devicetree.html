Device Tree 入門：kernel 怎麼知道板子上有什麼

Step 2、3 的 edge_test 不碰任何硬體，所以不需要問「裝置在哪裡」。從 Step 4 開始，每個 driver 都要知道暫存器在哪個位址、用哪根 GPIO、接哪條中斷、掛在哪條 I2C bus 的哪個位址。在 ARM 板子上，這些資訊不是 driver 自己找出來的，而是寫在一份叫 Device Tree 的資料結構裡，開機時交給 kernel。這一章不寫任何 code，只在板子上讀現成的 Device Tree，把之後每一章都會用到的語法和機制先講清楚：節點與屬性、reg 和位址 cell、phandle、compatible 配對，以及一個節點怎麼變成 /sys 底下的一個 device；最後把 4-a 會遇到的 pad、pinmux、pinctrl 三個詞分清楚。

kernel 5.15.148-tegra · L4T R36.4.7 · DTC 1.6.1 · 新增 docs/devicetree.html；修改 docs/{index.html, step03.html, step04a.html, step04b.html}。不新增 code，所有指令只讀不寫、不需要 root

DT.1起點為什麼需要

SoC 上的硬體不會自己報名

PC 上插一張 PCIe 網卡或一支 USB 隨身碟，kernel 不需要事先知道它存在：PCI 和 USB 是可列舉的 bus，裝置插上去後會回報自己的廠商 ID 和型號，kernel 拿這組 ID 找 driver。

Jetson 的 Orin SoC 不是這樣。GPIO controller、pinmux、I2C controller 都是晶片裡固定的電路區塊，對 CPU 來說只是一段位址：GPIO 在 0x02200000、pinmux 在 0x02430000、header pin 3/5 用的 I2C controller 在 0x0c250000。去讀這些位址不會得到「我是 I2C controller」這種回答。板子上外接的晶片更是如此：UPS 模組上的 INA219 只是 I2C bus 上位址 0x41 的一個晶片，不問它就不知道它在那裡。

早期的 ARM Linux 把這些資訊寫死在每塊板子的 C 檔案裡（arch/arm/mach-* 底下的 board file），換一塊板子就要改 kernel、重新編譯。Device Tree 把它改成資料：一份描述「這塊板子有哪些硬體、各自接在哪裡」的樹，由 bootloader 在開機時交給 kernel。同一個 kernel image 拿到不同的樹，就能在不同的板子上開機；driver 只說「我認得哪一種硬體」，不寫「它在哪裡」。

Step 4-a 會用 /dev/mem 直接寫 pinmux 暫存器，那個基底位址 0x02430000 就是從 Device Tree 的 pinmux@2430000 節點讀來的（DT.5）；4-b 起，我們自己的每一個裝置（LED、按鍵、INA219、OLED）都會寫成 Device Tree 的節點。所以先在這一章把樹讀懂。

互動雙方：寫入方是開機韌體（JP6 上是 UEFI），它把樹放進記憶體交給 kernel；讀取方是 kernel 的 OF core（of_ 開頭的那一組 API，名稱來自 Device Tree 的前身 Open Firmware）、各個 bus（platform bus、i2c core）和 driver。userspace 只能透過 /proc/device-tree 唯讀地看。這一章不做：不寫 overlay、不改開機設定、不寫 driver，那些是 4-b 的事。

Device Tree（DT）
描述硬體的一棵樹。每個節點描述一個硬體區塊或一條 bus，節點上的屬性寫它的資源：位址、中斷、GPIO、時脈。
.dts / .dtb
人寫的文字原始檔（device tree source）／編譯好的二進位檔（device tree blob，也叫 FDT，flattened device tree）。kernel 吃的是 .dtb。補丁用的 .dtbo（overlay）在 4-b 介紹。
dtc
Device Tree Compiler。.dts 和 .dtb 雙向轉換都用它，也能把開機後的樹（/proc/device-tree）倒回成文字。
compatible
節點上的字串屬性，說「這是哪一種硬體」，格式是「廠商,型號」，例如 "nvidia,tegra234-gpio"。driver 靠它認領節點（DT.7）。
binding
每一種 compatible 的「屬性規格書」：必須有哪些屬性、每個屬性的格式。DT 的作者和 driver 的作者靠它對齊（DT.8）。
DT.2全景原始碼 → probe()

一棵樹從原始碼走到 driver 的 probe()

同一份硬體描述會經過三個階段：在建置主機上編譯、開機時由韌體交給 kernel、kernel 把它展開成記憶體裡的節點，再依節點建立 device。下圖每個方框都可以點，會跳到講那一站的小節。

這台板子的 extlinux.conf 用的 label 叫 JetsonIO，它的 FDT 行指向 /boot/dtb/kernel_tegra234-p3768-0000+p3767-0005-nv-super.dtb，OVERLAYS 行列出要疊上去的 .dtbo。「疊上去」的細節（overlay 怎麼找到要改的節點）放在 4-b。這台的原廠 .dts 原始碼不在板子上，只有編好的 .dtb；要看它的內容，就從開機後的樹倒回來（DT.4）。

DT.3結構節點與屬性

/proc/device-tree：目錄是節點、檔案是屬性

kernel 展開後的樹開放在 /sys/firmware/devicetree/base，/proc/device-tree 是指向它的 symlink。每個節點是一個目錄，每個屬性是一個檔案，內容就是屬性的原始 byte。在 repo 根目錄（任何目錄都可以；這一章的指令都不需要 root）執行：

tr '\0' '\n' < /proc/device-tree/compatible
find /proc/device-tree/ -type d | wc -l
ls /proc/device-tree/bus@0/i2c@c250000/

  1. 1根節點的 compatible 描述整塊板子，從最具體排到最通用：載板＋模組的 Super 版、模組、SoC。字串之間用 \0 分隔，所以要先用 tr 換成換行才好讀。4-b 的 overlay 頂層也會寫這個字串，宣告「只適用這種板子」。
  2. 2整棵樹有 1749 個節點（含根節點）。這台已經裝了 4-b 起的 overlay，多出 edge-led、edge-button、ina219@41 等節點；還沒裝 overlay 時數字會少一些，原廠 DT 版本不同也會不一樣。
  3. 3子節點和屬性在同一層：ina219@41 是目錄（子節點，Step 7 的 overlay 加的），其餘都是檔案。name 是 kernel 補上的屬性，內容是節點名稱 @ 前面那段。

節點名稱的格式是 名稱@unit-address。@ 前面是通用的類別名（i2c、gpio、pinmux），後面是這個節點在父 bus 上的位址，必須和它的 reg 屬性第一個位址一致：i2c@c250000 的暫存器在 0xc250000，ina219@41 的 I2C 位址是 0x41。所以同一種硬體有好幾個時，名稱不會撞，看名字就知道它在哪裡。從根節點一路寫下來的完整名稱（/bus@0/i2c@c250000/ina219@41）叫 path，是節點在整棵樹裡唯一的名字。

DT.4屬性值bytes 與 cell

屬性的值只是一串 byte

blob 裡的屬性沒有型別標記，只有名稱和一串 byte。怎麼解讀由 binding 規定，常見的有四種寫法：

.dts 寫法blob 裡的 byte例子
字串 "a", "b"每個字串以 \0 結尾，接在一起compatible、status
cell <0x2430000 0x19100>每個 cell 是 32-bit、big-endian（高位 byte 在前）reg、interrupts、gpios
byte 陣列 [55 aa 16]原樣的 bytedisplay@13800000 的 nvidia,dcb-image（8407 byte 的顯示設定表）
空屬性 gpio-controller;長度 0，「存在」就是值gpio-controller、interrupt-controller

用 od 直接看檔案裡的 byte（cat 會把 cell 印成亂碼）：

od -An -c /proc/device-tree/bus@0/i2c@c250000/compatible
od -An -tx1 /proc/device-tree/bus@0/pinmux@2430000/reg
ls -l /proc/device-tree/bus@0/gpio@2200000/gpio-controller
$ od -An -c /proc/device-tree/bus@0/i2c@c250000/compatible
   n   v   i   d   i   a   ,   t   e   g   r   a   1   9   4   -
   i   2   c  \0 «1»
$ od -An -tx1 /proc/device-tree/bus@0/pinmux@2430000/reg
 00 00 00 00 02 43 00 00 00 00 00 00 00 01 91 00 «2»
$ ls -l /proc/device-tree/bus@0/gpio@2200000/gpio-controller
-r--r--r-- 1 root root 0 Oct 16 14:25 /proc/device-tree/bus@0/gpio@2200000/gpio-controller «3»
  1. 1Orin（tegra234）的 I2C controller 寫的是 tegra194-i2c：compatible 描述的是「這塊電路的程式介面跟哪一型相同」，不是「它在哪顆晶片上」。和上一代相同的區塊就沿用舊名，讓舊 driver 直接認得。
  2. 216 byte = 4 個 cell：0x00000000 0x02430000 0x00000000 0x00019100。怎麼切成「位址」和「長度」，要看父節點的 #address-cells／#size-cells，下一節講。
  3. 3大小 0 的檔案：空屬性。gpio-controller 存在，就代表「這個節點是 GPIO controller，別的節點可以向它要 GPIO」。日期時間是 sysfs 建立檔案的時刻，你看到的會不一樣。

一個一個屬性用 od 看太慢。dtc 可以把整棵開機後的樹倒回成 .dts 文字（-I fs 表示輸入是 /proc/device-tree 這種目錄樹）：

dtc -I fs -O dts /proc/device-tree 2>/dev/null | wc -l
dtc -I fs -O dts /proc/device-tree 2>/dev/null | grep -A6 '^\t\tpinmux@2430000 {' | head -5
$ dtc -I fs -O dts /proc/device-tree 2>/dev/null | wc -l
11925 «1»
$ dtc -I fs -O dts /proc/device-tree 2>/dev/null | grep -A6 '^\t\tpinmux@2430000 {' | head -5
		pinmux@2430000 {
			compatible = "nvidia,tegra234-pinmux";
			status = "okay";
			reg = <0x00 0x2430000 0x00 0x19100>; «2»
			phandle = <0x02>; «3»
  1. 1整棵樹倒回來將近一萬兩千行。2>/dev/null 丟掉的是一千多行 warning：dtc 用嚴格的格式檢查原廠樹（例如「節點名有 @ 卻沒有 reg」），不影響輸出。
  2. 2和上面 od 看到的 16 byte 是同一個值，dtc 幫忙切成 cell、用十六進位印出。
  3. 3phandle 是這個節點的編號，別的節點用這個數字指向它（DT.6）。

倒回來的文字和 NVIDIA 原本寫的 .dts 不一樣：屬性順序不同、巨集都變成數字、&gpio 這種名稱引用都變成 phandle 數字。它是「kernel 實際拿到的內容」，適合查值；要看「作者的意思」得看原始碼和 binding。

DT.5位址reg 與 cells

reg 要靠父節點才讀得懂

reg 是一串 (位址, 長度) 配對，但一個位址用幾個 cell、長度用幾個 cell，不寫在 reg 自己身上，而是由父節點的 #address-cells 和 #size-cells 決定。因為「位址」的意思取決於這個節點掛在哪種 bus 上：記憶體 bus 上是 64-bit 實體位址加長度，I2C bus 上是 7-bit 的裝置位址、根本沒有長度。

od -An -tx1 /proc/device-tree/bus@0/'#address-cells' /proc/device-tree/bus@0/'#size-cells'
od -An -tx1 /proc/device-tree/bus@0/i2c@c250000/'#address-cells' /proc/device-tree/bus@0/i2c@c250000/'#size-cells'
od -An -tx1 /proc/device-tree/bus@0/i2c@c250000/reg
$ od -An -tx1 /proc/device-tree/bus@0/'#address-cells' /proc/device-tree/bus@0/'#size-cells'
 00 00 00 02 00 00 00 02 «1»
$ od -An -tx1 /proc/device-tree/bus@0/i2c@c250000/'#address-cells' /proc/device-tree/bus@0/i2c@c250000/'#size-cells'
 00 00 00 01 00 00 00 00 «2»
$ od -An -tx1 /proc/device-tree/bus@0/i2c@c250000/reg
 00 00 00 00 0c 25 00 00 00 00 00 00 00 00 01 00 «3»
  1. 1bus@0 底下的子節點：位址 2 個 cell、長度 2 個 cell，都是 64-bit。
  2. 2i2c@c250000 底下的子節點：位址 1 個 cell、長度 0 個。
  3. 3I2C controller 自己掛在 bus@0 底下，所以照 2 + 2 切：位址 0x0c250000、長度 0x100（256 byte 的暫存器區）。

bus@0 還有一個 ranges 屬性，說明子節點的位址怎麼換算成父節點（最後是 CPU）的位址。這裡的值是「子位址 0 對應父位址 0，長度 0x100_0000_0000」，也就是一比一：pinmux@2430000 的位址就是 CPU 看到的實體位址 0x02430000。下一章 4-a 的 pad_pin29.py 會把 /dev/mem 從這個位址 mmap 進來。I2C controller 沒有 ranges：I2C 位址不在 CPU 的位址空間裡，要經過 I2C controller 收發才碰得到。

reg 解碼計算機（在瀏覽器裡計算，不讀板子）

把 od -An -tx1 …/reg 的輸出貼進來，選父節點的 cells 數。下面的按鈕會填入本章出現過的實測值。

gpio@2200000 的 reg 有兩段（32 byte），另一個屬性 reg-names = "security", "gpio" 依序替它們命名，driver 可以用名字要其中一段。一個 reg 放幾段、各段代表什麼，也是 binding 規定的。

DT.6引用phandle

phandle：一個節點怎麼指向另一個節點

樹狀結構只能表達「誰在誰底下」。可是硬體之間還有別的關係：一顆按鍵在 gpio-keys 底下，但它接在 GPIO controller 的某一根腳上；I2C controller 在 bus@0 底下，但它的中斷接到 GIC（中斷控制器）。這種「橫向」的關係用 phandle 表示：被指向的節點有一個 phandle 屬性（一個數字），要指向它的屬性就把這個數字放進 cell 裡。

原廠樹裡有一個現成的例子：載板上的 Force Recovery 按鍵。

dtc -I fs -O dts /proc/device-tree 2>/dev/null | grep -A6 'key-force-recovery {'
od -An -tx1 /proc/device-tree/bus@0/gpio@2200000/phandle /proc/device-tree/bus@0/gpio@2200000/'#gpio-cells'
gpioinfo gpiochip0 | grep 'line  35:'
$ dtc -I fs -O dts /proc/device-tree 2>/dev/null | grep -A6 'key-force-recovery {'
		key-force-recovery {
			label = "Force Recovery";
			linux,input-type = <0x01>;
			linux,code = <0x101>;
			gpios = <0xf3 0x30 0x01>; «1»
		};
	};
$ od -An -tx1 /proc/device-tree/bus@0/gpio@2200000/phandle /proc/device-tree/bus@0/gpio@2200000/'#gpio-cells'
 00 00 00 f3 00 00 00 02 «2»
$ gpioinfo gpiochip0 | grep 'line  35:'
	line  35:      "PG.00" "Force Recovery" input active-low [used] «3»
  1. 1按鍵節點只寫了三個數字。第一格 0xf3 是 phandle。
  2. 2gpio@2200000 的 phandle 正是 0xf3；它的 #gpio-cells = 2 告訴 kernel「指向我的時候，phandle 後面再接 2 格」。這和上一節 #address-cells 是同一種設計：格數由被指向的那一方宣告。phandle 的數值由 dtc 編譯時分配，原廠 DT 換版本就可能不同，你看到的不一定是 f3，但兩處會一致。
  3. 3kernel 解完這三格的結果：PG.00、consumer 是節點的 label "Force Recovery"、active-low。line 編號 35 是 gpiochip 依每個 port 實際腳數累加的：port A–F 實際各有 8、1、8、4、8、6 支腳，合計 35，所以 port G 的第 0 支是 line 35，不是 DT 的 48（4-a 會列出整張 port 表）。

第二格的 48 從哪裡來？binding 為 tegra234 定義了一個 header，原始 .dts 寫的是巨集，cpp 先展開成數字再交給 dtc。header 隨 kernel headers 安裝在板子上：

grep -n 'PORT_G ' /lib/modules/$(uname -r)/build/include/dt-bindings/gpio/tegra234-gpio.h
grep -n -A1 'define TEGRA234_MAIN_GPIO(' /lib/modules/$(uname -r)/build/include/dt-bindings/gpio/tegra234-gpio.h
$ grep -n 'PORT_G ' /lib/modules/$(uname -r)/build/include/dt-bindings/gpio/tegra234-gpio.h
25:#define TEGRA234_MAIN_GPIO_PORT_G   6
$ grep -n -A1 'define TEGRA234_MAIN_GPIO(' /lib/modules/$(uname -r)/build/include/dt-bindings/gpio/tegra234-gpio.h
45:#define TEGRA234_MAIN_GPIO(port, offset) \
46-	((TEGRA234_MAIN_GPIO_PORT_##port * 8) + offset)

所以原始碼裡這一格是 TEGRA234_MAIN_GPIO(G, 0)，展開成 6 × 8 + 0 = 48。下一章 4-a 要點亮的 pin 29 是 TEGRA234_MAIN_GPIO(Q, 5) = 15 × 8 + 5 = 125，line 卻是 105，道理相同。

原始碼裡寫的是名字，不是數字

寫 .dts 的人不會手填 0xf3。原始碼在節點前面加一個標籤（gpio: gpio@2200000 { … }），引用時寫 &gpio，dtc 編譯時才分配 phandle 數字、填進去。4-b 的 overlay 就是這樣寫的，先看一眼長相（細節 4-b 再講）：

&gpio 指的就是上面那個 phandle 0xf3 的節點；led-gpios 和 Force Recovery 的 gpios 格式完全一樣，只是屬性名多了 led- 前綴，讓 driver 可以用名字（"led"）要這組 GPIO。&edge_led_pins 指向同一份 overlay 裡另一個加了標籤的節點。overlay 是單獨編譯的，編的時候不知道原廠樹的 phandle 是多少，所以原廠樹必須把標籤也一起留下來。開機後可以在 __symbols__ 節點看到它們：

tr -d '\0' < /proc/device-tree/__symbols__/gpio; echo
ls /proc/device-tree/__symbols__ | wc -l
$ tr -d '\0' < /proc/device-tree/__symbols__/gpio; echo
/bus@0/gpio@2200000
$ ls /proc/device-tree/__symbols__ | wc -l
901

每個屬性名是一個標籤，值是它指向的節點 path。dtc 要加 -@ 才會產生 __symbols__；NVIDIA 的原廠樹有加，所以我們的 overlay 能用 &gpio、&pinmux、&hdr40_i2c1 這些名字。

中斷也是同一套

interrupts 屬性的格數由中斷控制器的 #interrupt-cells 決定，中斷控制器是誰則由 interrupt-parent（一個 phandle，沒寫就往上層找）決定。這棵樹的根節點 interrupt-parent = <0x01> 指向 interrupt-controller@f400000（"arm,gic-v3"，#interrupt-cells = 3）：

od -An -tx1 /proc/device-tree/bus@0/i2c@c250000/interrupts
grep c250000 /proc/interrupts
$ od -An -tx1 /proc/device-tree/bus@0/i2c@c250000/interrupts
 00 00 00 00 00 00 00 20 00 00 00 04 «1»
$ grep c250000 /proc/interrupts
168:       5574          0          0          0          0          0     GICv3  64 Level     c250000.i2c «2»
  1. 1三格：0 = GIC_SPI（共享周邊中斷）、0x20 = SPI 編號 32、4 = IRQ_TYPE_LEVEL_HIGH。兩個巨集都在 dt-bindings/interrupt-controller/ 底下的 header。
  2. 2GIC 的硬體中斷號是 SPI 編號加 32（前 32 個留給每顆 CPU 私有的中斷），所以是 64，觸發方式 Level。前面的計數是開機到現在各 CPU 收到的次數，每次跑都不同。
DT.7配對節點 → device

節點變成 device，device 等 driver 認領

節點只是資料。kernel 開機時走過這棵樹，為節點建立 struct device，掛到對應的 bus 上；之後任何時候有 driver 註冊到同一條 bus（內建的、或 insmod 載入的），bus 就拿 device 的 compatible 和 driver 的 of_match_table 逐一比對字串，對上了就呼叫 driver 的 probe()。誰負責建立 device，看父節點：

  • 根節點的子節點，和 compatible 含 "simple-bus"（及少數同類的 bus 型別）的節點底下的子節點（bus@0 就是 simple-bus）：由 of_platform_populate() 建成 platform device，名稱是「unit-address.節點名」，例如 2200000.gpio。
  • I2C controller 的子節點：controller 的 driver 註冊 I2C adapter 時，由 i2c core 建成 i2c client，名稱是「bus 編號-位址」，例如 7-0041。
  • status = "disabled" 的節點：不建 device。沒寫 status，或寫 "okay"（kernel 也接受舊寫法 "ok"）才算啟用。

每個 device 在 sysfs 都有一個 of_node symlink 指回它的節點；有 driver 認領的，還會有 driver symlink：

i2c-7 這個編號從哪來

Step 6 起，header pin 3/5 的 I2C 叫 i2c-7。7 不是「第幾個 I2C 節點」，而是 /aliases 節點指定的：

tr -d '\0' < /proc/device-tree/aliases/i2c7; echo
$ tr -d '\0' < /proc/device-tree/aliases/i2c7; echo
/bus@0/i2c@c250000

i2c core 建立 adapter 時，先查 aliases 裡有沒有指向這個節點的 i2cN，有就用 N 當 bus 編號。所以 i2c@c250000 是 i2c-7、i2c@c240000 是 i2c-1，和節點在樹裡的順序無關。原廠樹另外給這兩個節點取了標籤：pin 3/5 那個叫 hdr40_i2c1（「header 上的第 1 組 I2C」），pin 27/28 那個叫 gen2_i2c。三套名字（節點位址、bus 編號、標籤）裡的數字彼此無關，Step 9 的紀錄特別提醒：OLED 接在 pin 27/28，Step 10-a 的節點要掛在 &gen2_i2c，不能沿用 overlay 裡現成的 &hdr40_i2c1。

DT.8契約binding

binding：DT 作者和 driver 作者之間的契約

DT 的語法只規定「屬性是一串 byte」。gpios 有幾格、reg 有幾段、需不需要 interrupts、status 以外還有哪些必填屬性，都寫在每一種 compatible 的 binding 裡。上游 kernel 原始碼的 Documentation/devicetree/bindings/ 底下有幾千份，現在大多是 YAML schema，可以用工具驗證 .dts；這台板子只裝了 kernel headers，沒有這些文件，要看得上 kernel 原始碼網站或 NVIDIA 的 kernel 原始碼。

binding 有兩個部分會實際出現在我們的檔案裡：

binding 的部分在哪裡本書用到的地方
屬性規格（文件）上游 Documentation/devicetree/bindings/driver 的 probe() 照它讀屬性，例如 4-b 用 devm_gpiod_get(dev, "led", …) 讀 led-gpios
常數 header/lib/modules/$(uname -r)/build/include/dt-bindings/TEGRA234_MAIN_GPIO()、GPIO_ACTIVE_LOW、TEGRA_PIN_PULL_NONE；.dts 用 #include 引入，所以要先過 cpp

我們自己的裝置（LED、按鍵、INA219、OLED）用的是自訂的 compatible（"edge,gpio-led" 之類），沒有上游 binding。這時契約就是「overlay 寫什麼屬性，我們的 driver 就讀什麼屬性」，4-b 起每一步的靜態測試都會比對兩邊的字串，用測試代替那份文件。

為什麼要先過 cpp：dtc 本身不認得 #include 和 #define。kernel 建置時先用 C 前處理器展開，再把結果交給 dtc。4-b 的 dts/Makefile 照這個做法寫，而且要加 -undef：否則 gcc 預先定義的 linux 巨集會把 linux,code 這種屬性名稱展開掉（就是上面 Force Recovery 節點裡那個屬性）。

DT.9腳位pad · pinmux · pinctrl

pad、pinmux、pinctrl：一根腳怎麼接到晶片裡的電路

下一章 4-a 會遇到一個現象：程式把 GPIO 設成 1，LED 卻不亮，問題不在 GPIO，而在 GPIO 和腳位之間的那一層。這三個詞常常混著用，其實各指一層：pad 是晶片邊緣的電路，pinmux 是設定 pad 的硬體暫存器，pinctrl 是 Linux 裡管這些暫存器的子系統。DT 跟它們的關係是：pinctrl 要怎麼設定，寫在 DT 裡。

名詞是什麼在這台板子上
pad硬體：一根腳在晶片裡的那一小塊電路，包括訊號來源的選擇、輸出驅動器、輸入接收器、上拉／下拉電阻header pin 29 的 pad 叫 soc_gpio32_pq5
pinmux硬體：一整區暫存器，每個 pad 一個 32-bit 暫存器，用不同的 bit 設定上面那些開關pinmux@2430000；pin 29 的暫存器在 0x02430068（4-a 會直接讀寫它）
pinctrlLinux 的子系統：pinmux 的 driver，加上一套讓別的 driver 或 DT「要求某組 pad 設成某樣子」的機制driver tegra234-pinctrl；設定寫在 DT 的 nvidia,pins 這類節點裡

pad：一根腳背後的四個開關

SoC 的腳位比功能少很多，所以大多數腳都是多用途的：同一根腳可以接到 I2C、UART、時脈輸出等專用電路（這類專用功能叫 SFIO，special-function I/O），也可以交給 GPIO controller 當一般的 GPIO。pin 29 就是這樣：NVIDIA 的 40-pin overlay 把它設成 extperiph3（對外的時脈輸出），我們的 LED 則把它當 GPIO PQ.05。訊號選好以後，還要經過 pad 裡的電氣開關才到得了腳位：

JP6 剛開機時，pin 29 的 pad 暫存器低位元組是 0x58（4-a 會實際讀到），二進位 0101 1000：bit 6（input）= 1、bit 4（tristate）= 1、bit 3:2（pull）= 10 也就是上拉、bit 1:0（function）= 0，正好是圖上的三個開關。另外 pad 還有驅動強度、Schmitt trigger、高壓 I/O 這些電氣選項，nvidia,io-high-voltage 就是其中一個（下面 NVIDIA 的 overlay 會看到），本書用不到。「GPIO 模式」這個開關（GPIO 還是 SFIO）在 Tegra 上不在 pinmux 暫存器裡，而是由 GPIO controller 自己的暫存器決定，line 被請求時 GPIO driver 會切過去；這是依上游 gpio-tegra186 driver 的寫法推論的，這台沒有原始碼可以對照。

pinmux：每個 pad 一個暫存器

pinmux@2430000 是 SoC 裡的一塊暫存器區（reg 長度 0x19100，DT.5），每個 pad 在裡面佔一個 32-bit 暫存器，4-a 會讀寫的就是其中 pin 29 的那個。always-on 電源域的 pad 另外有一塊，NVIDIA 的 overlay 裡用 pinmux_aon 這個標籤引用。DT 的 binding header 裡的常數，就是直接照暫存器欄位的值定義的：

grep -n 'TEGRA_PIN_DISABLE\|TEGRA_PIN_ENABLE\|PULL_NONE\|PULL_UP\|PULL_DOWN' /lib/modules/$(uname -r)/build/include/dt-bindings/pinctrl/pinctrl-tegra.h
$ grep -n 'TEGRA_PIN_DISABLE\|TEGRA_PIN_ENABLE\|PULL_NONE\|PULL_UP\|PULL_DOWN' /lib/modules/$(uname -r)/build/include/dt-bindings/pinctrl/pinctrl-tegra.h
18:#define TEGRA_PIN_DISABLE				0
19:#define TEGRA_PIN_ENABLE				1
21:#define TEGRA_PIN_PULL_NONE				0
22:#define TEGRA_PIN_PULL_DOWN				1
23:#define TEGRA_PIN_PULL_UP				2

PULL_UP 是 2，就是上面 0x58 裡 pull 欄位（bit 3:2）的 10；tristate、enable-input 都是 0／1 的開關。所以 DT 裡寫 nvidia,pull = <TEGRA_PIN_PULL_UP>，最後就是 pinctrl driver 把 2 寫進那兩個 bit。

pinctrl：driver 不寫暫存器，只要「狀態」

如果每個 driver 都自己去寫 pinmux 暫存器，兩個 driver 就可能搶同一個 pad，而且 driver 要知道每一代 SoC 的暫存器位置。pinctrl 把這件事收到一個地方：只有 pinctrl driver 會碰 pinmux 暫存器，其他人用 DT 描述「我需要哪些 pad 設成什麼樣子」，這叫一個狀態（state）。DT 裡的寫法分兩半：

  • 設定節點放在 pinmux 節點底下：nvidia,pins 用 pad 名稱指定是哪個 pad，其他屬性各對應一個欄位（nvidia,function、nvidia,pull、nvidia,tristate、nvidia,enable-input）。屬性名稱前面的 nvidia, 表示這是 Tegra pinctrl binding 自己的格式，別家 SoC 寫法不同。
  • 引用的一方用 pinctrl-names 列出狀態名稱，pinctrl-0、pinctrl-1… 依序是各狀態的設定節點（phandle）。名稱叫 "default" 的狀態，driver core 會在 driver 的 probe() 被呼叫之前自動套用。

4-b 的 overlay 就是這樣寫的：fragment@1 在 pinmux 節點底下加一個設定節點，DT.6 節錄的 fragment@0 裡 edge-led 的 pinctrl-0 = <&edge_led_pins> 引用它：

那開機時的 0x58 是誰寫的？

原廠樹裡沒有 pin 29 的設定、也沒有 hog，所以 Linux 開機時根本沒動過這個 pad。上面那個 0x58 是在 Linux 之前就寫好的：Jetson 的早期 bootloader 會依刷機時帶進去的 pinmux 設定（NVIDIA 用一份 pinmux 試算表產生）初始化所有 pad。這部分是根據 NVIDIA 的文件，這台板子上看不到那份設定。JP6 這份預設把沒指定用途的 header 腳設成「上拉、tristate、只收輸入」，也就是 0x58，這是對沒接東西的腳最安全的狀態：不會輸出，也不會浮動。

所以要讓 pin 29 輸出，有三條路，本書會依序走過：

做法誰寫暫存器kernel 知不知道
4-a：pad_pin29.py 經 /dev/mem 直接寫userspace，繞過 pinctrl不知道；重開機就消失，pinctrl 之後也可能把它蓋掉
jetson-io／NVIDIA 的 hdr40 overlay（hog）pinctrl driver，probe 時一次套上知道；不必有 driver 使用這根腳
4-b：裝置節點上的 pinctrl-0pinctrl core，在 edge_gpio 的 probe() 之前知道，而且知道這個 pad 是給哪個 device 用的

和 4-a.4 用 /dev/mem 讀暫存器、拆欄位的結果一致，也就是 0x58 那三個開關。

DT.10常見錯誤

容易搞混的地方

前四格來自這個專案後面幾個 Step 的實際紀錄（docs/baseline.md 與 4-a、4-b 兩章），後兩格是讀 DT 時常見的誤會。

把 DT 編號當成 line 編號

症狀
DT 裡 pin 29 是 125，拿 125 去 gpioset gpiochip0，控制到的是另一根腳。
後果
動到錯的 GPIO，LED 沒反應。
正解
DT 用 binding 的 port × 8 + pin（125、48），gpiochip 用累加的 line（105、35）。用 gpioinfo 的名稱（PQ.05）對照。

i2c-N、節點、標籤當成同一套編號

症狀
看到 hdr40_i2c1 就以為是 i2c-1。
後果
overlay 的節點掛到錯的 bus，driver 永遠找不到晶片。
正解
bus 編號看 /aliases；hdr40_i2c1 是 i2c@c250000 = i2c-7。寫完用 /proc/device-tree 確認節點落在哪個 path。

改了 /boot 的檔案就以為生效

症狀
換了 dtbo，/proc/device-tree 沒變；或重跑 jetson-io 後自己的節點不見了。
後果
拿舊的樹在 debug 新的 driver。
正解
kernel 只看開機時 UEFI 交給它的樹；這台沒有 runtime overlay，改完要重開機。jetson-io 會重寫 JetsonIO label。以 /proc/device-tree 為準。

直接用 dtc 編含巨集的 .dts

症狀
dtc 在 #include 那一行報 syntax error、Unable to parse input tree。
後果
編不出來，或改成手填數字之後失去可讀性。
正解
先 cpp -nostdinc -undef -x assembler-with-cpp -I <kernel>/include，再交給 dtc（4-b 的 dts/Makefile）。

用 cat 看 cell 屬性

症狀
cat …/reg 印出亂碼或什麼都沒有。
後果
以為屬性是空的或壞了。
正解
cell 是 big-endian 的 32-bit 二進位：用 od -An -tx1；字串用 tr '\0' '\n'；整棵看用 dtc -I fs。

把 phandle 數字寫死

症狀
從 dtc -I fs 抄 <0xf3 …> 進自己的 overlay。
後果
原廠 DT 一更新，0xf3 可能變成別的節點，GPIO 指到錯的 controller。
正解
原始碼一律寫 &gpio 這種標籤引用，讓 dtc 和開機時的合併去填數字。
DT.11收尾DT → 4-a

這一章讀懂了什麼

  • DT 是開機時交給 kernel 的資料，kernel 看的是記憶體裡合併後的那份，開放在 /proc/device-tree（目錄 = 節點、檔案 = 屬性）。
  • 屬性只是 byte：字串以 \0 分隔、cell 是 big-endian 32-bit；reg 怎麼切由父節點的 #address-cells／#size-cells 決定。
  • phandle 讓節點互相引用；引用後面接幾格，由被引用的 controller 的 #gpio-cells／#interrupt-cells 決定。
  • 父節點決定誰建 device（platform bus 或 i2c core），compatible 決定哪個 driver 認領；device 可以存在而沒有 driver。
  • pad 是腳位背後的電路、pinmux 是設定它的暫存器、pinctrl 是 Linux 管它的子系統；pad 的設定寫成 DT 的狀態節點，由裝置的 pinctrl-0 或 hog 引用。
  • overlay 的格式（fragment、__fixups__）與怎麼安裝：4-b。
  • driver 端讀屬性的 API（devm_gpiod_get()、of_match_table、I2C 的 i2c_driver）：4-b、5-b、7 各自介紹。

下一章 4-a 會先繞過 Device Tree：用 userspace 程式控制 pin 29，再用 /dev/mem 直接改 pinmux@2430000 裡的一個暫存器，找出 LED 不亮的原因。這兩件事都是 kernel 不知情的，所以 4-b 回頭把它們寫進 Device Tree，交給 kernel 管。

1. 一個節點的 reg 是 00 00 00 00 03 16 00 00 00 00 00 00 00 01 00 00，它是什麼位址、多長？要先確認什麼？

先確認父節點的 #address-cells／#size-cells。如果是 2 / 2（像 bus@0），位址是 0x03160000、長度 0x10000。如果父節點是 1 / 1，同一串 byte 就變成兩段：(0, 0x03160000) 和 (0, 0x10000)，意思完全不同。可以貼進 DT.5 的計算機試。

2. 某按鍵節點寫 gpios = <0xf3 0x38 0x01>，在 gpiochip0 是哪一條 line？（提示：port A–G 實際共有 43 支腳）

0xf3 是 gpio@2200000 = gpiochip0。0x38 = 56 = 7 × 8 + 0，port 7 是 H，所以是 PH.00；port H 從 line 43 開始，第 0 支就是 line 43，active-low。這正是 Step 5 按鍵用的腳（overlay 裡寫成 TEGRA234_MAIN_GPIO(H, 0)）。

3. 板子上的 INA219 一直在那裡，為什麼 Step 6 用 i2cget 讀得到它，/sys/bus/i2c/devices/7-0041 卻要等 Step 7 的 overlay 開機後才出現？

i2cget 透過 /dev/i2c-7 直接在 bus 上送封包，不需要 kernel 知道那裡有晶片。7-0041 是 i2c core 依 DT 子節點建立的 client；I2C 不會自動列舉，沒有 ina219@41 節點就不會建立 device，driver 也就沒有東西可以認領。

4. 你在 /proc/device-tree 找到一個節點，但 /sys/bus/platform/devices/ 底下沒有對應的 device。列出兩個可能的原因。

它的 status 是 "disabled"（像 ethernet@6800000）；或者它的父節點不是根節點也不是 simple-bus，device 由別的 bus 建立（例如 I2C controller 底下的節點會變成 i2c client，不是 platform device），或是根本沒有人替它建 device（例如 prod-settings 這種只給 driver 讀的設定節點）。

5. 4-b 把 pad 設定的 pinctrl-0 放在 edge-led 節點上，NVIDIA 的 hdr40 overlay 放在 pinmux 節點自己身上。edge_gpio.ko 沒載入時，兩種做法下 pin 29 的 pad 各是什麼狀態？

放在 edge-led 上：狀態要等 edge_gpio 的 probe() 之前才套用，module 沒載入就不會套，pad 維持 bootloader 設的 0x58（tristate）。放在 pinmux 上（hog）：pinctrl driver 開機 probe 時就套上，不管有沒有 driver 使用這根腳，pad 都已經打開。
